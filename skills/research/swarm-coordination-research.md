# Swarm coordination: готовая спецификация для диспетчера без оркестратора

> B53 research (owner 2026-09-23): когда «всё хорошо», агенты должны работать
> без оркестратора. Пробуждение — механический диспетчер как детерминированный
> конечный автомат (DFA) по состоянию доски. Ниже — обзор готовых тактик
> координации роя и проектного управления; внизу — целевая спецификация.

## 1. Обзор готовых тактик/моделей

### 1.1 Contract Net Protocol (FIPA CNP) — задача→агент без центрального планировщика
- Источник: Reid Smith (1980); стандартизирован FIPA (SC00029, iterated SC00030).
- Суть: менеджер объявляет задачу (`call-for-proposals`), агенты шлют `proposal`,
  менеджер выбирает и шлёт `accept`/`reject`, исполнитель завершает `inform`.
- Применимо: раздача задач по способности/нагрузке без центрального планировщика.
- Ограничение: требует переговоры (round-trips); для *пробуждения* избыточно,
  но **канбан-борд = та же идея**, где «call-for-proposals» материализуется как
  статус `ready` на карточке задачи.

### 1.2 Blackboard system — среда как единственный канал связи
- Источник: Hearsay-II, BB1, GBB (классика ИИ).
- Суть: знания-source'ы не общаются напрямую; все пишут/читают общую «доску»
  (blackboard), управляемую control-shell (может быть простым priority-автоматом).
- Применимо: наш `graph.mdbx` (память) + `skynet_tasks` (борд) — буквально
  blackboard. Знание-источники = агенты. Control-shell = оркестратор-диспетчер.
- Ключевой урок: **control-shell может быть детерминированным** (состояние →
  выбор KS по trigger-условиям), без генеративных решений в рутине.

### 1.3 Stigmergy — непрямая координация через следы в среде
- Источник: Grassé (1959), swarm intelligence.
- Суть: действие оставляет след (феромон/артефакт), который стимулирует
  следующее действие любого агента; планирование «встроено» в среду.
- Применимо: наш Kanban-борд — чистый stigmergic артефакт: агент, изменив
  статус задачи, «оставляет след», на который реагирует следующий агент.
- Урок: **минимум прямых сообщений; максимально — реакция на состояние борда.**

### 1.4 Project management: pull-based Kanban + WIP-лимиты
- Суть: агент сам берёт карточку из `ready` при свободном слоте (WIP-лимит),
  а не получает задачу от планировщика. Доказанная практика (Kanban/TPS).
- У нас уже так: §14 (Kanban-поток, pull-модель, WIP in_progress≤3, review≤2).
- Урок: диспетчеру НЕ нужно распределять задачи — только (a) следить за
  WIP, (b) пробуждать агентов, у которых появилась готовая работа.

### 1.5 Современные фреймворки агентов (контекст)
- LangGraph: явный **граф состояний + условные переходы** (DFA по сути);
  узлы вызываются, когда их precondition удовлетворён. Канон для построения
  «производственных» пайплайнов агентов.
- CrewAI/AutoGen: sequential/hierarchical процессы + ручные handoffs.
- Урок: даже современные инструменты сводят координацию к **детерминированному
  графу состояний с условиями на переходах** — никакой магии, только чёткий
  формализм и минимум LLM в самом диспетчере.

## 2. Синтез: целевая спецификация «SwarmDisp-DFA»

Вывод исследования: не нужно изобретать новое. Комбинация трёх готовых моделей
— **stigmergic board + blackboard control + DFA** — даёт спецификацию диспетчера,
в которой оркестратор в рутине не нужен:

### 2.1 Состояния борда (вход автомата)
Читаются из `skynet_tasks` (MCP-memory) — карточка задачи:
- `backlog` → `ready` (готова к взятию) → `in_progress` → `review` → `done`.
- WIP-лимиты: `in_progress ≤ 3`, `review ≤ 2` (уже в §14).

### 2.2 События (переходы DFA) — кто делает переход
| Переход | Триггер | Действует |
|---|---|---|
| `backlog→ready` | владелец/координатор (или комиссия ревьюеров) ставит приоритет | любое лицо с правом |
| `ready→in_progress` | **агент сам берёт карточку** (pull, §14) | свободный агент |
| `in_progress→review` | агент закончил + VALIDATED-матрица (§27) | агент-исполнитель |
| `review→done` | ревьювер APPROVED (REV:*) | доменный ревьювер |
| `review→in_progress` | needs-work | ревьювер |
| `done` | — | — |

### 2.3 Диспетчер-пробуждатель (механический, без LLM)
Периодический цикл (как сейчас duty daemon, но проще):
1. Прочитать борд.
2. Для каждой карточки вычислить, кому она «адресована» по правилу
   (owner поля, домен REV:, статус WIP) — **чистая таблица соответствия**.
3. Если у агента появилась адресованная ему работа и его слот свободен →
   wake (письмо/FIFO). Никаких приоритетных разборов почты, никаких
   «координационных» писем — только триггер «появилась твоя работа».
4. Staleness: если карточка висит в `in_progress` дольше SLA и heartbeat
   агента устарел → эскалация координатору (единственное генеративное место).

Это **DFA**: состояния = статусы борда + занятость агента; переходы —
таблица; выходы — wake/write статуса. Оркестратор остаётся только для
исключений (staleness, конфликты, эскалации, вехи) — редкие события.

### 2.4 Что берём из чего
- Kanban pull + WIP — уже реализовано (§14) — база.
- Blackboard control — борд как единственный канал («нет писем в рутине»).
- CNP — опционально для раздачи задач, когда владелец делегирует «кому-то
  свободному» (можно как расширение, не критично для v1).
- Stigmergy — принцип: агент пишет статус, диспетчер не рассылает инструкции.
- LangGraph-подход — выразить правило как таблицу переходов (детерминизм),
  проверяемую юнит-тестом.

### 2.5 Принципы внедрения (чтобы не получить «множество исправлений»)
1. **Не убирать оркестратор сразу** — добавить «тихий режим»: диспетчер
   ничего не решает, только логирует «что бы сделал»; сверка с фактическими
   действиями координатора несколько дней.
2. Правило «борд первичен, письма вторичны»: письма остаются только для
   вех/эскалаций/вопросов владельцу; рутина — реакция на статусы.
3. SLA-поля на карточках (`started_at`, `finished_at`) уже есть (§14) —
   для staleness-детекции нужны только они.
4. Всё как таблица в коде (list of dicts), без YAML-движков и без LLM в петле.
5. Валидация: «симулятор» на историческом борде — диспетчер воспроизводит
   прошедшие 2 недели и должен выдать ровно те же wake, что делал координатор.

## 3. Вывод для владельца
Готовой «коробочной» спецификации роевого DFA-диспетчера для LLM-агентов нет
(фреймворки дают графы, но не политику роя). Однако **композиция трёх зрелых
моделей** (CNP task-allocation + blackboard control + stigmergic board) плюс
уже существующий у нас Kanban-pull §14 даёт полную и проверяемую спецификацию.
Исследование завершено; следующий шаг (по вашему решению) — фаза «тихого
диспетчера» (dry-run поверх текущего оркестратора, ~день наблюдения) или
развёрнутый документ-спецификация с таблицами переходов.
