## 1. Инструменты

### 1.1. `mdbx_chk` — проверка целостности

Полное описание опций — `src/man1/mdbx_chk.1`. Ключевое:

| Опция | Что делает |
| --- | --- |
| `-v…-vvvvv` | Уровень подробности: от сводки пространства/страниц до полного списка pgno в GC-записях и размеров каждой пары ключ→значение |
| `-q` | Полная тишина (ничего, даже ошибки) |
| `-c` | Кооперативный режим открытия (не эксклюзивный). **Только эксклюзивный режим** позволяет полную проверку всех мета-страниц и фактического размера файла |
| `-w` | Открытие read-write с блокировкой записи: позволяет откат к последнему steady-коммиту (если БД не была закрыта корректно) и проверку txnid мета-страниц; без `-w` — read-only |
| `-d` | Отключить постраничный обход B+tree; **без него невозможно** обнаружить lost-unused и double-used страницы |
| `-i` | Игнорировать ошибки порядка ключей (ложные при кастомных компараторах) |
| `-s table` | Проверить только конкретную таблицу |
| `-0/-1/-2` | Проверка с конкретной мета-страницы |
| `-t` / `-T` | Переключиться на указанную мета-страницу после успешной / **даже при неуспешной** проверке |
| `-u` / `-U` | Warmup БД (уведомление ядра) / warmup + принудительная загрузка страниц в память |

Exit-код: `0` — ошибок нет, ненулевой — найдены ошибки (+ диагностика в stderr).

**Что `mdbx_chk` НЕ проверяет** (без `-d` нельзя): двойное использование и потерю
страниц; при кастомных компараторах упорядоченность даёт ложные срабатывания →
используйте `-i`.

### 1.2. `MDBX_ENABLE_PROFGC` — профилирование GC

Опция сборки (`CMakeLists.txt:815`, `add_option(MDBX ENABLE_PROFGC ...) OFF`).
Профиль GC накапливается в LCK-файле (общий для всех процессов) и возвращается
в `mdbx_txn_commit_ex()` / `mdbx_txn_checkpoint()`; сбрасывается при коммите
top-level транзакции (`mdbx.h:4193–4280`).

Поля `gc_prof` (структура `MDBX_commit_latency.gc_prof`, `mdbx.h:4221–4276`):

| Поле | Что значит | Норма |
| --- | --- | --- |
| `max_reader_lag` | Максимальная разница между свежим и старейшим MVCC-снапшотом (в коммитах) | Зависит от паттерна чтения; резкий рост — долгие читатели |
| `max_retained_pages` | Максимум страниц, удержанных от переиспользования старыми снапшотами | Рост = давление долгих читателей (`functional-architecture.md` §10) |
| `work_rtime_monotonic` | Wall-clock время чтения/поиска в GC для пользовательских данных | Должно быть малой долей коммита |
| `work_xtime_cpu` | CPU user-mode на подготовку страниц из GC (включая подкачку) | Page-fault'ы — красный флаг (см. `majflt`) |
| `work_rsteps` | Число итераций чтения-поиска в GC при аллокации | Растёт при фрагментации |
| `work_xpages` | Число запросов выделения последовательностей (больше одной страницы) | Много = большие значения или фрагментация |
| `work_majflt` | Hard page faults в GC | >0 при активной записи — признак нехватки памяти/page-cache |
| `self_*` | То же, но для поддержки самой GC | Сравнение work/self показывает стоимость «мусора» против «данных» |
| `wloops` | Итераций обновления GC (>1 = повторы/рестарты) | >1 часто — признак нестабильности детента |
| `wipes` | Уничтоженные steady-точки в `MDBX_UTTERLY_NOSYNC` | Только в this режиме |
| `flushes` | Принудительные fsync вне UTTERLY_NOSYNC, чтобы избежать роста БД | Частые — эффект «квази-долгого читателя» |
| `kicks` | Обращения к HSR | >0 = пространство исчерпано читателями |
| `pnl_merge_*` | Время/объём/число слияний списков страниц | — |

Аналог по «простой» статистике страниц — `pgops` (`src/layout-lck.h:44–80`):
`newly`, `cow`, `clone`, `split`, `merge`, `spill`, `unspill`, `wops`, `msync`,
`fsync`, `prefault`, `mincore`, `incoherence` (счётчик срабатываний issue #269).

### 1.3. `MDBX_commit_latency` — стадии коммита

`struct MDBX_commit_latency` (`mdbx.h:4193–4280`), заполняется `mdbx_txn_commit_ex()`
и `mdbx_txn_checkpoint()`:

| Поле | Стадия | Пороги/норма |
| --- | --- | --- |
| `preparation` | Подготовка: вложенные, обновление записей таблиц, уничтожение курсоров | Малая доля whole |
| `gc_wallclock` | Обновление GC по wall clock | Растёт при тяжёлой фрагментации/больших значениях |
| `audit` | Внутренний аудит (если включён) | 0, если аудит выключен |
| `write` | Суммарное время `write()` при коммите | Растёт с объёмом грязных страниц |
| `sync` | Время `fdatasync()`/`msync()` | Зависит от режима sync; ноль в nosync-режимах |
| `ending` | Завершение (освобождение ресурсов) | — |
| `whole` | Полное время коммита | Сумма стадий + накладные |
| `gc_cputime` | CPU user-mode на GC | Сравнивать с gc_wallclock |

Типичные аномалии: `sync` доминирует → проверяйте режим долговечности и число
транзакций; `write` большой при малом объёме данных → спилл/дублирование;
`gc_wallclock` велик → фрагментация GC или bigfoot-цепочки.

### 1.4. `MDBX_FORCE_ASSERTIONS` / `MDBX_CHECKING` / `MDBX_DEBUG`

Семантика — `src/options.h:243–249,585–649`:

- `MDBX_DEBUG`: `0` (дефолт) — всё выключено; `>0` — включает логирование +
  ассерты + внутренний аудит; `>=3` дополнительно `MDBX_DBG_AUDIT`; `<0` — полная
  тишина включая критические ошибки.
- `MDBX_CHECKING` (может задаваться отдельно от DEBUG; дефолт = DEBUG):
  - `0` — все проверки, кроме `ENSURE()`, выключены;
  - `1` — `CHECK0()`/`ASSERT()` (лёгкие, всегда активны);
  - `2` — + `CHECK1()` (средние, управляются `MDBX_DBG_ASSERT`);
  - `3` — + `CHECK2()` (дорогие);
  - `<0` — всё выключено, включая `ENSURE()`.
- `MDBX_FORCE_ASSERTIONS=1` — принудительный `MDBX_CHECKING=2` (deprecated,
  используйте `MDBX_CHECKING`). Сочетание обоих — ошибка сборки
  (`src/options.h:643–647`).

Цена: `MDBX_CHECKING=2/3` существенно замедляет хот-пути; для воспроизведения
тонких багов — включайте, для бенчмарков — выключайте.

### 1.5. Диагностические API

- `mdbx_env_info_ex()` — геометрия, меты `meta[3]`, UUID (`mi_dxbid`), статистика
  операций со страницами; поля авто-sync (`mdbx.h:2926,2933`).
- `mdbx_txn_info()` — пер-транзакционная диагностика (`mdbx.h:4090–4145`):
  `txn_id`, `txn_reader_lag`, `txn_space_used/limit_soft/limit_hard/retired/
  leftover/dirty`, page-get счётчики. Ключевые поля для диагностики долгих
  читателей — `txn_space_retired` (сколько освободится после читателя) и
  `txn_space_leftover` (порог срабатывания HSR).
- `mdbx_gc_info()` — состояние переиспользования.
- `mdbx_reader_list()` / `mdbx_reader_check(env, &dead)` (`mdbx.h:6880,6890`) —
  список живых читателей и подсчёт мёртвых слотов (`dead`), которые можно очистить.
- `mdbx_stat -p` — общая статистика операций со страницами (`src/man1/mdbx_stat.1:40–41`).

### 1.6. Логирование

Макросы `TRACE/DEBUG/VERBOSE/NOTICE/WARNING/ERROR` (`src/logging_and_debug.h:177–210`).
Настройка — `mdbx_setup_debug()` и переменные окружения; уровни
`MDBX_LOG_DEBUG/TRACE` удобны для трассировки ошибок API. Колбэк логов без
`vprintf` — для привязок.

### 1.7. Санитайзеры и valgrind

CMake-опции (`cmake/profile.cmake`):

- `ENABLE_ASAN` (`cmake/profile.cmake:42`), `ENABLE_UBSAN` (`:44`) — Address/UB
  санитайзеры; поддерживаются GCC/CLANG/MSVC (`cmake/compiler.cmake:357–358,956–971`).
- `ENABLE_MEMCHECK` — интеграция valgrind/memcheck.h (`cmake/profile.cmake:48–64`);
  нужен установленный заголовок valgrind. Готовый `valgrind.supp` лежит в корне.
- `ENABLE_GPROF`/`ENABLE_DTRACE` — профилирование.

Известные оговорки: TSAN в CMake не включён из коробки (см. §3.5); для проверки
гонок используйте стресс-тесты под `ENABLE_ASAN`/`ENABLE_UBSAN` или ручную
инструментацию.

## 2. Пошаговые сценарии отладки

Для каждого: симптомы → гипотезы → проверка → решение.

### 2.1. БД растёт без видимой причины

Симптом: файл увеличивается, хотя логический объём данных не меняется.

Гипотезы (по убыванию вероятности):
1. **Долгий читатель** пинит GC (`functional-architecture.md` §10.1, §17.2).
2. Режим `MDBX_SAFE_NOSYNC` — постоянный «квази-долгий читатель» (steady-коммит).
3. Фрагментация GC / rp_augment_limit заставляют дописывать в хвост.
4. Bigfoot-цепочки после гигантских значений.

Шаги:
1. `mdbx_env_info_ex` → смотрите меты и геометрию.
2. `mdbx_txn_info` у долгоживущих читателей → `txn_reader_lag`, `txn_space_retired`.
3. `mdbx_reader_list()` → кто держит старые снапшоты.
4. `mdbx_txn_commit_ex()` с PROFGC → `max_reader_lag`, `max_retained_pages`, `kicks`.
5. `mdbx_stat -p` → соотношение `newly` vs `cow` (рост = новые страницы вместо переиспользования).
6. `mdbx_chk -w` → нет ли потери страниц (lost pages).
7. Если всё чисто и это SAFE_NOSYNC — настройте авто-sync (`syncbytes`/`syncperiod`)
   или перейдите на `NOMETASYNC`/`DURABLE`.

Решение: парковка читателей, HSR-колбэк, steady-point'ы, дефрагментация (§2.9),
коррекция геометрии.

### 2.2. Коммит тормозит

Симптом: `commit` занимает заметное время, throughput падает.

Шаги:
1. `mdbx_txn_commit_ex()` → разложить `whole` на стадии (`mdbx.h:4193`).
2. `sync` доминирует → проверьте режим долговечности; слишком частые fsync при
   мелких транзакциях → укрупняйте батчи или переходите на
   `MDBX_SAFE_NOSYNC`/`NOMETASYNC`.
3. `gc_wallclock`/`gc_cputime` велики → включите `MDBX_ENABLE_PROFGC` и посмотрите
   `work_rsteps`/`work_xpages`/`work_majflt`: фрагментация/большие значения.
4. `write` велик при малых данных → spилл работает рано (dp_limit мал) или
   дублирование грязных страниц; проверьте `MDBX_opt_txn_dp_limit`.
5. В WRITEMAP-режиме тормоза → page-fault'ы: включите prefault
   (`MDBX_opt_prefault_write_enable`) и следите за `mincore`/`prefault` счётчиками.
6. `mdbx_stat -p` → msync/fsync счётчики: много мелких синков.

Решение: режим sync, dp_limit/спилл-знаменатели, prefault, батчинг,
дефрагментация, проверка `incoherence` (issue #269).

### 2.3. `MDBX_MAP_FULL`

Симптом: запись возвращает `MDBX_MAP_FULL`.

Порядок диагностики:
1. `mdbx_txn_info` → `txn_space_limit_hard` (верхняя граница геометрии) vs `used`.
2. `mdbx_reader_list()` → старые снапшоты пинят пространство.
3. PROFGC → `kicks`, `max_reader_lag`, `max_retained_pages`.
4. Проверьте, что HSR-колбэк установлен (`mdbx_env_set_hsr`), парковка используется.
5. Проверьте геометрию: `upper` занижен? Файл реально упёрся?

Решение: HSR-колбэк (ждать/убить читателя/расти), выселение припаркованных,
новый steady-point, увеличение `upper`, явная дефрагментация.

### 2.4. Deadlock / `MDBX_BUSY`

Симптом: взаимоблокировка или `MDBX_BUSY` при операциях.

Гипотезы:
- `MDBX_NOSTICKYTHREADS` + функции с write-блокировкой: транзакция переехала в
  другой поток;
- две среды/два писателя конфликтуют;
- многократное открытие БД в процессе (запрещено; legacy — `MDBX_DBG_LEGACY_MULTIOPEN`).

Шаги: проверьте дисциплину потоков (коды `MDBX_THREAD_MISMATCH`,
`MDBX_TXN_OVERLAPPING`, `MDBX_BAD_RSLOT`), единый ли поток владеет писателем,
нет ли повторного открытия. `mdbx_reader_list()` покажет чужих владельцев.

### 2.5. Долгий читатель блокирует GC

Симптом: растёт файл, GC пуст/заморожен, коммиты упираются.

1. `mdbx_reader_list()` → кто и с каким `txnid`.
2. `mdbx_txn_info` долгого читателя → `txn_reader_lag`, `txn_space_retired`.
3. Решения: парковка (`mdbx_txn_park`/`autounpark`), HSR-колбэк (kill/reset),
   выселение (`restart_if_ousted`).

### 2.6. Повреждение данных / `MDBX_CORRUPTED`

Симптом: операции возвращают `MDBX_CORRUPTED` или chk находит повреждения.

1. `mdbx_chk -w -vvv` → локализуйте (мета? дерево? GC? порядок ключей?).
2. Проверьте среду: включён ли `boot_id`-контроль (LXC?), не было ли
   некогерентности page cache (`incoherence` счётчик, `MDBX_FORCE_CHECK_MMAP_COHERENCY`).
3. Если повреждена одна из мет → попробуйте `mdbx_chk -1`/`-2` (другие меты) и
   `-T` для переключения на валидную.
4. `MDBX_WANNA_RECOVERY` при read-only → откройте read-write или
   `mdbx_env_open_for_recovery()` (`mdbx.h:7079`) для аккуратного восстановления.
5. Recovery-проверки (0.12.7+) не изменяют базу — безопасно запускать.

### 2.7. Утечка слотов читателей

Симптом: `mdbx_reader_list` показывает мёртвых читателей; слоты кончаются.

1. `mdbx_reader_check(env, &dead)` → сколько мёртвых.
2. Причина обычно: потоки завершились без очистки (нет TLS-деструктора /
   DSO-выгрузка). Проверьте работу `rthc_thread_dtor` (glibc bugs #21031/#21032).
3. Для потоков без TLS — явная регистрация/дерегистрация
   (`mdbx_thread_register/unregister`).

### 2.8. Производительность ниже ожидаемой

1. Сборка отладочная? `MDBX_CHECKING>0` замедляет; соберите release.
2. `mdbx_stat` → высота дерева, заполненность, длина ключей.
3. Page size: маленькая страница → высокое дерево.
4. Проверьте NUMA/страничный кэш; `mdbx_env_warmup` для холодного старта.
5. PROFGC → дорогой GC-путь.
6. Сравните с бенчмарками проекта (учитывайте режим sync).

### 2.9. Фрагментация и дефрагментация

1. Диагностика: PROFGC (`work_rsteps`/`work_xpages`), `mdbx_stat -p` (split/merge).
2. Дефрагментация: `mdbx_env_defrag(defrag_atleast, time_atleast_dot16, defrag_enough,
   time_limit_dot16, acceptable_backlash, preferred_batch, cb, ctx)`
   (`mdbx.h:7688`); код результата `MDBX_defrag_enough_threshold=16`
   (`mdbx.h:7512`).
3. Утилита `mdbx_defrag` — CLI-обёртка.

### 2.10. Проблема после fork

Симптом: в дочернем процессе операции падают/висят (`resource temporarily unavailable`).

Решение: после `fork()` вызовите `mdbx_env_resurrect_after_fork()` (`mdbx.h:3214–3252`)
в ребёнке; без него использование окружения невозможно. Не вызывайте в родителе
и дважды.

### 2.11. Windows-специфичные тормоза

- `LockFileEx` медленный в ядре Windows; наивные бенчмарки мелких транзакций
  проигрывают LMDB (сознательный компромисс, `libmdbx-improvements.md` §11.3).
- Расширение файла через Native API; сжатие — только в однопроцессном сценарии;
  изменение геометрии приостанавливает потоки (SRWL на читателя).
- Используйте overlapped/async запись (`WriteGather`, небуферизованный I/O).

### 2.12. Контейнеры и спец-среды

- **LXC**: `boot_id` меняется/одинаков для контейнеров — контроль отката слабых
  мет учитывает это.
- **WSL1**: возврат `ENOLCK` — работа невозможна принципиально, это штатное
  поведение.
- **tmpfs/ENOSPC**: расширение файла на tmpfs — смотрите ошибки `fallocate`/SIGBUS;
  отключайте/настраивайте геометрию.
- **NFS/CIFS/SMB**: только эксклюзивный режим или кооперативный read-only;
  копирование работает (fix fcntl/flock конфликта).

## 3. Внутренняя отладка для разработчика

### 3.1. Добавление точки трассировки в ядро

Используйте макросы `TRACE/DEBUG/VERBOSE/NOTICE/WARNING/ERROR`
(`src/logging_and_debug.h:177–210`) — они гейтятся уровнями `MDBX_DEBUG`/
`MDBX_CHECKING` и не попадают в релизные сборки с `MDBX_DEBUG=0`. Для временной
отладки добавьте уровень и уберите после; не оставляйте `printf` в хот-путях.

### 3.2. Написание теста для воспроизведения

- Используйте стохастический `mdbx_test` (`tests/framework/`) с фиксированным
  `--prng-seed` для воспроизводимой последовательности операций одного актора
  (межпроцессная интерливинг не воспроизводится). Ограничьте `--nops`.
- Для регрессий по конкретному issue — `tests/ut/issues/` (GoogleTest).
- Укажите seed и конфигурацию в баг-репорте.

### 3.3. Интерпретация краш-дампа

Краш внутри mmap (Bus error/SIGSEGV): адрес → вычислите страницу
`pgno = (addr - base) / pagesize` → определите, принадлежит ли она дереву/GC →
проверьте, не переиспользована ли страница (txnid на странице) →
сравните с `txn->txnid/front_txnid`. Диагностические зонды/`ENSURE` подскажут
нарушенный инвариант.

### 3.4. Проверка гипотезы о гонке

- TSAN в CMake из коробки нет — включите вручную (`-fsanitize=thread`).
- Стресс-тесты: `battery-tmux.sh`/`stochastic.sh` с несколькими процессами.
- Ищите доступ к разделяемым полям `lck->...` (RLT, pgops, gc_prof) без атомик;
  `incoherence` счётчик ловит issue #269.

### 3.5. Локализация регрессии

- Биссекция по коммитам dev-ветки (политика — каждый коммит CI-green).
- Сравнение `commit_latency`/PROFGGC до/после изменения.
- `git blame` по подозрительному участку; сверка с ChangeLog.
