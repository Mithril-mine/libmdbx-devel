# Verification campaign protocol — agent brief template (libmdbx master b5ba3018)

Единый протокол для всех верификационных агентов потоков A/B/C.
Координатор выдаёт агенту: протокол, точный список функций, актуальные леммы
LEDGER, формат строки реестра. Агент возвращает отчёт в формате ниже.

## Обязательства доказательства (P1–P7)

- **P1** условия: корректность предиката, полнота разбиения, достижимость ветвей (мёртвые фиксируются);
- **P2** арифметика: домены операндов, overflow/underflow, единицы, знаковость;
- **P3** память: границы, выравнивание, lifetime (машина состояний страницы);
- **P4** циклы: убывающая мера терминации;
- **P5** выходы: согласованность состояния на каждом выходе (вкл. error-пути/goto);
- **P6** конкуренция: single-writer, acq/rel, safe64-ABA, lifetime reader-слота;
- **P7** формат/ABI: layout-dxb/lck, двухфазный протокол мет.

Логгинг-арифметика — одно бланкетное заключение на файл.

**Вердикты функции:** `PROVED` / `PROVED·A` (допущения перечислены, каждое —
обязательство) / `REFUTED` (контрпример + репродьюсер) / `SUSPECT` / `N/A`
(мёртвый код — доказать недостижимость).

## Обязанности агента сверх отчёта (обязательны с Волны 2)

### 1. Пополнение базы знаний shared-graph-memory (MCP)

После завершения транша агент обязан записать в Store
(`shared-graph-memory_mdbx_*`):

- **Каждую находку** — `safe_store(key, type, summary, importance)`:
  - `bug:<модуль>:<slug>` (type=bug) — дефект/REFUTED; importance 1.0 critical,
    0.9 high, 0.7 medium, 0.4 low;
  - `bottleneck:<модуль>:<slug>` (type=bottleneck) — liveness/перф-опасность;
  - `fact:verification:<slug>` (type=fact) — установленная лемма/инвариант,
    полезная последующим траншам;
  - `proc:verification:<slug>` (type=proc) — воспроизводимый приём анализа.
- **Связи**: `link(record_key, "related-to", "fn:<символ>")` для каждой
  находки/инварианта на затронутые символы карты (`cg_symbols` для проверки
  ключей); при необходимости `link(..., "guarded-by", "test:...")`.
- **ADR** для сквозных решений кампании: `adr_update(name, ...)` — например
  `verification-campaign-protocol`, `refuted-handling-policy`.
- Повторное использование: перед началом транша — `recall("fact:verification:*")`
  и `search(<тема>)`; не переоткрывать уже доказанное.

### 2. Дополнения в инженерную документацию

Агент готовит (не коммитит в канонические доки сам — собирает в
`docs/verification/doc-additions.md`, секция по своему траншу):

- предложения по `libmdbx-invariants.md` (новые доказанные инварианты —
  нумерация продолжает существующую);
- предложения по `subsystem-map.md` / `module-interfaces.md` (уточнение границ,
  контрактов, риска);
- предложения по `test-coverage.md` (новые белые пятна/тесты, вытекающие из
  REFUTED и допущений PROVED·A);
- контракты примитивов, пригодные для `module-interfaces.md` (pre/post-условия
  в формате пары «структура→потребитель»).

Координатор сводит дополнения, провалидирует и вносит в канонические доки на
ветке кампании.

## Формат строки реестра (LEDGER)

`### <name> (file:l0-l1) — VERDICT` + компактные доказательства по P1–P7
(тривиально-безопасные — одной строкой), список ASSUMPTIONS (A-ids),
FINDINGS (F-ids + контрпример). В конце отчёта: сводная таблица находок,
список установленных лемм.

## Полнота

Механические свипы (grep-реестры по классам операторов) прилагаются к отчёту
как контроль полноты ручной верификации. REFUTED обязан иметь репродьюсер
(`docs/verification/repro/`). Массовые прогоны существующих тестов (вкл.
ASAN/UBSAN) НЕ выполняются; точечные аналитические пробы — допускаются.
