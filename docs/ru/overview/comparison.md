# Сравнение с другими СУБД

> Смежные: [Обзор](index.md) · [Ограничения и подводные камни](restrictions.md) ·
> [Режимы долговечности](../getting-started/durability-modes.md) ·
> [Improvements относительно LMDB](../deep-dive/improvements.md)

_libmdbx_ — встраиваемая транзакционная key-value СУБД. Здесь она сопоставлена
с движками, с которыми её обычно сравнивают: с ближайшими родственниками —
[LMDB](https://ru.wikipedia.org/wiki/Lightning_Memory-Mapped_Database) и
[bbolt](https://github.com/etcd-io/bbolt) (BoltDB) — и с «якорными»
альтернативами из других классов — [SQLite](https://www.sqlite.org/) и
[RocksDB](https://rocksdb.org/). Оси выбраны те, которыми обычно и делают
выбор: лицензия, модель надёжности, конкурентность, лимиты, компактация,
инструменты, платформы.

## LMDB

Ближайший родственник: _libmdbx_ исторически — глубоко переработанный потомок
LMDB, сегодня самостоятельная кодовая база. Полный каталог отличий —
[Improvements относительно LMDB](../deep-dive/improvements.md); коротко о том,
что заметно при выборе:

- размер БД у LMDB задаётся заранее и не меняется (по умолчанию всего 10 МиБ),
  у libmdbx — авто-рост на лету с настраиваемой геометрией;
- ключи длиннее: ≈½ страницы при настраиваемом размере страницы до 64 КиБ,
  против ≈511 B у LMDB;
- формат файла libmdbx не зависит от разрядности и порядка байтов
  (файл, созданный на 32-битной big-endian системе, читается на x86-64);
- асинхронный режим `MDBX_SAFE_NOSYNC` гарантирует целостность после сбоя
  (откат к последнему steady-состоянию), тогда как `MDB_NOSYNC` у LMDB может
  разрушить базу;
- непрерывная zero-overhead компактация и дефрагментация против
  «перелить в компакт-копию» у LMDB;
- стабильная навигация курсоров после удаления записей — исправлены
  унаследованные от LMDB краевые случаи позиционирования;
- диагностика (`mdbx_chk`), защита от зависших читателей, полная типобезопасная
  обвязка C++ и ещё [десятки доработок](../deep-dive/improvements.md).

API близок по духу, миграция с LMDB обычно не меняет логику приложения.

## bbolt (BoltDB)

[bbolt](https://github.com/etcd-io/bbolt) — потомок идей LMDB на Go
(наследие etcd). Семейство то же — copy-on-write B+tree без WAL, один писатель,
снапшоты у читателей. Ключевые отличия от libmdbx:

- только один процесс на БД: эксклюзивная блокировка файла, никакого общего
  доступа «роем» процессов;
- файл не уменьшается сам: компактация — только отдельной утилитой;
- без учёта дискового I/O libmdbx примерно в 3 раза быстрее.

## SQLite

Если нужны SQL и реляционная модель — SQLite в этом классе безальтернативен.
Но для чистого key-value доступа он тяжелее: парсинг SQL на каждом запросе,
копирование данных между приложением и библиотекой вместо прямого доступа
через mmap. WAL-режим даёт конкурентное чтение с одним писателем;
компактация — `VACUUM`, то есть полная перезапись файла (или инкрементальный
`auto_vacuum` ценой накладных расходов).

## LevelDB / RocksDB

LSM-семейство (LevelDB, RocksDB и др.) оптимизировано под интенсивную запись
и большие объёмы на медленных носителях: запись идёт в memtable и WAL,
фоновые потоки уплотняют данные. Цена — read/space amplification, фоновые
потоки и потоки компакции, заметный объём кода и зависимостей, отсутствие
доступа из нескольких процессов. RocksDB допускает конкурентную запись из
нескольких потоков, но это не делает её «легковесной».

libmdbx против LSM — это классический размен «чтение против записи»:
минимальный оверхед на чтение, отсутствие фоновых потоков и полный
набор транзакционных гарантий — против преимуществ LSM на write-heavy
нагрузках. Стоит заметить, что из-за отсутствия WAL у libmdbx объём записи
пропорционален изменившимся страницам, а на быстрых NVMe разрыв с LSM
по записи обычно невелик.

## Производительность

Любые числа зависят от профиля нагрузки — измеряйте на своём. Подтверждённые
ориентиры: без учёта времени дискового I/O _libmdbx_ примерно в 3 раза быстрее
BoltDB, а в отдельных крайних случаях — например, повторные чтения «горячих»
ключей через [разделяемый lock-free кэш](https://libmdbx.dqdkfa.ru/docs/en/reference/api/group__c__crud.html) —
до 10–100 000 раз быстрее и BoltDB, и LMDB.

## Как выбирать

- Нужны SQL, реляционная модель, сложные запросы — **SQLite**.
- Терабайты под интенсивную запись на медленных носителях, допустимы фоновые
  компакции и заметный ресурсный след — **RocksDB**.
- Максимальная скорость чтения, минимум оверхеда, доступ из нескольких
  процессов, отсутствие фоновых потоков — **libmdbx** (или LMDB, если её
  ограничения — фиксированный размер, ключи ≈511 B, отсутствие компактации —
  не критичны).
- Уже есть код под LMDB — _libmdbx_ почти наверняка подойдёт без изменения
  логики, сняв часть ограничений.
