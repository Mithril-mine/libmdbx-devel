# Testing Codex (Infra v3) — правила жизни тестов и CI

> Операционный кодекс роя. Черновик: Этап 1 Infra v3 (2026-09-28).
> Полные версии C0–C6 — по итогам Этапа 2 (после переноса всего корпуса из
> poc1-failed и первых метрик). План: `.skynet/plans/testing-infra-v3-plan.md`.
> Источники правил: решения владельца 28.09, факты `fact:testing:*`,
> memory-codex (`double-loop`, Кайдзен).

## C0 — Двойная петля и Кайдзен (сквозной принцип)

Каждое отклонение обрабатывается на двух уровнях:

1. **Single-loop** — исправить/перезапустить в рамках существующих правил.
2. **Double-loop** — пересмотреть сами правила: какое правило корпуса/тайеров/
   флаков допустило отклонение? Обновить этот кодекс; записать наблюдение в
   память роя (`proc:meta:*`).

Периодическая кайдзен-ревизия (раз в спринт): снять метрики, сравнить с
бюджетами (C4), скорректировать пороги/профили, зафиксировать вывод.

## C1 — Адресность

- **«Не запускай то, что не изменилось»**: дифф → (метки ∪ ячейки).
- Локально: `tests/ci/select-cells.py` (дифф→ячейки) + `ctest -L 'ut\.' -LE
  'ut\.heavy'` (метки). CI-гейты: push на любой ветке →
  `select-cells.py --profile push-quick` (7 клетей); pull_request →
  change-addressed (union push-quick+win-gate, ~16 клетей) при изменении
  общего кода (см. `common_prefixes` в `tests/ci/config.json`).
- Каждый новый тест обязан указать свою область: через подкаталог
  `tests/ut/<area>/` или метку `ut.<area>`.
- Пути→ячейки: рукописные `path_zones` удалены во избежание многократного
  несогласования с `cells`. Вместо них действует фиксированный
  `change-addressed` гейт: любое изменение общего кода (src/, CMakeLists,
  mdbx.h, .github/, ...) гоняет полный ось-набор (все Windows-тулчейны,
  арки, CRT/shared, Debug/Release, Linux/macOS), docs-only — компактный
  push-quick. Актуальность набора гарантируется
  `tests/ci/validate-config.py` (job `validate-config` в ci-dispatch +
  локально `make test-ci-config`).

## C2 — Тайеринг и бюджет

| Тайер | Селектор | Бюджет | Когда |
|---|---|---|---|
| P0 target | `ctest -R '^<test>$'` | секунды | правка конкретного теста |
| P1 fast ut | `ctest -L 'ut\.' -LE 'ut\.heavy'` | ≤ ~2 мин локально | рутинная правка |
| T1 smoke | `ctest -L 'smoke-t1'` | секунды, детерминирован | каждый прогон CI (fast) |
| T2 smoke | `ctest -L 'smoke-t2'` | минуты | nightly |
| T3/long | `ctest -L 'smoke-t3'` | минуты-часы, opt-in | milestone/nightly |
| heavy | `ctest -L 'ut\.heavy'` | opt-in | stress/nightly |

- Тест превышает бюджет быстрого тайера → ускорить (RELIEF_FACTOR,
  `--nops`, таймауты) или явно перевести в `ut.heavy`.
- Тяжёлые/флак-тесты — вне быстрого тайера (метки `ut.heavy`, `chk`).

### C2.1 — Мягкий лимит выполнения (runtime limiter, `tests/ut/test-env.h`)

Общий TU `tests/ut/test-env.{h,c++}` собирается **один раз** в объектную
библиотеку `mdbx_test_env` и её объект линкуется в **каждый** gtest-таргет
(`add_gtest()` в `cmake/testing.cmake`); он содержит единственный на бинарь
экземпляр `ci_runtime_limiter` (deadline вычисляется при статической
инициализации из переменных окружения, см. ниже) и единственный подавитель
CRT-попапов Windows (только на CI: env `CI` или `MDBX_TEST_NO_CRT_POPUP`;
локально попапы сохраняются для интерактивной отладки).

Переменные окружения лимитера (обе опциональны, читаются при старте бинаря):

- **`GTEST_RUNTIME_LIMIT`** — относительный бюджет в секундах от момента старта
  бинаря (как было всегда).
- **`GTEST_RUNTIME_DEADLINE`** — абсолютный дедлайн в **UTC-секундах** (unix
  epoch). Предназначен для ограничения суммарного времени набора тестов,
  запускаемых параллельно и/или в случайном порядке: координатор вычисляет
  момент окончания прогона и передаёт его всем процессам, так что они
  останавливаются в один общий момент, а не каждый по своему относительному
  бюджету. Значение в прошлом означает немедленный таймаут.
- Если заданы обе — действует **более ранний** дедлайн. Отсчёт ведётся от
  `std::chrono::steady_clock` (абсолютный дедлайн конвертируется в смещение
  один раз при старте), поэтому перевод системного времени не влияет на
  лимитер.

CI-обвязка: `tests/ci/run-cell.py` экспортирует
`GTEST_RUNTIME_LIMIT = CI_CTEST_TIMEOUT − 60` (по умолчанию 540 при 600) и
пробрасывает `GTEST_RUNTIME_DEADLINE`, если он задан снаружи;
`GTEST_SHUFFLE=1` ставится только для nightly (`CI_NIGHTLY=1` в
`ci-dispatch.yml`), рутинные ячейки идут в детерминированном порядке.

Правила принятия лимитера в тест:

1. Проверка `MDBX_GTEST_IS_EXECUTION_TIMEOUT()` — **в самом начале тела
   каждого** `TEST()` и `TEST_P()` **без исключений** (кроме однострочных
   заглушек, тело которых само является безусловным `GTEST_SKIP()`, и
   `ut/api/test-env-selftest.c++`, который тестирует сам лимитер); **нельзя** в
   fixture `SetUp()`/`TearDown()` или в хелпере, вызываемом один раз на бинарь
   (иначе deadline вычисляется один раз вместо per-test).
2. Паттерн (образец: `tests/ut/issues/issue_gh0083.c++`):
   ```c++
   #include "../test-env.h"   // единая форма; каталог tests/ut добавлен в include-путь add_gtest()
   TEST(suite, name) {
     if (MDBX_GTEST_IS_EXECUTION_TIMEOUT()) {
       GTEST_SKIP() << "SKIPPED by RUNTIME_LIMIT";
       return;
     }
     ...
   }
   ```
   Новый gtest-тест **обязан** следовать этому паттерну; при ревью проверяется
   наличие guard'а в каждом `TEST()`/`TEST_P()`.
3. При исчерпании лимита бинарь печатает `[  SKIPPED ] RUNTIME_LIMIT was
   reached` один раз; последующие проверки скипаются, rc=0 — жёсткий
   ctest-timeout (убийство процесса) не наступает.
4. Поведение покрыто self-test'ом `ut/api/test-env-selftest.c++`
   (детерминированные переходы через конструктор `runtime_limiter(for_testing,
   offset)` и математику дедлайнов `runtime_limiter::compute_edge(limit,
   utc_deadline)` — без sleep и без манипуляций окружением). При изменении
   `runtime_limiter` обновляйте self-test.
5. При достижении лимита каждый раз скипается один и тот же «хвост» набора
   (детерминированный порядок в рутинных ячейках) — это ожидаемо.
6. Plain-C тесты (`add_simple_test`: `details_pnl`, `details_rkl`, `probes`)
   `test-env.c++` **не** получают — они не gtest-овые, лимитер им не нужен.

## C3 — Флак-менеджмент

- **Авто-карантин**: тест падает N раз без изменения кода → known-flaky:
  пометить в реестре (`known_flaky` в config.json), исключить из push-gate,
  включить в отчёт.
- **Retry-политика**: флак-падения перезапускаются (локально `--repeat
  until-pass:3`); CI — перезапуск job.
- **Атрибуция**: в отчёте разделять «новые падения» (блокируют merge) и
  «известные флаки» (не блокируют, но отслеживаются).

## C4 — Метрики и SLA

- Каждый прогон `run-cell.sh` пишет `cell-metrics.json`: cell, scope, rc,
  wall_ms, per-test timing (JSON в `Testing/Temporary/`).
- Ключевые SLA (черновик, будут уточнены на Этапе 2):
  - push-CI (fast, ≤10 ячеек): стена ≤ ~20–25 мин.
  - P1 fast ut локально: ≤ ~2 мин.
- Тренды: накапливать cell-metrics артефактами CI; раз в спринт — кайдзен-
  ревизия бюджетов.

## C5 — Паритет локально/CI

- `tests/ci/run-cell.sh <cell> [--scope fast|full]` == логика `ci-run.yml`
  (единый источник: `tests/ci/config.json` + run-cell.sh).
- Любой красный CI-прогон воспроизводится локально одной командой
  `run-cell.sh <cell> --scope ...`.
- Не добавлять CI-логику, которую нельзя выполнить локально.
- **Исключение — Windows-ячейки**: паритет «локально == CI» для них обеспечивается
  только настоящими Windows-ячейками CI (`ci-job (windows-latest)`, mingw/msvc).
  **Wine непригоден**: его ядро принципиально отличается от Windows (часть
  функций — заглушки, завершающие процесс вместо возврата ошибки; расширение
  секции `NtExtendSection` не поддерживается), поэтому успех/отказ теста под
  Wine не говорит о поведении в Windows ни в одну сторону. Кросс-сборка mingw-w64
  валидна только для проверки **компилируемости** `#if IS_WINDOWS`-веток, не
  поведения. Подробности: [`debugging-methodology.md` §2.13](debugging-methodology.md).

## C6 — Гигиена корпуса (черновик, Этап 2)

- Докончить gtest-миграцию всех `tests/ut/`; перевести `.c`-уты в `.c++`.
- Убрать дубль make/ctest в легаси `ci.sh` (полный прогон одного и того же
  дважды на linux/macos).
- Чистить долгие/дублирующие сценарии; `smoke_sp_*`/`chk` вне рутины.
- Каждый тест: одна область, одна метка-дом, явный бюджет времени.

### C6.1 — Удаление временного при завершении (TEMP-CLEANUP)

- По завершении задачи или этапа **обязательно** удалять все временные
  артефакты, созданные в этой сессии: локальные build-каталоги (`@ci-*`,
  `@sc-*`, `@cmake-*`, `@check-*`), скачанные логи/артефакты CI (`/tmp/*`),
  распакованные деревья. Диск на dev-машине общий для всех nooks — полный
  диск вызывает Bus error/false-failures у чужих прогонов (SIGBUS при
  mmap-write, как в `bug:testing:issues-parallel-buserror-diskfull`).
- Правило: «приступил → артефакты; завершил/сдал этап → удалил». Перед
  коммитом финального результата проверять `df -h` и оставлять ≥20%
  свободного места.
- Только долгоживущие кэши не трогаются: `.skynet/ccache`, `.skynet/tmp/*`
  (рабочие каталоги других агентов).
