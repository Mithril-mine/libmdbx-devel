# Module Interfaces & Dependency Map

> Part of the [Skynet project index](README.md).
> Cross-module interface map: who exports what (from `src/proto.h` and module headers) and who
> depends on what (include backbone + verified call sites). Granularity: module-level. A full
> function-level call graph is best generated by tooling (`ctags -x --c-kinds=f` + grep, or
> `cscope`); this document is the stable, curated index.

---

## 1. Include backbone (факты из кода)

```
preface.h ──► essentials.h ──► { options.h, osal.h, atomics-types.h, layout-dxb.h, layout-lck.h }
essentials.h ──► internals.h ──► { atomics-ops.h, rkl.h, txl.h, unaligned.h, proto.h,
                                   windows-import.h (Windows) }
internals.h ◄── каждый модуль src/*.c
```

- `proto.h` включается **из** `internals.h` (подтверждено правилом squash в GNUmakefile,
  см. build.md §7.5): все объявления прототипов доступны всем модулям.
- `mdbx.h++` (C++-слой) включается только из `src/mdbx.c++` и тестов; ядро C не зависит от C++.
- Amalgamation: `xMDBX_ALLOY` превращает `MDBX_INTERNAL` в `static` — межмодульные вызовы
  существуют только на этапе линковки dev-сборки и через единую TU в alloy.

## 4. Циклы зависимостей (осторожно при рефакторинге)

- **txn ↔ gc ↔ mvcc**: commit вызывает gc; gc_get проверяет читателей (mvcc); rkl — внутри gc.
- **cursor ↔ page ↔ node ↔ tree**: курсор держит стек страниц; мутации идут через page_touch;
  split/rebalance через tree-ops.
- **env ↔ meta ↔ dxb**: meta-переключение вызывается из env/txn/dxb-синка.
- Это функциональные циклы, разрывать их нельзя без изменения архитектуры; выносить общие
  утилиты можно в `utils.c`/`pnl.h`/`rkl.h` без циклов.

## 5. Правила рефакторинга интерфейсов

1. Новый межмодульный экспорт → объявление в `proto.h` (или в модульном заголовке при
   header-inline API); иначе при alloy-сборке символ станет `static` и «потеряется».
2. Перенос функции между модулями = правка объявления в `proto.h` + включение заголовка
   потребителем; проверять оба режима сборки (alloy и per-module: `MDBX_ALLOY_BUILD=OFF`).
3. Не добавлять зависимостей от `mdbx.h++`/`mdbx++` в C-ядро.
4. Для полной карты вызовов: `ctags -x --c-kinds=f src/*.c | ...` или cscope; генерировать
   по мере необходимости, не хранить в репозитории.
5. После перемещения кода сверять `techdebt.md` (упразднённые ветки pnl/gc/defrag) — часто
   рефакторинг интерфейса и чистка мёртвых веток идут вместе.
