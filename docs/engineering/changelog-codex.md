# changelog-codex — инструкция по дополнению ChangeLog (libmdbx)

> Адаптация черновика владельца (2026-09-22), приведена к формату
> [Keep a Changelog 2.0.0](https://keepachangelog.com/en/2.0.0/) (2026-11-10).
> Применяется к `ChangeLog.md` (текущая линия разработки) и к файлам
> `ChangeLog-0.XX.md` (история релизных линий; в `master` —
> `docs/changelog-history/`, в релизных ветках — в корне). Ревью инструкции: типы и
> таксономия подсечек `Fixed` сверены с фактическим форматом файлов.

## Назначение

Рой (Skynet) дополняет существующий `ChangeLog.md` проекта libmdbx, работая в
стиле, уже заданном в файле. Цель — не протоколировать каждый коммит, а
фиксировать **интегрально значимые ценности и ключевые моменты** развития
проекта, включая потенциальные риски и устранённые дефекты с описанием их
проявлений.

## Принцип отбора: что документировать, а что нет

**Главное правило: changelog — это не git log.**

Документируем:
- Изменения, влияющие на поведение, производительность, надёжность или
  совместимость, которые заметит пользователь или разработчик, использующий libmdbx.
- Устранённые дефекты, которые могли проявляться в реальных сценариях — с
  описанием симптомов и условий.
- Новые возможности и усовершенствования, дающие измеримую ценность.
- Изменения, требующие действий при миграции (новые дефолты, удалённые API, изменение ABI).
- Риски и ограничения, о которых нужно знать при обновлении.

Не документируем:
- Косметические правки (опечатки, форматирование) — за исключением случаев,
  когда опечатка в публичном API или документации вводила в заблуждение.
- Внутренние рефакторинги без эффекта для пользователя.
- Обновления CI/CD, скриптов сборки, вспомогательных утилит — если они не
  меняют процесс сборки или требования к окружению для конечного пользователя.
- Промежуточные коммиты внутри одного логического изменения (WIP, fixup,
  squashed). Документируем итоговый результат, а не ход работы.
- Дублирующие записи: несколько коммитов по одной теме — объединяем в одну запись.

**Критерий:** перед добавлением записи задать вопрос: *«Изменится ли что-то для
того, кто обновит libmdbx до этой версии?»* Если «нет» — запись не нужна.

## Структура и формат

Формат следует [Keep a Changelog 2.0.0](https://keepachangelog.com/en/2.0.0/)
с домашними отклонениями (полный список — в `AGENTS.md` §6). Английский язык
(русскоязычная фраза «Всё будет хорошо!» в шапке сохраняется как элемент
брендинга).

Заголовок версии:
```markdown
## v0.X.Y at a deep development stage
```
или
```markdown
## v0.X.Y at YYYY-MM-DD
```

Версия открывается сводкой из одного-двух простых предложений: что релиз даёт
пользователю. Далее — типы Keep a Changelog, в порядке следования:

- `### Added:` — новые публичные API, утилиты, флаги, режимы, возможности.
- `### Changed:` — изменения существующего поведения, не являющиеся багами
  (новые дефолты, более строгие проверки, порядок операций, ускорения).
- `### Deprecated:` — будущие удаления (анонсируются до самого удаления).
- `### Removed:` — удалённое (в т.ч. исполненные прошлая `Deprecated`).
- `### Fixed:` — исправленные дефекты с описанием проявлений (см. ниже).
- `### Security:` — устранённые уязвимости.
- `### Appreciations:` — домашняя секция благодарностей.

Пустой тип опускается. Других секций верхнего уровня нет; исторические
заголовки в старых файлах (`### Important:`, `### Improvements:` и т.п.)
сохраняются как история — новые записи в них не добавляются.

Каждая запись начинается с глагола своего типа: `Added …`, `Changed …`,
`Deprecated …`, `Removed …`, `Fixed …`; запись `Security` при наличии CVE
начинает с его идентификатора. Ломающие изменения помечаются `**Breaking:**`
на самой записи, внутри её типа — отдельная секция для них не заводится.

Каждый пункт — одна строка, начинается с ` - `. Продолжение — с отступом.
Разделитель между версиями — длинная линия `----...` (как в файле).

## Подсекции Fixed (домашнее отклонение)

Внутри `### Fixed:` допускаются тематические подсекции — пользователи
жаловались на отсутствие группировки исправлений. Состав установленный и
стабильный; новая подсекция — только по согласованию с владельцем:

- `Data safety and durability` — потери и порча данных, надёжность;
- `Resistance to corrupted or crafted data` — устойчивость к испорченным
  и поддельным данным;
- `Crashes, hangs and undefined behavior` — падения, зависания, UB;
- `Wrong results and API behavior` — неверные результаты и контракты API;
- `Platform-specific` — особенности платформ (Windows, Linux, BSD…) и сборки;
- `Tools` — утилиты (`mdbx_chk`/`dump`/`load`/`stat`/`defrag`/`copy`);
- `C++ API` — C++ обёртки;
- `Performance` — исправленные замедления;
- `Resource leaks` — утечки;
- `Minor` — прочее мелкое.

## Описание исправленных дефектов (Fixed)

Каждая запись отвечает на два вопроса: **как проявлялось** и **когда/при каких условиях**.

Шаблон:
```
 - Fixed <что> when <условия/сценарий> — <симптомы/последствия>.
```

Примеры (стиль libmdbx):
```markdown
### Fixes:

 - Fixed a deadlock when `mdbx_cursor_put` and `mdbx_txn_reset` are called concurrently in the same thread — the transaction could hang indefinitely under high contention.
 - Fixed `MDBX_TXN_TRY` leakage into transaction state flags — could cause `mdbx_txn_flags()` to return unexpected values after a read-only transaction with `MDBX_TXN_TRY`.
 - Fixed page cache corruption after abrupt termination during a long-running write transaction with many dirty pages — could result in `MDBX_CORRUPTED` on subsequent open.
```

Если дефект мог затронуть пользователей в production — явно указать условия
воспроизведения и последствия, но без раскрытия деталей эксплойта (для Security)
или внутренних алгоритмов.

## Сводка версии и ломающие изменения

Версия открывается сводкой из одного-двух предложений простым языком: что
релиз даёт пользователю. Риски при обновлении и ломающие изменения
описываются на самой записи маркером `**Breaking:**` внутри её типа, с
конкретикой и действиями при миграции:

```markdown
### Changed:

 - **Breaking:** Changed the default durability mode from durable to safe-nosync; existing databases keep the previous mode. If durable sync is required, set the mode explicitly.

### Removed:

 - **Breaking:** Removed `mdbx_env_set_flags_v1()` (deprecated since v0.12.0); replace all calls with `mdbx_env_set_flags()`.
```

## Описание Added и Changed

`Added` — фокус на новой ценности для пользователя; `Changed` — на
измеримом эффекте (цифры, сценарии), не «стало лучше»:

```markdown
### Added:

 - Added the `MDBX_opt_shrink_retry_period` option to rate-limit futile datafile-shrink attempts.

### Changed:

 - Reduced `fsync()` syscalls by ~40% for frequent small transactions by batching dirty page flushes.
```

## Какие файлы и секции обновлять (адаптация под наш процесс)

- **Текущая разработка (devel/master):** дополняем существующую секцию
  `## vX.Y.Z at a deep development stage` в `ChangeLog.md` — НЕ создавать новую
  секцию без смены версии; сортировать по значимости внутри категории.
- **Релизные линии (backport):** исправления, перенесённые в `stable`
  (v0.14.x) — в `ChangeLog-0.14.md`; в `lts/0.13` — в `ChangeLog-0.13.md`
  (аналогично для будущих линий). Формат и правила те же.
- **Источник для сканирования:** закрытые PR + коммиты в `devel`/`master`
  (только публичный репозиторий). Для релизных линий — коммиты бэкпорта.

## Роль роя и человека

1. **Рой (Skynet):**
   - Сканирует закрытые PR и коммиты (devel/master, публичный репозиторий).
   - Фильтрует несущественное по критерию выше.
   - Группирует родственные коммиты в одну запись.
   - Распределяет по типам Keep a Changelog (метки PR + анализ diff).
   - Формирует/дополняет черновик секции `[deep development stage]`.
   - НЕ публикует: внутренние обсуждения, фрагменты кода, логи, ключи, токены,
     ссылки на внутренние ресурсы, персональные данные, проприетарные детали роя.
2. **Ревьюеры:** техническая точность формулировок и категорий (REV:docs,
   при API-затрагивающих записях — REV:cpp).
3. **Координатор:** сводит, контролирует чек-лист, эскалирует человеку.
4. **Человек:** финальное решение о включении/исключении записей, критичность,
   миграционные инструкции; при релизе — дата, перенос записей между версиями.

## Чек-лист для агента перед предложением правок

- [ ] Каждая запись отвечает на вопрос «что изменится для пользователя/разработчика?»
- [ ] Нет дублирования — коммиты по одной теме объединены.
- [ ] Запись начинается с глагола своего типа (`Added`, `Changed`, …, `Fixed`).
- [ ] В `Fixed` описано, как и когда проявлялся дефект; подсекция соответствует таксономии.
- [ ] Ломающие изменения помечены `**Breaking:**` внутри своего типа, с действиями при миграции.
- [ ] В `Changed` есть измеримый эффект (цифры, сценарии), не «стало лучше».
- [ ] Нет чувствительных данных (ключи, логи, внутренние ресурсы, ПДн, алгоритмы роя).
- [ ] Стиль соответствует существующему файлу (типы записей, подсекции Fixed, язык, терминология).
- [ ] Записи отсортированы по значимости внутри типа/подсекции — критичное первым.
- [ ] Обновлён правильный файл/секция (dev-секция vs релизная линия).
