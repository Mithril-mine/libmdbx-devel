# Проектирование целочисленных индексов MCP-memory (INTEGERKEY / INTEGERDUP)

> Статус: согласованный дизайн (владелец + Алиса + документация libmdbx).
> Дата: 2026-09-25.
> Пересмотр решения «inverted = non-dupsort, packed-список строк» от 2026-09-25.

## 1. Контекст

Переписываем модуль персистентной памяти роя (MCP-memory) на Python + cffi + libmdbx.
Старый сервер (`memory-mdbx-server.py`, 4 subdb `E/O/R/RV`) падал в семантический тупик LLM
на ошибках лимита dupsort-значений (~2022 B @4K, корень B48). Новый дизайн обязан сделать
класс таких ошибок невозможным в обычном сценарии.

Предыдущее решение по `inverted` (non-dupsort, term → packed-список ключей) отвергнуто:
оно перекладывает лимит на RMW целой строки и overflow-страницы. Вместо него —
классические постинг-списки на `MDBX_INTEGERDUP`.

## 2. MDBX_INTEGERKEY — семантика и преимущества

По `mdbx.h` (`MDBX_db_flags`): ключи — бинарные целые **uint32_t или uint64_t**,
native byte order, все одного размера, выравненные при передаче. Другие типы
(signed, uint16, float) — не поддерживаются. Сортировка числовая.

| Преимущество | Механизм |
|---|---|
| Скорость сравнения | Числовое сравнение O(1) вместо побайтового цикла по строке; branchless-компараторы (`cmp_uint32/64`, aligned/unaligned/align2, comparators.c) |
| Компактность | 4–8 байт на ключ против ~40–60 байт у `bug:crypto:alignment-arm64`; плотнее страницы, меньше кэш-промахов, меньше глубина B-tree |
| Монотонные вставки | Автоинкрементные ID идеально ложатся на APPEND-путь вставки «в конец» (без поиска позиции, плотное заполнение) |
| Range-поиск | Нативные `MDBX_SET_RANGE` / `SET_LOWERBOUND` / `SET_UPPERBOUND` по числовому диапазону |
| Связка с мультизначениями | Даёт пару «числовой ключ → сортированное множество целых» вместе с `MDBX_INTEGERDUP` |

**Ограничения:**
- строго uint32/uint64, единый размер всех ключей, выравнивание при передаче
  (в cffi — выровненный буфер через `uint64_t*`, не сырые `bytes`);
- неприменим к float-ключам (score для gc) и к произвольным строкам (канонические
  ключи, термы);
- native byte order ⇒ перенос БД на архитектуру с другим endianness потребует
  миграции. Неактуально: рой на одном хосте, перенос не нужен (решение владельца).

## 3. Инвертированные списки на MDBX_INTEGERDUP

**Устройство.** Таблица `inverted` с флагами
`MDBX_DUPSORT | MDBX_DUPFIXED | MDBX_INTEGERDUP`:

```
term (строка, нормализованная)  →  сортированное множество record_id (uint64)
```

Каждый id — отдельный элемент набора (постинг-список). Сортировка числовая по
возрастанию — готовая структура для пересечений.

**Операции** (все внутри одной write-txn safe_store):
- Индексация: `mdbx_cursor_put(cur, term, &id, MDBX_NODUPDATA)` — добавить id;
  повторная вставка того же id отвергается (MDBX_KEYEXIST) — дедуп бесплатно.
- lookup(term): `MDBX_SET` → `MDBX_FIRST_DUP` → `MDBX_NEXT_DUP`, либо пакетно
  `MDBX_GET_MULTIPLE`/`NEXT_MULTIPLE` — до страницы id за один вызов.
- Пересечение термов: списки отсортированы ⇒ merge-intersect за O(|L1|+|L2|),
  без хэш-таблиц и без RMW.
- Удаление id: `mdbx_del(txn, dbi, term, &id)` — точечное удаление одного значения.
- Подсчёт документов по терму: `mdbx_cursor_count()`.
- Проверка наличия: `MDBX_GET_BOTH` / `MDBX_TO_EXACT_KEY_VALUE_EQUAL`.

**Преимущества над packed-списком строк (прошлое решение):**

| Критерий | packed-строка в non-dupsort | INTEGERDUP-набор id |
|---|---|---|
| Лимит ~2022 B (корень B48) | список растёт → RMW всей строки → overflow-страницы | не существует: каждый id — элемент набора (sub-page → LEAF2/вложенное B-tree), набор растёт без верхнего предела |
| Обновление списка | read-modify-write целиком | точечная вставка/удаление одного элемента (CoW одной страницы/ветки) |
| Уникальность id | проверка в приложении | `MDBX_NODUPDATA` на уровне движка |
| Пакетное чтение | нет | `GET_MULTIPLE`/`NEXT_MULTIPLE`/`SEEK_AND_GET_MULTIPLE` (до страницы id за вызов) |
| Плотность хранения | заголовки длины на ключ | LEAF2-страницы фиксированного размера, без служебных полей |
| Пересечение | сортировка в приложении | готовый сортированный список |

## 4. Применение к схеме MCP-memory

Вводим суррогатные числовые id (нужны для INTEGERDUP-значений):

| DBI | Флаги | Ключ → Значение | Назначение |
|---|---|---|---|
| `records` | DEFAULTS | канонический ключ → JSON body | prefix-recall `bug:crypto:*` (строковые ключи обязательны) |
| `vocab` | DEFAULTS | `module:topic` → meta | словарь |
| `history` | DEFAULTS | `_history:{key}:{ts}` → body | версии |
| `ids` | DEFAULTS | record_key → uint64 id | record_key → id (для индексации) |
| `id2key` | INTEGERKEY | uint64 id → record_key | id → record_key (для поиска/графа) |
| `inverted` | DUPSORT\|DUPFIXED\|INTEGERDUP | term → set of uint64 id | постинг-списки |
| `links` | DUPSORT\|DUPFIXED\|INTEGERDUP | subject_id+predicate → set of object_id | граф на id (компактно) |
| `simhash` | INTEGERKEY | uint64 id → uint64 hash | скан для Hamming ≤ 3 (корпус мал) |
| `access` | INTEGERKEY | uint64 id → packed(score,last_access,count) | LRU/тиринг; gc = скан + сортировка в памяти |
| `meta` | DEFAULTS | строка → uint64 | next_id sequence (атомарный ++ в write-txn; в libmdbx нет встроенных sequences) |

Решения по умолчанию:
- **id = uint64** (выравнивание = машинное слово, масштаб неограничен).
- **links на id**: `subject_id\0predicate` → object_id. Trade-off: компактность/
  скорость против читаемости дампа (graph() гоняет через id2key).
- `mdbx_env_set_maxdbs` ≥ 11 (10 named + main).

## 5. Вывод

`MDBX_INTEGERKEY` — быстрые/компактные числовые ключи для суррогатных id и всех
индексов; `MDBX_INTEGERDUP` даёт классический постинг-список, который полностью
снимает класс ошибок лимита B48, делает обновление индекса точечным и открывает
пакетное чтение. Решение заменяет более ранний вариант «packed-список в non-dupsort».
