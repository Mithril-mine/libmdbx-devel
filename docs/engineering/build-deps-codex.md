# Кодекс зависимостей сборки и тестов (build-deps codex)

> Стандарт гигиены графа зависимостей для всех задач роя (протокол §29, TASK-21).
> Правило: **всё, что читается или пишется при сборке и тестах, обязано быть
> декларировано в графе зависимостей CMake/Ninja** — исходники, заголовки,
> генерируемые файлы, depfiles, скрипты, скачиваемые зависимости. Недекларированный
> файл = «выпал из-под контроля»: изменение такого файла не пересобирает
> зависимые цели, ломая инкрементальные сборки и прогоны.

## 1. Область действия

Кодекс применяется к любому изменению, которое добавляет/переносит/удаляет
файлы, участвующие в:

- **конфигурации** (`cmake` configure: `CMakeLists.txt`, `cmake/*.cmake`,
  `*.in`-шаблоны);
- **компиляции и линковке** (исходники, заголовки, генерируемые `config-cmake.h`
  / `version.c`, asm/nasm-объекты, импорт-библиотеки);
- **прогоне тестов** (исполняемые тесты, googletest, скрипты
  `tests/ci/ci.sh`, `tests/stochastic.sh`, `tests/battery-tmux.sh`,
  `tests/probes-check.sh`, фикстуры, DLL/PDB-копирование);
- **амальгамации** (`make dist`, `dist-cutoff` маркеры) — только если меняется
  набор дистрибутивных файлов (`DIST_SRC`/`DIST_EXTRA`).

НЕ попадает под кодекс: служебные файлы владельца, логи, артефакты CI вне графа
сборки, системный тулчейн (`/usr/include`, `/usr/lib` и т.п.).

## 2. Контракт: что обязано быть в графе

### 2.1 Входы сборки (инпут-файлы)

| Категория | Декларация | Где именно |
|---|---|---|
| Библиотека: C-модули и заголовки | список `LIBMDBX_SOURCES` | `CMakeLists.txt` (dev-layout ветка, строки ~946–1060) |
| Публичные заголовки | `mdbx.h` в `LIBMDBX_SOURCES`; `mdbx.h++` + `mdbx++/*.h++` | `CMakeLists.txt` (C++ API блок) |
| Генерируемый `config-cmake.h` | `configure_file(src/config.h.in → build/config-cmake.h)`; файл входит в `LIBMDBX_SOURCES` | `CMakeLists.txt:947,1586–1588`; `src/config.h.in` |
| Генерируемый `version.c` | `configure_file(src/version.c.in → build/version.c)`; входит в `LIBMDBX_SOURCES` | `CMakeLists.txt:952–954`; `src/version.c.in` |
| Тест-исходники | `add_gtest`/`add_ut`/`add_simple_test(SOURCE ut/<name>.<ext>)` | `tests/CMakeLists.txt`, `cmake/testing.cmake:347–501` |
| Скрипты тестов | явная команда теста (путь в `add_test`) | `tests/CMakeLists.txt` (`stochastic.sh`, `probes-check.sh`) |
| googletest | `find_package(GTest)`/`gtest_paths`/ExternalProject-fetch | `cmake/testing.cmake:43–136`, `cmake/googletest-download.cmake.in` |
| Windows-специфика | `windows-safeseh-*.asm/.obj`, `ntdll_extra`, `wingetopt` | `CMakeLists.txt:644,1130–1141`, `src/tools/wingetopt.*` |

### 2.2 Автозависимости компилятора (depfiles)

Для C/C++ инкрементальную корректность по **заголовкам** обеспечивает компилятор:
ninja получает depfile (`-MD -MF`) и обновляет `.ninja_deps` автоматически. Поэтому
главная зона контроля — не заголовки, а **всё остальное**, что открывается при
сборке, но не попадает в `-MD`:

- файлы, читаемые CMake-скриптами при configure (`.cmake`, шаблоны `.in`);
- файлы, читаемые тестовыми процессами в рантайме (скрипты, данные, DLL);
- файлы, читаемые генераторами/утилитами внутри custom-команд;
- `MDBX_SOURCE_DIR`-структура — менять состав `src/` можно только вместе с
  декларацией (см. §3).

### 2.3 Выходы (артефакты)

Каждый выход должен иметь производителя с объявленными входами: цель
(`add_library`/`add_executable`/`add_custom_target`) либо правило
`add_custom_command(OUTPUT ... DEPENDS ...)`. Исключение — побочные выходы тестов
(файлы БД в рабочем каталоге: `smoke.db`, `fault.db`, `singleprocess.db`):
они не переиспользуются сборкой и учитываются аудитом как «ожидаемые побочные».

## 3. Правила для агентов

1. **Новый исходник библиотеки** (`src/*.c|.h`) → добавить в `LIBMDBX_SOURCES`
   (dev-layout ветку CMakeLists.txt) и в `ALLOY_DEPS`-список автоматически
   (`git ls-files src/` — файл должен быть закоммичен до сборки через make).
2. **Новый тест** → регистрировать через `add_gtest`/`add_ut`/`add_simple_test`
   в `tests/CMakeLists.txt` (или `tests/issues/CMakeLists.txt`); файл теста —
   явно в `SOURCE`, путь от `tests/`.
3. **Новый скрипт/фикстура для теста** → путь указать в команде `add_test`
   (абсолютным через `${CMAKE_CURRENT_SOURCE_DIR}` или `${CMAKE_CURRENT_LIST_DIR}`).
4. **Скачиваемая зависимость** (googletest и т.п.) → только через ExternalProject/
   FetchContent в `cmake/`, с URL/тегом в опциях (`GTEST_CLONE_URL`,
   `GTEST_CLONE_TAG`); кэшировать в `${CMAKE_BINARY_DIR}`.
5. **Новый модуль CMake** → добавить `include(...)` в точку, где используется,
   и зафиксировать в `dist-extra-rule`/`DIST_EXTRA`, если нужен в дистрибутиве.
6. **dev-only дополнения CMake/GNUmakefile** → внутри `dist-cutoff` маркеров
   (`#> dist-cutoff-begin`…`#< dist-cutoff-end`), иначе утекут в амальгаму (§29,
   AGENTS.md).
7. **Удаление файла** → удалить и его декларацию (иначе configure падает на
   `FATAL_ERROR "The set of libmdbx source code files is incomplete!"` или ninja
   на битой ссылке).

## 4. Аудит strace (процедура)

Инструмент: `.skynet/tools/strace-audit.sh` (вне git, общий для роя).

```
strace-audit.sh --build-dir <dir> [--target <T>] [--ctest <regex>] [--force]
```

Логика:

1. Проверка нагрузки хоста (`/proc/loadavg`, load1 ≤ порог, по умолчанию
   1.2×nproc; `--force` для пропуска).
2. `strace -f -e trace=%file` вокруг `cmake --build <dir>` (и, при запросе,
   `ctest -R <regex>`).
3. Сбор всех путей из трассы → классификация:
   - **системный тулчейн** (`/usr/*`, `/lib*`, `/proc`, `/sys`, `/dev`, `/opt`)
     → игнорируется;
   - **граф сборки** (известен через `build.ninja` + `ninja -t deps`) → ok;
   - **выходы сборки** (под каталогом сборки) → ok;
   - **проект, но не в графе** → «вне графа», попадает в отчёт.
4. Отчёт: файлы вне графа, группами по каталогам, с количеством обращений.

Критерий успеха: **0 файлов «вне графа»** (кроме задокументированных побочных
выходов тестов). Появление нового файла вне графа — блокер ревью (§29).

Частота: полный аудит на тяжёлых целях — не чаще раза в несколько дней и только
при низкой нагрузке; лёгкие точечные аудиты (один тест) — по мере изменений
сборки.

## 5. Типовые «выпавшие из-под контроля» места (исторические находки)

- Копии генерируемых файлов, случайно попавшие в `src/` (например
  `src/config-cmake.h`, `src/version.c`) — CMake их принудительно удаляет
  (`file(REMOVE ...)`), но при ручной правке они переживают пересборку.
- Файлы, открываемые тестом из `tests/` не через декларированный путь
  (жёстко зашитые относительные пути).
- `googletest-src` в каталоге сборки при отключённом network-фетче: если gtest
  был найден в системе (`/usr/src/googletest`) — источник вне дерева, и это
  ок; если фетчится — путь обязан быть `${CMAKE_BINARY_DIR}/googletest-src`.
- Скрипты `tests/*.sh`, вызываемые из GNUmakefile/CI без регистрации в CTest.

## 6. Сверка с остальными кодексами

- `AGENT-WORKSPACE.md` — раздача задач по нагрузке (не запускать тяжёлые аудиты
  при высокой load1).
- `skynet/test-scenarios-codex.md` — сценарии задают `speed_class`/`sync_mode`;
  кодекс сборки требует, чтобы новые юнит-тесты были зарегистрированы в CTest
  с label-деревом (`ut.*`), иначе они не прогоняются сегментированно.
