# SystemTap: справочник по пробированию (user-space и kernel-space)

> Консолидированная справка, чтобы не переискивать заново (2026-09-29).
> Источники: SystemTap Beginners Guide (5.5, sourceware.org), семантика `stapprobes`,
> консультация Алисы (route=design). Применение к libmdbx — см. `skynet/probes.md`.

## 1. Два домена трассировки

SystemTap работает в двух независимых доменах:

| Домен | Точки | Примеры |
| --- | --- | --- |
| **kernel-space** | внутри ядра ОС | `kernel.function("sys_open")`, `vfs.read`, `ioblock.request`, `vm.pagefault`, `syscall.close` |
| **user-space** | внутри пользовательского процесса | `process("PATH").function()`, `.statement()`, `.mark()`, `.syscall`, `.begin/.end` |

**Почему нужен root (важно понимать):** дефолтный рантайм `stap` компилирует скрипт в
**kernel-модуль** и делает `insmod` — даже для user-space пробирования (оно идёт через
uprobes-механизм). Т.е. root нужен **за механизм доставки событий**, а не потому что
«мы трассируем ядро». Обходные пути без root:

1. **stap-server**: root-демон (`stap-serverd`) компилирует/грузит модули по запросу;
   пользователь должен состоять в группе `stapdev`/`stapusr`. На dev-хосте пакеты
   установлены (`systemtap-client`, `stap-server`), но демон не запущен и пользователь
   не в группах — одноразовая настройка администратором.
2. **`stap --runtime=dyninst`**: инструментирует user-space бинарь в памяти без
   kernel-модуля → root не нужен; требует debuginfo у цели; работает через `-c`
   (запуск) или attach; менее надёжен на heavily-inline/оптимизированном коде.

## 2. Архитектура сессии (Beginners Guide, Procedure 3.1)

```
скрипт.stp
  → проверка/расширение против tapset-библиотеки (/usr/share/systemtap/tapset/)
  → трансляция в C + компиляция kernel-модуля (cc)
  → staprun грузит модуль, включает все probe-точки
  → события исполняют хендлеры (быстрые подпрограммы в трассировочном контексте)
  → по завершении сессии модуль выгружается
```

Tapsets (`/usr/share/systemtap/tapset/linux/{vfs,ioblock,memory,...}.stp`) — библиотека
алиасов высокого уровня, чтобы не помнить конкретные функции ядра между версиями.

## 3. User-space probe-точки (полный список)

Все события начинаются с `process`; PID или путь исполняемого файла обязательны там,
где указано.

| Событие | Что ловит |
| --- | --- |
| `process("PATH").function("FN")` | вход в функцию (аналог `kernel.function`); `.return` — выход |
| `process("PATH").statement("SPEC")` | конкретный оператор исходника (см. §4) |
| `process("PATH").mark("MARKER")` | статический USDT-маркер; аргументы `$arg1..$argN` — **только чтение** |
| `process.begin` / `process.end` | создание/смерть процесса (можно ограничить PID/PATH) |
| `process.thread.begin` / `.thread.end` | создание/смерть потока |
| `process.syscall` (+`.return`) | сисколлы процесса: `$syscall`, `$arg1..$arg6`, `$return` |

Wildcards (`*`) разрешены в именах функций/файлов/маркеров, например
`process("/usr/lib/libmdbx.so").mark("alloc__*")`.

## 4. `process("PATH").statement("SPEC")` — разбор

**Определение:** «earliest instruction in the code for *statement*» — синхронный пробинг
на самой первой машинной инструкции, сгенерированной компилятором для данного оператора
исходника. User-space аналог `kernel.statement("SRC:LINE")`. Слово *statement* — оператор
**языка C** (строка/`if`/присваивание), не операторы тела хендлера.

**Формы адресации:**

| Форма | Значение |
| --- | --- |
| `statement("SRC:LINE")` | оператор на строке `LINE` файла `SRC` |
| `statement("FN@SRC:LINE")` | тот же оператор внутри конкретной функции `FN` (снимает неоднозначность при inline-копиях/нескольких функциях на одной строке) |
| `statement("*@SRC:LINE")` / wildcards | все функции файла / несколько файлов |
| `statement("FN@SRC:LINE+N")` | N-я инструкция после начала оператора (обход пролога / конкретное подвыражение) |
| `statement("FN@SRC:LINE-N")` | N-я инструкция до начала |
| `statement(0xADDR)` | абсолютный адрес — единственная форма без debuginfo |

**Отличие от граничных пробников:**

| Пробник | Точка | Что доступно |
| --- | --- | --- |
| `function("FN")` | вход функции | аргументы + локали на входе |
| `function("FN").return` | выход | `$return`, изменённые локали |
| `statement(...)` | середина тела | `$var`, живые **в этой точке** (DWARF location lists) |

**Требования и подводные камни:**

- Нужна **DWARF-отладочная информация** (маппинг строка→адрес); без неё — только абсолютный адрес.
- При `-O2` и выше: операторы расщепляются/перемещаются (код «островами»), пробник может
  сработать не в исходном порядке или несколько раз; локали могут быть выброшены
  (`$var` → «optimized away»).
- Inline-функции: одна строка в нескольких копиях → форма `FN@SRC:LINE` обязательна для точности.

## 5. Целевые переменные и чтение user-space памяти

- `$var` — локаль/параметр по DWARF (доступна там, где «жива»).
- Для разыменования указателей на данные процесса:
  `user_char/user_short/user_int/user_long/user_string/user_string_n(addr[,n])`.

## 6. Наблюдение vs изменение поведения (fault injection)

**Базовое правило:** SystemTap-пробники — это **наблюдение**. Хендлер исполняется в
трассировочном контексте и не может изменить ход трассируемого процесса.

| Способ | Можно ли изменить поведение? |
| --- | --- |
| `mark("...")` | **нет** — аргументы передаются по значению, запись в `$argN` меняет лишь локальную копию в хендлере; движок уже принял решение |
| `statement(...)`, `function("FN")` | **нет** — только чтение контекста |
| `function("FN").return { $return = X }` | **да**, единственный легитимный вектор: перезапись возвращаемого значения перед реальным выходом из функции |

**Ограничения инъекции через `.return`:**

- функция должна быть видимой/неinline (иначе проба не встанет);
- tail-call/оптимизация могут «съесть» return-точку;
- нужен debuginfo и (для дефолтного рантайма) права;
- неприменимо в CI (рантайм/права) и на macOS/DTrace (нет перезаписи возврата).

**Вывод для практики:** для управляемой инъекции ошибок в конкретные ветви надёжнее
встроенные тестовые механизмы (тест-хуки в коде под `#if`, параметризуемые инжекторы во
фреймворке), а не SystemTap. SystemTap — инструмент наблюдения/диагностики.

## 7. Практические примеры

Наблюдение, какая ветвь `if` выполнена (user-space):

```systemtap
probe process("/path/app").statement("commit@src/txn.c:320") {
  if ($dirty_pages > 0)
    printf("fastpath: false, dirty=%d\n", $dirty_pages);
  else
    printf("fastpath: true\n");
}
```

Чтение локали в точке решения:

```systemtap
probe process("/path/app").statement("alloc@src/page.c:95") {
  printf("need=%d source=%d\n", $need, $source);
}
```

Подсчёт попаданий на строку:

```systemtap
global hits;
probe process("/path/app").statement("store@src/put.c:77") { hits++ }
probe end { printf("hits=%d\n", hits) }
```

Инъекция (единственный рабочий приём — перезапись возврата):

```systemtap
probe process("/path/app").function("mdbx_txn_commit").return {
  if (randint(100) < 5) $return = -30785;   /* MDBX_MAP_FULL эмуляция */
}
```

## 8. Kernel-тапсеты для VM/ФС/диска (справка)

Наблюдение за тем, что ядро делает **за** пользовательский процесс (read-only, root):

| Подсистема | Тапсеты / примеры |
| --- | --- |
| Диск/блочный слой | `ioblock.request`, `ioscheduler.*` |
| Файловая система (VFS) | `vfs.read`, `vfs.write` (+`.return`), `vfs.*file_operation*`; пример `disktop.stp` (учёт байт по процессам с пропуском кэша через `devname != "N/A"`) |
| Виртуальная память | `vm.pagefault` и др. из `tapset/linux/memory.stp`, `proc_mem.stp` |
| Сисколлы | `syscall.*` (+`.return`), `syscall_any.stp` |

## 9. Чек-лист ошибок

- [ ] debuginfo целевого бинаря установлен/собран (`-g`; проверить `readelf -S` на `.debug_*`);
- [ ] путь к исполняемому файлу точный (использовать абсолютный `PATH`);
- [ ] `FN@SRC:LINE`, а не голый `SRC:LINE`, если возможны inline/несколько функций;
- [ ] версия ядра ≥3.5 (встроенный uprobes) для дефолтного user-space режима;
- [ ] права: root ИЛИ настроенный stap-server + группа `stapusr` ИЛИ `--runtime=dyninst`;
- [ ] учитывать влияние `-O2`/inline на `$var` и позицию statement;
- [ ] помнить: `.mark()`/`.statement()` не меняют поведение; инъекция — только `.return`;
- [ ] статическая проверка наличия маркеров в CI — через `readelf -n` (без root и рантайма).
