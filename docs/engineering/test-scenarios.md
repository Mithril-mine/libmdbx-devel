# Тестовые сценарии и точки встройки зондов (test-scenarios)

> Часть индекса [Skynet](README.md).
> Спецификации сценариев для расширения тестового покрытия libmdbx: **что и как тестировать**.
> Документ предназначен:
>   - агенту, пишущему тесты (`tests/ut/*`, `tests/issues/*`) — сценарии как ТЗ;
>   - агенту(ам), встраивающему пробники SystemTap/DTrace — «болевые точки» с контекстом.
>
> Связанные документы: [`test-coverage.md`](test-coverage.md) (карта «тесты → модули» и дыры),
> [`functional-architecture.md`](functional-architecture.md) (как работает движок, без привязки
> к файлам), [`architecture.md`](architecture.md) (внутренняя структура по модулям).
>
> Статус: **первая партия** — ядро (GC, commit-конвейер, CoW, мета/восстановление, спилл,
> долгие читатели). Партии по API-группам (`c_dbi`, `c_crud`, `c_cursors`, `c_rqest`,
> `c_extra`, C++ API) — следующие итерации.

## 1. Как пользоваться документом

Каждый сценарий имеет:

| Поле | Смысл |
| --- | --- |
| `ID` | сквозной идентификатор `SC-<n>` |
| `Область` | подсистема/API-группа (см. `test-coverage.md` §6 — дыры) |
| `Сценарий` | что делаем, какими API, какой паттерн (белый/серый ящик) |
| `Ожидания` | конкретные проверяемые результаты (включая коды ошибок и исключения C++) |
| `Пробники` | предлагаемые USDT-точки для встройки, наблюдаемые переменные, инъекции |

Правила:

- Сценарии пишутся **по функциональным механизмам**, без жёсткой привязки к файлам,
  но с именами внутренних фаз/функций (это то, что нужно для встройки пробников).
- Для каждого сценария указано, **какие ветки исполнения должны быть затронуты**
  (иначе тест может «проходить мимо» механизма — классическая ловушка поверхностных тестов).
- Инъекция сбоев: пробники могут **менять значения** на точке входа/выхода фазы
  (например, принудительно вернуть код ошибки или подменить число страниц).
- Каждый сценарий должен быть выполним **без опоры на внутренние структуры**
  (публичный API + диагностика `mdbx_env_info_ex` / `mdbx_txn_info` / `mdbx_gc_info`),
  пробники — белая вкладка поверх.

## 2. Инфраструктура пробников (SystemTap/DTrace/USDT)

### 2.1. Что уже есть в коде

- В `preface.h` определены `DTRACE_PROBE0..9` из `<sys/sdt.h>` при
  `ENABLE_DTRACE || ENABLE_SYSTEMTAP`, иначе — `__noop`.
- Провайдер: `mdbx`; макросы `MDBX_DTRACE0..9` (`MDBX_DTRACE_PROVIDER=mdbx`).
- Единственный существующий пробник: `panic` (в обработчике панических ошибок).
- Проверка сборки: `-DENABLE_SYSTEMTAP` (+ наличие `sys/sdt.h`).

### 2.2. Что это даёт тестам

Система USDT (статическая трассировка) позволяет тесту/обвязке:

1. **Наблюдать путь исполнения**: на какие ветви попало выполнение (например,
   «страница взята из GC» vs «из хвоста файла» vs «спилл включился»).
2. **Читать значения** локальных переменных на точках входа/выхода фаз.
3. **Инъектировать ошибки/отказы**: перезаписывать возвращаемое значение или параметр
   в точке выхода, эмулируя сбой (см. SystemTap `return` probe / `$retval = N`).

### 2.3. Соглашение об именах пробников

Предложение (нужно согласовать с главным архитектором):

```
mdbx::<подсистема>::<фаза>::<событие>
пример: mdbx::commit::gc_update::begin / end
        mdbx::alloc::from_gc / from_tail / spill_kicked
        mdbx::meta::two_phase::validate
        mdbx::reader::slot_park / oust
```

Свойства хорошей точки встройки («болевая точка»):

- **на границе фаз** (вход/выход), а не внутри цикла — дешёво и однозначно;
- параметры — **простые типы** (txnid, pgno, счётчики, коды) — их можно и логировать, и менять;
- для инъекции — точка, где решение уже принято, но ещё не применено
  (удобнее всего выход из функции с возвращаемым кодом).

### 2.4. Болевые точки по умолчанию (кандидаты на встройку)

| Фаза/место | Кандидаты пробников | Наблюдаемые величины |
| --- | --- | --- |
| Снятие снапшота читателя | вход/выход захвата снапшота, повторные попытки | txnid, число ретраев |
| Старт пишущей транзакции | получение мьютекса писателя, вычисление front-txnid | txnid, front_txnid |
| Коммит: gc_update | начало/конец цикла, число итераций | число записей GC, txnid |
| Коммит: refund | сработал ли refund, объём возврата | кол-во страниц |
| Коммит: спилл | триггер спилла, выбор кандидатов | dp_limit, dirtyroom, LRU-метки |
| Аллокация страницы | источник: GC (LIFO/FIFO) / хвост файла / рост файла | pgno, npages, режим |
| CoW/touch страницы | frozen→копия, spilled→unspill, shadowed | txnid страницы, состояние |
| Утилизация большой записи | bigfoot-цепочка, эффективный txnid | длина цепочки |
| Мета: двухфазное обновление | validate/invalidate половины, sign | txnid_a/txnid_b, steady/weak |
| Recovery/открытие | выбор последней цельной меты | выбранная мета, stuck_meta |
| Долгие читатели | детент, kick_laggards, HSR-вызов | детент, lag, space_retired |
| Парковка/вытеснение | PARKED→OUSTED переход | старый/новый tid слота |
| Дефрагментация | цикл переноса страниц, сдвиг родителя | число перенесённых страниц |

## 3. Ядро: сценарии (первая партия)

### SC-1. Переиспользование страниц уважает детент (долгий читатель)

**Область:** GC, mvcc-readers. Дыра: нет прямого теста «заморозки» GC долгим читателем.

**Сценарий:**
1. Создать БД, заполнить N записей, закоммитить.
2. Открыть долгую read-транзакцию R (зарегистрировать слот).
3. В цикле перезаписывать один и тот же ключ K раз (каждый раз — отдельная write-транзакция).
4. Наблюдать: размер файла растёт, `txn_space_retired` у R растёт; `txn_info(R).txn_reader_lag`
   увеличивается; пространство не переиспользуется (нет отката first_unallocated).
5. Завершить R. Следующие write-транзакции должны переиспользовать освобождённые страницы
   (first_unallocated перестаёт расти; при включённом shrink — файл уменьшается).

**Ожидания:** рост файла объясним только «замороженными» страницами; после завершения R —
немедленное переиспользование; `txn_space_retired` корректно отражает объём.

**Пробники:**
- `mdbx::alloc::source` (pgno, mode=gc/tail/grow) — проверить, что при живом R всегда `tail`/`grow`,
  после смерти R появляются `gc`.
- `mdbx::gc::detent_update` (oldest_txnid) — детент зафиксирован номером R.
- `mdbx::reader::slot_release` (tid) — момент освобождения R.

**Инъекция:** на `mdbx::alloc::source` принудительно вернуть `MDBX_MAP_FULL` (эмуляция исчерпания)
и проверить поведение писателя (см. SC-14).

### SC-2. BigFoot: цепочка записей GC при гигантском освобождении

**Область:** GC, bigfoot. Дыра: только косвенное покрытие в stochastic.

**Сценарий:**
1. БД со страницей 4 КБ. Положить значение V ≈ 64–128 МБ (прогон overflow-страниц).
2. Перезаписать V другим значением того же порядка (CoW всего прогона + освобождение старого).
3. Через `mdbx_gc_info()` и `env_info_ex` убедиться, что появилась цепочка записей GC
   (несколько последовательных txnid), а не одна запись.
4. Повторить несколько раз; затем удалить ключ с V полностью.
5. Убедиться, что после завершения всех читателей страницы переиспользуются корректно
   (размер не растёт без причины).

**Ожидания:** освобождение оформлено как цепочка (BigFoot), утилизация корректна, no UAF/двойного
освобождения (валидация `MDBX_CHECKING=2` не ругается).

**Пробники:**
- `mdbx::gc::bigfoot_chain::begin/end` (txnid_begin, txnid_end, длина цепочки).
- `mdbx::alloc::big_run` (pgno, npages) — поиск контигуальной последовательности.
- `mdbx::gc::time_limit_hit` — срабатывание `gc_time_limit` (опционально).

### SC-3. Спилл: лимиты, LRU, страницы под курсорами

**Область:** spill, dpl. Дыра: только issue_gh0010/0011; нет прямых сценариев LRU/приоритетов.

**Сценарий:**
1. Установить маленький `txn_dp_limit` (через `mdbx_env_set_option`), включить спилл.
2. Создать много грязных страниц: (а) массовая вставка; (б) обновление большого значения.
3. (а) Проверить: страницы, на которые указывают открытые курсоры, не выгружаются
   (`MDBX_TXN_SPILLS` флаг, поведение без ошибок).
4. (б) Проверить: overflow-страницы имеют приоритет выгрузки (LRU age).
5. Довести грязный список до предела → проверить `MDBX_TXN_FULL` (если спилл невозможен).
6. Убедиться, что после коммита данные консистентны (повторное чтение всех ключей).

**Ожидания:** корректность при любом порядке выгрузки; спилл-страницы не «теряются»
(повторная модификация выгруженной страницы корректна).

**Пробники:**
- `mdbx::spill::kick` (reason=limit/lru, n_pages).
- `mdbx::spill::pick` (pgno, priority) — проверить, что pinned-курсорами страницы не выбраны.
- `mdbx::dpl::sort` (режим: insertion/mergesort/radix) — для проверки пути сортировки.

**Инъекция:** на `mdbx::spill::pick` форсировать выбор «неправильной» страницы (той, что под
курсором) и убедиться, что движок всё равно корректен (или что тест ловит нарушение).

### SC-4. Commit-конвейер: порядок фаз и их наблюдаемость

**Область:** txn-basal, gc-update, dxb-sync, мета. Дыра: нет прямых тестов порядка фаз.

**Сценарий:**
1. Выполнить серию write-транзакций, порождающих освобождения и dirty-страницы.
2. С помощью пробников построить «журнал событий» коммита
   (последовательность: gc_update → refund → spill → audit → meta → sync).
3. Проверить инварианты: refund выполняется до записи в GC; спилл до меты;
   мета двухфазно; не-WRITEMAP — единый `pwrite` меты.
4. Прогнать с `MDBX_CHECKING=2` — аудит коммита не сообщает о расхождениях.

**Ожидания:** порядок фаз стабилен и соответствует документации; после сбоя в любой точке
(инъекция) база остаётся консистентной.

**Пробники:**
- `mdbx::commit::phase` (phase=gc_update|refund|spill|audit|meta|sync, txnid).
- `mdbx::meta::two_phase::invalidate/validate` (txnid_a/b).
- `mdbx::refund::tail` (first_unallocated, n_pages).

**Инъекция:** эмулировать сбой на каждой фазе (прервать «питание» между invalidate и validate
меты) → открыть БД → должна быть выбрана предыдущая цельная мета.

### SC-5. CoW: состояния страницы и перенацеливание курсоров

**Область:** page-ops, cursor tracking. Дыра: нет прямых тестов repoint/shadow.

**Сценарий:**
1. Открыть курсор на ключе K.
2. В той же пишущей транзакции обновить K (и соседние ключи), вызывая CoW листа и его предков.
3. Убедиться: курсор продолжает указывать на актуальную версию (значение обновлено),
   стек курсора перенацелен (можно проверить через поведение, а не структуру).
4. Спровоцировать split листа (вставки) при живом курсоре → курсор валиден после split.
5. Использовать `mdbx_is_dirty()` — данные с грязных страниц корректно определяются.

**Ожидания:** ни одного висячего указателя; итерация «чтение-изменение-удаление» в одной
транзакции корректна; `MDBX_CHECKING` probe-проверки стеков не срабатывают.

**Пробники:**
- `mdbx::cow::touch` (pgno, state=frozen|spilled|shadowed, new_pgno).
- `mdbx::cursor::repoint` (dbi, level) — перенацеливание на новую версию.
- `mdbx::cursor::dangling_check` (промах при проверке).

### SC-6. Троика мета и восстановление после «полукоммита»

**Область:** meta-troika, recovery. Дыра: meta-переключение и coherency — только косвенно.

**Сценарий:**
1. Построить серию коммитов, затем эмулировать сбой между фазами двухфазного обновления меты
   (инъекция: оборвать после invalidate).
2. Открыть БД заново: должна быть выбрана последняя цельная (recent или prefer_steady) мета.
3. Проверить `env_info_ex.mi_meta[3]` и поведение читателя (снапшот — старая цельная мета).
4. (Опционально) режим `open_for_recovery`/`turn_for_recovery`: переключение на заданную мету,
   монотонный рост txnid.

**Ожидания:** согласованность троики (216 состояний, fsm); ни одно состояние не даёт «смешанного»
снапшота; инвариант `txnid_a == txnid_b` для валидной меты.

**Пробники:**
- `mdbx::meta::tap` (fsm_state, recent/prefer_steady/tail).
- `mdbx::meta::two_phase::invalidate/validate` (как в SC-4).
- `mdbx::open::pick_meta` (выбранный номер меты, причина).

### SC-7. SAFE_NOSYNC и устойчивая точка (steady)

**Область:** durability (SAFE_NOSYNC), steady-point. Дыра: только smoke/stochastic.

**Сценарий:**
1. Открыть env с `MDBX_SAFE_NOSYNC`.
2. Выполнить серию коммитов (без явного sync). Проверить: последний steady-коммит сохраняется,
   страницы новее steady не переиспользуются (эффект «квази-долгого читателя»).
3. Вызвать `mdbx_env_sync[_poll]` → новый steady-point → переиспользование возобновляется.
4. Проверить счётчик `unsynced_pages` (в env_info/статистике) и `meta_sync_txnid`.

**Ожидания:** после `sync` все коммиты durable; без sync база консистентна (откат к steady при
имитации сбоя); авто-синхронизация (syncperiod/syncbytes) срабатывает по порогам.

**Пробники:**
- `mdbx::sync::steady_point` (txnid) — новый steady.
- `mdbx::sync::poll` (dirty>threshold?) — триггер auto-sync.
- `mdbx::durability::mode` (режим) — проверка активного режима.

### SC-8. Refund и авто-компактификация (implicit shrink)

**Область:** refund, dxb (shrink). Дыра: нет прямых тестов refund/автокомпакции.

**Сценарий:**
1. Геометрия с `shrink_threshold > growth_step`. Наполнить БД, затем удалить ~все данные.
2. Убедиться, что после серии коммитов файл уменьшается (implicit shrink), `first_unallocated`
   откатывается, MADV-вызовы происходят (наблюдаемо через пробы ОС/пробники).
3. Проверить refund: удаление хвостовых записей не порождает записей GC (объём GC не растёт).
4. При активном долгом читателе — файл НЕ сжимается; после его завершения — сжимается.

**Ожидания:** хвост возвращается в неразмеченное пространство (refund), shrink срабатывает только
когда край файла никто не держит; гистерезис (shrink_threshold > growth_step) соблюдается.

**Пробники:**
- `mdbx::refund::tail` (first_unallocated, n_pages) — как в SC-4.
- `mdbx::dxb::shrink` (new_size, threshold) — срабатывание усечения.
- `mdbx::dxb::grow` (old/new size) — рост.

### SC-9. Парковка, вытеснение и HSR

**Область:** park/unpark, ousting, HSR. Дыра: txn-park.c++ частично; нет HSR- и oust-сценариев.

**Сценарий:**
1. Читатель R паркуется (`mdbx_txn_park`): слот помечается `MDBX_TID_TXN_PARKED`, детент не
   удерживается (проверить через рост/переиспользование или txn_info).
2. Писатель при нехватке места вытесняет R (`PARKED→OUSTED`). R при следующем обращении:
   (а) `restart_if_ousted=true` — перезапускается на свежем снапшоте;
   (б) иначе — `MDBX_OUSTED` + reset.
3. Установить HSR-колбэк; довести БД до исчерпания пространства при живом читателе →
   колбэк вызван с корректными {pid,tid,lag,space,retry}; проверить все ветки возврата
   (≤-2, -1, 0, 1, ≥2) по документации.
4. Проверить `MDBX_TXN_PARKED/AUTOUNPARK/OUSTED` во `txn_flags()`.

**Ожидания:** парковка не морозит GC; вытеснение атомарно (CAS); HSR вызывается до роста/MAP_FULL;
после вытеснения память в итоге освобождается.

**Пробники:**
- `mdbx::reader::park` (slot, old_tid).
- `mdbx::reader::oust` (slot, parked→ousted).
- `mdbx::hsr::call` (pid, tid, lag, space, retry, возврат).

**Инъекция:** HSR возвращает -1 (согласие на MAP_FULL) → проверка `MDBX_MAP_FULL`;
возвращает ≥2 (процесс убит) → проверка перерегистрации слота.

### SC-10. Диагностика пространства: txn_info при долгих читателях

**Область:** api-statinfo (`txn_info`, `env_info_ex`). Дыра: поля существуют, но сценариев мало.

**Сценарий:**
1. При живом долгом читателе R: `txn_info(R)` → `txn_space_retired` растёт, `txn_space_leftover`
   убывает к порогу HSR.
2. У пишущей транзакции: `txn_space_dirty` = объём грязных страниц; `txn_space_limit_soft/hard`
   соответствуют настройкам.
3. `scan_rlt` поведение (перечисление слотов читателей) — корректность имён/pid/tid.
4. После завершения R: retired обнуляется/уменьшается.

**Ожидания:** поля согласованы с реальным поведением (проверка через пробники аллокации);
значения монотонны и соответствуют документации.

**Пробники:** см. SC-1 (`alloc::source`, `reader::slot_release`); добавить
`mdbx::stats::space` (retired, leftover, dirty) на выборке.

### SC-11. chk-движок: проверка целостности через API

**Область:** `mdbx_env_chk`, валидация. Дыра: только утилита `mdbx_chk` в smoke.

**Сценарий:**
1. Корректная БД: `mdbx_env_chk` (scopes full) → без ошибок; колбэки прогресса/ошибок вызваны.
2. Повредить данные (через прямой edit файла на странице-листе вне mmap):
   (а) битый порядок ключей; (б) битый счетчик `tree_t.items`; (в) битая мета (txnid_a != txnid_b);
   → `mdbx_env_chk` находит все виды повреждений с корректными кодами.
3. Режим `MDBX_VALIDATION`: открытие повреждённой БД + операция чтения не падает, а возвращает
   ошибку/логирует; «выживание» при обходе повреждённых веток.
4. `mdbx_chk` через API (в библиотеке) совпадает по поведению с утилитой.

**Ожидания:** каждый класс повреждений детектируется; сценарий не зависит от внутренностей
(только публичный API + искусственные правки файла).

**Пробники:**
- `mdbx::chk::scope` (scope, результат).
- `mdbx::chk::page_check` (pgno, повреждение).

## 3.6. Партия 3: CRUD и курсоры

### SC-27. Семантика put/del по матрице (single vs multi-value)

**Область:** c_crud. Дыра: тестов матрицы нет; есть точечные (upsert_alldups, dupfix_multiple).

**Сценарий:**
1. Для обычной таблицы пройти всю матрицу put: `MDBX_NOOVERWRITE` (вставка / `MDBX_KEYEXIST`
   с возвратом старого значения), `MDBX_UPSERT` (вставка/обновление), `MDBX_CURRENT`
   (обновление существующего / `MDBX_NOTFOUND` если нет).
2. Для dupsort-таблицы добавить ветки: `MDBX_UPSERT` добавляет значение;

3. `mdbx_del`: удаление по значению (нет ключа → `MDBX_NOTFOUND`; нет пары → `MDBX_NOTFOUND`);
   `MDBX_ALLDUPS` удаляет все значения; `MDBX_NODUPDATA` — отдельное значение.
4. Сверка результата каждого шага с «эталонной» моделью (независимый справочник).

**Ожидания:** каждое правило матрицы выполняется буквально; ошибки — с точными кодами.

**Пробники:**

- `mdbx::crud::del` (mode=by_key|by_value|alldups, rc).

### SC-28. mdbx_replace: получить/обновить/удалить/извлечь

**Область:** c_crud (replace). Дыра: прямых тестов replace нет.

**Сценарий:**
1. `mdbx_replace(txn, dbi, key, new_data=NULL, old_value=NULL, flags=0)` — «извлечь» (прочитать и
   удалить): значение возвращается, ключ удаляется.
2. Обновление с получением предыдущего значения (`old_value` заполняется).
3. Обновление конкретного мультизначения: `MDBX_CURRENT|MDBX_NOOVERWRITE` + `old_value` задаёт

**Сценарий:**

2. Слоты читателей: потомок не «наследует» чужие живые снапшоты так, чтобы морозить GC.
3. Родитель продолжает работать параллельно; детент учитывает обе ветки.

**Ожидания:** ни повреждений, ни гонок; документированные ограничения (не мульти-писатель).

**Пробники:**
- `mdbx::fork::resurrect` (ok, переназначение mmap).
- `mdbx::reader::slots_after_fork` (родительские слоты сброшены).

### SC-50. Эквивалентность value2key кастомному компаратору

**Область:** value2key vs comparators. Дыра: нет прямого сравнения.

**Сценарий:**
1. Две таблицы с одинаковыми числами: (а) ключи через value2key (порядок по умолчанию);
   (б) сырые биты + кастомный компаратор. Полный скан → одинаковый порядок.
2. `MDBX_INTEGERKEY`-таблица как эталон для int-преобразований.

**Ожидания:** порядок идентичен; value2key «безопасен» для `mdbx_chk` (нет кастомных компараторов).

**Пробники:**
- `mdbx::v2k::compare` (a, b) — сверка с компаратором.

### SC-51. get-cached поверх value2key

**Область:** api-get-cached + value2key. Дыра: связка не покрыта.

**Сценарий:**
1. Читать числовые ключи через `mdbx_cache_get` (после заполнения): HIT/CONFIRMED/REFRESHED
   статусы; значения декодируются обратно в числа.
2. Обновить значение под тем же числовым ключом в отдельной транзакции → кэш корректно
   обновляется/инвалидируется (REFRESHED), без ложных HIT.

**Ожидания:** кэш уважает версии страниц и числовую семантику ключей.

**Пробники:** см. SC-2 (get-cached statuses) + `mdbx::v2k::decode`.

### SC-52. value2key в dupsort/dupfix-таблицах

**Область:** value2key + multimap. Дыра: нет тестов числовых мультизначений.

**Сценарий:**
1. dupsort-таблица, где значения — числовые ключи (через value2key): упорядоченность значений,
   count_ex, навигация по числовым значениям.
2. dupfix-таблица с фиксированным размером (8/4 байта) числовых значений: пакеты
   (`MDBX_MULTIPLE`) читаются/пишутся с сохранением числового порядка.

**Ожидания:** числовая семантика сохраняется внутри мультизначений.

**Пробники:**
- `mdbx::multimap::numeric_value` (dbi, key, n_dups).

## 3.9. Партия 6: платформенные ветки

> Часть сценариев выполнима только на конкретных платформах; помечены `[platform: …]`.
> На CI они должны гейтиться по матрице (Linux/Windows/macOS), а не гоняться везде.

### SC-53. POSIX-блокировки: flavour'ы блокировок

**Область:** lck (POSIX/SysV/semaphore). `[platform: POSIX]`. Дыра: только `check-posix-locking`.

**Сценарий:**
1. Для каждого flavour'а сборки (POSIX 1988/2001/2008, SysV, semaphore): два процесса на одном
   env — сериализация писателей, таблица читателей согласована, детент общий.
2. Писатель держит блокировку → второй писатель корректно ждёт/получает busy-код
   (таймаутные ожидания — по документации).
3. Смерть процесса-писателя при удержании блокировки → блокировка освобождается ОС,
   новый писатель продолжает (без «зависшей» блокировки).

**Ожидания:** поведение идентично между flavour'ами; никаких мёртвых блокировок после краха.

**Пробники:**
- `mdbx::lck::flavor` (id).
- `mdbx::lck::acquire` (mode=writer, rc).
- `mdbx::lck::released_by_os` (pid).

### SC-54. Windows: файловые блокировки LockFileEx

**Область:** lck (Windows). `[platform: Windows]`. Дыра: нет локальных тестов.

**Сценарий:**
1. Два процесса на одном env (файл на локальном диске): LockFileEx-дисциплина —
   сериализация, таблица читателей в lock-файле.
2. Файл на сетевом шаринге (SMB) — открытие и базовые операции (см. poka-yoke мотивацию).
3. Неверное использование (второе открытие с несовместимыми флагами/страницей) →
   явная ошибка, база не повреждается.
4. Краш писателя → блокировка снимается, следующий писатель продолжает.

**Ожидания:** корректность на локальном диске и SMB; защита от повреждения.

**Пробники:**
- `mdbx::lck::windows::acquire` (LockFileEx rc, offset).
- `mdbx::lck::windows::release`.

### SC-55. WRITEMAP: запись через mmap

**Область:** c_opening (WRITEMAP). Дыра: нет прямых тестов.

**Сценарий:**
1. Открыть с `MDBX_WRITEMAP` (в комбинации с DURABLE/SAFE_NOSYNC/UTTERLY_NOSYNC):
   данные пишутся через mmap; после коммита видны без переоткрытия.
2. `prefault_write_enable`: отсутствие page-fault'ов/чтений с диска при первом обращении
   к новым страницам (наблюдаемо через mincore/pgop).
3. Сочетание WRITEMAP + вложенные транзакции — документированное ограничение
   (несовместимо) → явная ошибка при старте вложенной.
4. Crash-семантика: соответствует выбранному режиму долговечности (steady-точка).

**Ожидания:** консистентность как у не-WRITEMAP при том же режиме; prefault работает.

**Пробники:**
- `mdbx::writemap::touch` (pgno, prefault?).
- `mdbx::sync::msync` (rc, n_pages).

### SC-56. MAPASYNC legacy: нормализация

**Область:** c_opening (флаги env). Дыра: нет теста нормализации.

**Сценарий:**
1. Открыть с `MDBX_MAPASYNC` → фактически включается `MDBX_SAFE_NOSYNC`
   (legacy-поведение); проверить через эквивалент `combine_durability_flags` на уровне API
   (документированный итог).
2. `MDBX_NOSYNC`/`MDBX_NOMETASYNC`/`MDBX_UTTERLY_NOSYNC` — нормализация и комбинации
   (см. SC-22).

**Ожидания:** нормализация однозначна и задокументирована; ни одна комбинация не «проскакивает».

**Пробники:** `mdbx::opts::normalize_durability` (вход/выход).

### SC-57. Режимы без lock-файла и WSL1

**Область:** c_opening (exclusive/lck-less), platform. `[platform: как указано]`. Дыра: частично
issue_gh0016.

**Сценарий:**
1. `MDBX_EXCLUSIVE`/без-LCK режим в одном процессе: сериализация сохраняется,
   таблица читателей внутри процесса; второй процесс не может открыть — явная ошибка.
2. `[platform: Linux/WSL]` WSL1: `mdbx_env_open` возвращает `ENOLCK` (работа невозможна),
   БД не повреждается.
3. `MDBX_NORDAHEAD` и прочие флаги открытия — отсутствие побочных эффектов на чтении.

**Ожидания:** явные коды ошибок вместо повреждения; exclusive корректен.

**Пробники:**
- `mdbx::lck::exclusive` (ok).
- `mdbx::open::enolck` (WSL1, rc).

### SC-58. Многопроцессная среда: общий детент

**Область:** mvcc-readers, lck. `[platform: POSIX/Windows]`. Дыра: частично open.c++ (multi-env),
нужен сценарий reader-синхронизации между процессами.

**Сценарий:**
1. Процесс A: долгий читатель. Процесс B: churn-запись. Детент в B учитывает снапшот A
   (рост файла, затем после завершения A — переиспользование) — сквозь процессы.
2. Смерть A с живым снапшотом → его слот очищается механизмом живости; детент в B сдвигается.
3. Одновременные писатели в двух процессах — строго один (сериализация).

**Ожидания:** межупроцессный детент корректен; чужие мёртвые слоты не морозят GC.

**Пробники:**
- `mdbx::reader::cross_proc_detent` (oldest_pid, txnid).
- `mdbx::lck::writer_serialize` (pid, очередь).

### SC-59. Переносимость формата: endianness и размер страницы

**Область:** database_format, c_opening. `[platform: big-endian, прочее]`. Дыра: нет тестов.

**Сценарий:**
1. БД, созданная на little-endian, открывается на big-endian (и наоборот) — данные читаются
   корректно (формат зависит только от endianness).
2. Нестандартные размеры страницы (256…65536): создание, работа, переоткрытие; граничные
   значения (min/max).
3. Несовпадение размера страницы/разрядности при открытии → `MDBX_INCOMPATIBLE`.

**Ожидания:** симметричный формат; корректные ошибки несовместимости.

**Пробники:**
- `mdbx::fmt::endian` (host, db).
- `mdbx::open::pagesize_mismatch` (rc).

### SC-60. Большие БД и лимиты

**Область:** dxb (рост), limits. Дыра: probe.c++ частично; нужны сценарии пределов.

**Сценарий:**
1. `mdbx_limits_*`: keysize/valsize/pairsize `...4page_max`, min-границы — согласованность
   с фактическими возможностями (большое значение на грани → ок; сверх → `MDBX_BAD_VALSIZE`).
2. Рост файла до больших размеров (несколько ГБ) при `growth_step` — рост кратен шагу;
   `MDBX_UNABLE_EXTEND_MAPSIZE` при невозможности расширить.
3. `MDBX_MAX_DBI`/`MDBX_READERS_LIMIT` — поведение на пределе (см. также SC-21/SC-23).

**Ожидания:** лимиты точны; ошибки на границе явные.

**Пробники:**
- `mdbx::limits::check` (kind, value, ok?).
- `mdbx::dxb::grow` (old/new, cause).
