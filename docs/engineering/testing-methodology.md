# Методика управляемого/контролируемого тестирования

> Документ описывает методику достижения полного покрытия libmdbx тестами через
> замкнутый контур управления над кодом: **измеряй → наблюдай → инжектируй →
> проверяй последствия**, управляемый данными парсера исходников (refactoring-map)
> и динамического покрытия. Синтез с конкретными инструментами трассировки
> (SystemTap/DTrace, ETW, LTTng, bpftrace, Frida, Detours, strace/п-налоги) —
> отдельный этап (глава 8); здесь макросы описываются как абстрактный контракт,
> независимый от реализации.

## Глава 0. Определение и место в контуре

**Управляемое/контролируемое тестирование** = замкнутый контур управления над
испытуемым кодом. Три канала инструментации образуют его «привод»:

| Канал | Макрос | Аналог в контуре | Что даёт тесту |
| --- | --- | --- | --- |
| Измерительный | `MPROBE_COLLECT` | датчик | статистика, распределения, величины по контексту |
| Событийный | `MPROBE_WATCH` | сигнальная лампа | факт выполнения ветви/фазы, инварианты порядка |
| Исполнительный | `MPROBE_FAULT` | актуатор | принудительное изменение хода (инъекция ошибок) |

Закон управления («как довести покрытие до полноты») — конвейер из главы 2:
парсер+coverage → дельта пробелов → гипотеза (SC) → встройка макросов по anchors →
верификация по трём осям полноты → итерация.

**Важно:** имена макросов условные; по мере применения набор будет разнообразен
(см. главу 5, «расширяемость»). Макросы — это **контракт**, не реализация: на
разных платформах один и тот же макрос исполняется разными механизмами (проба в
коде, ETW-лог + парсинг, динамическая инструментация, перезапись возврата), а в
production-сборках компилируется в `noop`.

## Глава 1. Контракт трёх макросов

### 1.1 `MPROBE_COLLECT` — статистический пробник

Собирает статистику прохождения точки с привязкой к контексту.

- **Семантика:** при каждом прохождении точки выполняется агрегация значений
  аргументов по ключу контекста; результат доступен по запросу/в конце сессии.
- **Минимальные параметры (обязательные):**
  - `anchor` — стабильный идентификатор точки из карты кода (`symbol#block-id`);
  - `value` — значение/величина для агрегации (или просто счётчик попаданий);
  - `agg_scope` — **иерархия привязки контекста**: `process > env > txn > thread > call-site`
    (что агрегируется — критично для непротиворечивости, см. Кайдзен K1);
  - `reset_mode` — когда статистика обнуляется (`on-demand` / `per-session`).
- **Желательные (декорирующие):** фильтры по условию, временное окно,
  гистограмма/статистические агрегаты (min/max/p90), экспорт в метрики.
- **Пример (SystemTap):** распределение источника аллокации страниц по txn —
  `probe mark("alloc__source") { cnt[$arg2]++ }` с выдачей по завершении.

### 1.2 `MPROBE_WATCH` — событийный пробник (детектор)

Фиксирует факт выполнения ветви/фазы/события, при необходимости с условиями по
контексту или значениям. **Обязан быть эмулируемым через специфическое
логирование (например ETW) и парсинг этих логов** — т.е. его контракт — это
«наблюдаемый факт», а не конкретный механизм.

- **Семантика:** при прохождении точки вычисляется предикат; при истинности
  порождается событие с контекстом; доставка события абстрагирована.
- **Минимальные параметры:**
  - `anchor`; `predicate` — условие (по аргументам/контексту; может быть «всегда»);
  - `delivery` — способ доставки события (прямая проба / трассировочный лог / производное);
  - `fidelity` — уровень достоверности: `direct-probe` | `traced-log` | `derived`
    (см. Кайдзен K2).
- **Желательные:** correlation-id для связывания фаз, агрегация «первый раз»,
  повторы/пороги (сработать не чаще раза за N), приоритет/маска важности.
- **Пример:** фиксация факта «детент GC обновлён до txnid=R» —
  `mark("gc__detent_update") { if ($oldest_txnid == R) log(...) }`.

### 1.3 `MPROBE_FAULT` — инъекционный пробник (закладка)

Изменяет ход выполнения программы: подмена возвращаемого значения, аргумента или
системного вызова — с целью тестирования отказа и восстановления.

- **Семантика:** в точке, при выполнении условий активации, модифицирует результат
  операции до того, как он повлияет на вызывающий код.
- **Минимальные параметры:**
  - `anchor`; `action` — вид вмешательства: `return` | `arg` | `syscall`;
  - `code` — значение/код ошибки (например `MDBX_MAP_FULL`, `ENOSPC`);
  - `activation` — условие срабатывания (вероятность / шаг N / предикат / однократно);
  - `scope` — область видимости: процесс / env / экземпляр БД (изоляция! см. K3);
  - `teardown` — обязательное восстановление исходного поведения после сценария.
- **Желательные:** каскад действий, стек инъекций, классификация codepoint,
  автоматический отчёт «какая точка и каким кодом была проинъецирована».
- **Пример:** эмуляция исчерпания места на аллокаторе —
  `function("...").return { if (randint(100)<5) $return = MDBX_MAP_FULL }`.

### 1.4 Сквозные атрибуты всех макросов

| Атрибут | Требование |
| --- | --- |
| `anchor` | стабильный id из карты кода (`symbol#block-id`), **не номер строки** (строки нестабильны) |
| `tier` | `noop` (продакшн) / `test` (тестовые сборки) / `dev` (рантайм-трассировка) |
| `availability` | маска платформ, где макрос имеет реализацию (иначе — noop/эмуляция) |
| `determinism` | детерминированный сценарий — фиксированные seeds/шаги; рандом — только в явном `activation` |

## Глава 2. Движок полноты (конвейер)

1. **База.** Карта кода из парсера (символы, блоки, `#if`-регионы, рёбра вызовов)
   + динамическое покрытие (coverage строк/ветвей, uncovered-острова).
2. **Дельта пробелов.** Для каждой области: какие блоки/ветви не пересечены ни одним
   тестом (uncovered-острова) и какие пересечены, но без доказательства инварианта
   («ложное покрытие» — линия пройдена, смысл не проверен).
3. **Целеполагание.** Остров/ложное покрытие → формулировка поведенческого контракта
   → гипотеза (SC по каталогу `docs/engineering/test-scenarios.md`).
4. **План наблюдения.** Определить, какие каналы нужны для доказательства гипотезы:
   - «сколько/распределение/в каком контексте» → `MPROBE_COLLECT`;
   - «факт/порядок/условие/не-произошло» → `MPROBE_WATCH`;
   - «поведение при отказе/восстановление» → `MPROBE_FAULT`.
5. **Встройка контракта.** Макросы ставятся в точки по `anchor` из карты, в
   минимальном наборе параметров; реализация выбирается по платформе и `tier`.
6. **Верификация полноты** (глава 3).
7. **Итерация** — неподтверждённые пункты превращаются в новые SC или уточнение
   параметров макросов (глава 7).

## Глава 3. Полнота покрытия (три оси)

Область кода считается полностью покрытой, когда выполнены все три оси:

1. **Структурная** — все достижимые блоки/ветви области пересечены хотя бы одним
   тестом (данные coverage; недостижимые ветви помечаются через `#if`-классификацию).
2. **Поведенческая** — по каждому содержательному блоку есть доказательство смысла:
   `MPROBE_COLLECT` подтвердил ожидаемые распределения (не пустые, соответствуют
   модели), `MPROBE_WATCH` подтвердил порядок фаз и инварианты.
3. **Отказоустойчивая** — каждая точка возврата ошибки/граничное условие области
   проинъецирована `MPROBE_FAULT` хотя бы раз, последствия проверены, восстановление
   корректно (БД цела, повторные операции успешны).

**Метрики эффективности методики:**
- доля закрытых uncovered-островов на сценарий;
- число инъекционных покрытий на точку (сколько кодов ошибок прогнано);
- стоимость (wall-clock теста на покрытую область);
- fidelity-сводка (сколько WATCH-фактов получено direct vs traced-log vs derived);
- детерминизм (число повторных прогонов без флаков).

## Глава 4. Правила применения каналов

| Нужно доказать | Канал | Типичный вопрос |
| --- | --- | --- |
| распределение/величина/тренд | `COLLECT` | «сколько раз, в каком контексте, каково p90» |
| факт выполнения ветви | `WATCH` | «выполнилась ли ветвь/фаза, в каком порядке» |
| инвариант «не должно случиться» | `WATCH` + сбор события в «ловушку» | «встретилось ли запрещённое состояние» |
| поведение при отказе | `FAULT` | «что если вернуть ошибку в точке X» |
| восстановление | `FAULT` + повторные операции | «корректен ли следующий коммит после сбоя» |

- **Эмуляция WATCH через логи** (ETW и т.п.): допустима, но требует указания
  `fidelity` и **калибровки по эталону** (хотя бы раз на платформе детектор
  сверяется с прямой пробой, например SystemTap) — см. Кайдзен K2.
- **Изоляция FAULT:** инъекция только в тестовых сборках (`tier=test`), строгий
  `scope` (процесс/env/экземпляр БД), явный `activation` и обязательный `teardown` —
  иначе инъекция «протекает» в соседние тесты (см. K3).

### 4.1. Таксономия инструментов (классификация реализаций)

Ландшафт средств трассировки широк и запутан (SystemTap/DTrace, eBPF/bpftrace,
ETW, LTTng, Frida, Detours, strace, Lever и др.); возможности разные, частью
дополняют друг друга, не все умеют влиять на поток, на разных платформах —
разные инструменты. Чтобы методика не зависела от перечисления имён, ЛЮБОЙ
инструмент описывается набором классификационных осей:

| Ось | Значения | Влияние на методику |
| --- | --- | --- |
| **mutate-capability** | `observe-only` \| `mutate` | решает, может ли инструмент служить реализацией `MPROBE_FAULT` |
| **область** | `kernel` \| `user-space` \| `both` | решает, какие anchors доступны |
| **механизм** | `static-markers` (USDT/ETW) \| `dynamic-instr` (Frida/Detours/uprobes) \| `log-parse` (ETW-файлы) \| `syscall-trace` (strace/Lever) | решает, как доставляются события и какой `fidelity` достижим |
| **платформа** | Linux/macOS/Windows/FreeBSD/… | определяет доступный набор кандидатов |
| **права/стоимость** | root vs нет; рантайм vs нет; per-run vs attach | влияет на выбор в CI/dev |
| **применимость к FAULT** | способ и надёжность mutate | вход для процедуры выбора (4.2) |

### 4.2. Процедура выбора реализации и fallback-цепочка

Правило «самая дешёвая реализация» (глава 8) разворачивается в явную процедуру:

1. Для канала (`COLLECT`/`WATCH`/`FAULT`) определить **требуемую capability**:
   наблюдение достаточно или нужно изменение потока.
2. По платформе выбрать кандидатов из таксономии (4.1), у которых требуемая
   capability есть.
3. Из кандидатов предпочесть самую дешёвую по стоимости при сохранении
   необходимого `fidelity` (CI > dev; static-markers/log-parse дешевле
   dynamic-instr).
4. Если на платформе **нет** реализации с нужной capability → fallback-цепочка
   (сверху вниз, пока не применимо):
   - тестовая сборка с `#if`-хуками (`tier=test`);
   - параметризованные инжекторы тестового фреймворка (`mdbx_test`);
   - для `WATCH` — специфическое логирование + парсинг (ETW) с `fidelity` и
     калибровкой по эталону;
   - последний резерв — «тест без доказательства»: факт доказывается косвенно
     через observable-API (размер, статистика, коды возврата) — помечается как
     `derived` и не считается полноценным поведенческим покрытием.

### 4.3. Правило FAULT-оси (инъекция при отсутствии mutate-инструмента)

Большинство трассировочных инструментов — `observe-only`; мутация либо хрупка
(например перезапись `$return` у SystemTap), либо доступна только у
специализированных (Frida, Detours). Поэтому:

- **Отказоустойчивая ось полноты обеспечивается приоритетно через тестовые
  сборки и инжекторы фреймворка**, а не через трассировочные инструменты;
- трассировочные инструменты выполняют роль наблюдения и **валидации** (что
  инъекция сработала в нужной точке и с нужным эффектом);
- mutate-способные инструменты (Frida/Detours и т.п.) — дополнительный канал
  FAULT там, где они доступны и надёжны;
- следствие: `MPROBE_FAULT` обязан иметь реализацию на `tier=test` (хуки/инжекторы),
  чтобы ось была обеспечена независимо от ландшафта инструментов.

## Глава 5. Требования к макросам (минимальные vs желательные)

| | Минимальное ядро (без него макрос не работает) | Желательное (расширение, реализация может не поддерживать) |
| --- | --- | --- |
| Все | `anchor` по карте кода; 0..N аргументов; `noop`-компиляция без рантайма; компилируемость на всех платформах | wildcards по anchors; фильтры; экспорт в метрики; attach/detach к живой системе |
| `COLLECT` | значение + `agg_scope` + `reset_mode` | гистограммы/агрегаты; временное окно; условная выборка |
| `WATCH` | предикат + `delivery` + `fidelity` | correlation-id; «первый раз»; пороги повторов |
| `FAULT` | `action` + `code` + `activation` + `scope` + `teardown` | каскад/стек инъекций; классификация codepoint; автоотчёт |

**Расширяемость имён (по мере применения):** триада COLLECT/WATCH/FAULT — ядро;
дальнейшие варианты — через суффиксы по действию/виду: `FAULT_RETURN`, `FAULT_ARG`,
`FAULT_SYSCALL`; `COLLECT_METER`/`COLLECT_ACCUM`; `WATCH_TRACE`/`WATCH_EVENT` и т.п.
Все варианты могут пригодиться под разные реализации.

## Глава 6. Проверка на трёх сложных сценариях

Три сценария выбраны так, чтобы каждый требовал всех трёх каналов (см. каталог
`docs/engineering/test-scenarios.md`).

### SC-1. Переиспользование страниц уважает детент (долгий читатель)

- **Гипотеза:** при живом долгом читателе R GC не переиспользует «замороженные»
  страницы (источник аллокации — tail/grow), после смерти R — сразу gc.
- **Пробел покрытия:** нет прямого теста «заморозки» GC долгим читателем.
- **Каналы:**
  - `MPROBE_COLLECT` на `alloc::source` (pgno, mode=gc/tail/grow), `agg_scope=txn`
    → распределение источников до/после смерти R;
  - `MPROBE_WATCH` на `gc::detent_update` (oldest_txnid=R) и `reader::slot_release`
    → факт фиксации детента и момент освобождения;
  - `MPROBE_FAULT` на `alloc::source` → форсировать `MDBX_MAP_FULL` (эмуляция
    исчерпания) и проверить поведение писателя (мост к SC-14).
- **Верификация:** структурно — ветви tail/grow/gc пересечены; поведенчески —
  COLLECT показывает gc=0 при живом R и gc>0 после; WATCH подтвердил порядок
  detent→release; отказоустойчиво — MAP_FULL проинъецирован, писатель корректно
  вернул ошибку, БД цела.

### SC-6. Троика мета и восстановление после «полукоммита»

- **Гипотеза:** двухфазное обновление меты согласовано (216 состояний FSM); после
  обрыва между invalidate и validate выбирается последняя цельная мета.
- **Пробел:** meta-переключение и coherency проверялись только косвенно.
- **Каналы:**
  - `MPROBE_COLLECT` на `open::pick_meta` → статистика выбора recent vs prefer_steady;
  - `MPROBE_WATCH` на `meta::two_phase::invalidate/validate` (+`meta::tap`) → порядок
    фаз и отсутствие «смешанного» снапшота;
  - `MPROBE_FAULT` → оборвать коммит между фазами (полукоммит), затем проверить
    выбор меты и восстановление; опционально `open_for_recovery`.
- **Верификация:** все состояния FSM, достижимые при полукоммите, пересечены;
  COLLECT показывает монотонность txnid; WATCH доказал инвариант
  `txnid_a == txnid_b` для валидной меты; FAULT-прогоны охватили каждую фазу обрыва.

### SC-14. Исчерпание места: MDBX_MAP_FULL и рост

- **Гипотеза:** последовательность tail→grow→HSR→MAP_FULL корректна; после
  увеличения upper запись возобновляется; рост кратен growth_step.
- **Пробел:** нужны сценарии пределов (частично issue_gh0023).
- **Каналы:**
  - `MPROBE_COLLECT` на `dxb::grow` (old/new, cause) → статистика роста;
  - `MPROBE_WATCH` → факт порядка фаз (tail→grow→HSR→MAP_FULL), срабатывание HSR;
  - `MPROBE_FAULT` → `MDBX_UNABLE_EXTEND_MAPSIZE` (эмуляция отказа mmap) на росте,
    `MDBX_MAP_FULL` на аллокаторе.
- **Верификация:** ошибки в правильном порядке; после инъекций БД не повреждена;
  COLLECT подтверждает кратность роста `growth_step`; повторные операции после
  расширения успешны.

## Глава 7. Кайдзен-протокол (четыре итерации)

Протокол: каждая итерация прогоняет методику на одном из сценариев, фиксирует
недостаток контракта/правил и вносит правку в документ. Итог четырёх итераций уже
отражён в главах 1–4; ниже — сами записи «проблема → правка».

### K1 (SC-1) — контекстная привязка COLLECT неустойчива

- **Наблюдение:** `MPROBE_COLLECT` на `alloc::source` с привязкой «txn» дал
  несогласованную агрегацию: один и тот же путь исполнения проходится из разных
  транзакций, распределение смешалось, вывод не воспроизводим между прогонами.
- **Правка:** в контракт COLLECT добавлено **обязательное** поле `agg_scope` с
  иерархией `process > env > txn > thread > call-site`; методика требует явно
  указывать «что агрегируется». (Глава 1.1.)

### K2 (SC-6) — эмуляция WATCH через логи даёт ложные срабатывания

- **Наблюдение:** детектор фаз меты, эмулированный через специфическое логирование
  (ETW-подобное) + парсинг, срабатывал ложно из-за нестабильного формата лога и
  потери порядка записей между процессами.
- **Правка:** введено поле `fidelity` (`direct-probe | traced-log | derived`) и
  требование **калибровки детектора по эталону** (хотя бы раз на платформе сверка
  с прямой пробой — SystemTap/пробой в коде). (Глава 1.2, 4.)

### K3 (SC-14) — инъекция «протекла» в соседние тесты

- **Наблюдение:** `MPROBE_FAULT` на рост геометрии оказался глобальным для процесса:
  параллельно исполнявшиеся тесты в том же env тоже получили сбой, прогон упал по
  чужой причине.
- **Правка:** контракт FAULT дополнен обязательными `scope` (процесс/env/экземпляр
  БД), `activation` (шаг/вероятность/предикат) и `teardown`; правило «инъекция
  только в тестовых сборках, изолированный env» внесено в главу 4.

### K4 (ландшафт инструментов) — выбор реализации при отсутствии capability

- **Наблюдение:** ландшафт средств трассировки широк и запутан; возможности разные,
  часть инструментов не умеет влиять на поток, на разных платформах разные наборы.
  Правило «предпочесть самую дешёвую реализацию» неприменимо, когда нужной
  capability нет вовсе.
- **Правка:** в главу 4 добавлены: таксономия инструментов по осям
  (mutate-capability/область/механизм/платформа/права/применимость к FAULT),
  явная процедура выбора реализации с **fallback-цепочкой** (тестовые `#if`-хуки →
  инжекторы фреймворка → логи+парсинг для WATCH → последний резерв `derived`) и
  правило FAULT-оси (инъекция обеспечивается приоритетно `tier=test`, трассировка —
  наблюдение/валидация). Глава 8 переоформлена в матрицу синтеза.
