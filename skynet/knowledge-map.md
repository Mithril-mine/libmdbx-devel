- **`decision:memory:readonly-default-server`** (decision, 2026-09-27, imp 0.9): MCP-сервер памяти стартует read-only (SHARED_GRAPH_MEMORY_READONLY, дефолт 1); запись только после явного db_set_mode(readonly=false). Причина: защита от случайных/двойных write-агентов и молчаливой потери данных. Открытие БД сначала read-only; при WANNA_RECOVERY пользователь явно выбирает mdbx_chk или rw-open. Utterly_nosync исключён из ротации db_set_mode и доступен только через опасный db_enable_utterly_nosync.
- **`fact:memory:data-loss-rootcause`** (fact, 2026-09-27, imp 0.95): Настоящая причина потери данных MCP-памяти (26.09): rsync --delete 08:58:52 удалил живую ~/.local/share/shared-graph-memory/db.mdbx — в источнике синка не было файла данных. Операция развёртывания, НЕ дефект движка/модуля: матрица персистентности + probe движка (tests/test_persistence_crash.py, .skynet/tmp/persist-probe) подтвердили штатное поведение libmdbx (краш процесса данные не теряет при любом режиме синка; после kill9 read-only open даёт MDBX_WANNA_RECOVERY). Предотвращение: только tools/install.sh (никогда не трогает db.mdbx/backups).
- **`fact:memory:persistence-verdict`** (fact, 2026-09-27, imp 0.95): Регресса персистентности MCP-модуля НЕТ. Матрица A2/A3 x B1/B2/B3 x C1/C2/C3 (tests/test_persistence_crash.py): durable x любой exit = все записи; safe_nosync x close/SIGTERM = все; safe_nosync x kill9 без close -> меты unsteady (троица s:w:w), read-only open возвращает MDBX_WANNA_RECOVERY (НЕ молчаливый откат), rw-open сам делает steady-sync и данные целы. Probe A1 (чистый Env без Store, .skynet/tmp/persist-probe/probe_engine.py) подтверждает: это поведение движка, не дефект модуля.
- **`proc:memory:durability-policy`** (proc, 2026-09-27, imp 0.85): Критичные знания фиксировать через db_flush() сразу после safe_store (sync force=true), либо переключить режим в durable. По умолчанию safe_nosync: при краше процесса (kill9 без close) страницы данных в page cache, но меты unsteady и read-only открытие требует решения (WANNA_RECOVERY). Выход из режима без краха всегда безопасен (close/SIGTERM делают force sync).

- **`decision:meta:lru-sync-design`** (decision, 2026-09-25, imp 0.9): Редизайн LRU и синхронизации (master 85a570ad, не запушен). Одна write-txn на батч касаний вместо N мелких; env открыт с MDBX_SAFE_NOSYNC (durability выровнена с окружением, WRITEMAP off); автосброс по sync_bytes=64MiB/sync_period=60c (межпроцессные пороги); фоновый тред раз в секунду шлёт mdbx_env_sync_ex(force=false,nonblock=true), на close — stop+join+финальный force-sync. Учтено: схему будем наращивать (карта исходников/функц. блоков, длительности тестов), реестр таблиц TABLES централизован, возможно управление схемой через MCP.
