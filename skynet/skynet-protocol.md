# skynet — протокол координации агентов (v2.16)

> Внутренний протокол взаимодействия агентов, работающих над **libmdbx-devel**
> на одной машине. Реализуется поверх общего хранилища **MCP-memory**
> (libmdbx `graph.mdbx`; см. `AGENT-WORKSPACE.md`, раздел «Общая память агентов»,
> и `memory-codex.md`). Не попадает в амальгамированную версию.
>
> Версия протокола: **2.2** (развивается, см. §8).

## 1. Цель и принципы

Агенты работают параллельно в собственных nook-ах (см. `AGENT-WORKSPACE.md`)
и координируются **асинхронно** через «почту» в MCP-memory. Почта — только
краткая конкретика (что, кому, когда, ссылка); весь объёмный контекст
передаётся файлами (в репозитории — коммиты/PR, вне репозитория —
`${SKYNET_ROOT}/.skynet/`).

Три правила:

1. **Единый источник правды** — граф MCP-memory (общий для всех агентов).
2. **Асинхронность** — письма не требуют одновременного присутствия агентов;
   каждый агент читает почту при старте сессии и периодически.
3. **Восстановимость** — ситуацию можно понять по одним лишь данным памяти,
   либо по одним лишь git-состоянию (см. §7 «Восстановление»).

## 2. Сущности в MCP-memory

| Сущность | Назначение |
| --- | --- |
| `skynet` | мета: версия протокола, формат писем, ссылки на документ |
| `skynet_registry` | реестр агентов: roster, heartbeat-сводка, правила рангов/сессий |
| `skynet_agent_<slug>` | состояние агента: ранг, роль, специализация, status, session_id, heartbeat, last_ref |
| `skynet_inbox_<slug>` | почтовый ящик агента (наблюдения = письма) |

Связи (relations): `skynet_registry -tracks-> agent`,
`agent -uses_mailbox-> inbox`, `skynet -defines-> registry`.

Соглашения об именах: slug латиницей в нижнем регистре, слова через `_`
(`main_architect`, `tests_lead`, ...). Папка внешних артефактов:
`${SKYNET_ROOT}/.skynet/` (вне git).

## 3. Ранги, роли, специализация

- **Ранг** (иерархия): `0` owner (человек), `1` главный архитектор/координатор,
  `2` ведущие специалисты (leads), `3` исполнители (workers).
- **Роль** (чем занимается): coordinator, architect, reviewer, tester, writer,
  skills-maintainer, release-manager (можно несколько, через запятую).
- **Специализация** (фокус): наполнение/поддержание SKILL и контекста
  по своему направлению (core/engine, cpp-api, tests/qa, build/ci, docs/legal...).

Правила изменений:

- Ранги в основном назначает **owner**. Командир может менять ранг/роли
  подчинённых **в пределах своей иерархии** (т.е. агент ранга N управляет
  рангами > N и ниже себя).
- **Специализацию** меняет только **owner или главный архитектор**.
- Изменения фиксируются наблюдением в `skynet_agent_<slug>`
  (`rank=...`, `role=...`, `specialization=...`) с датой и автором изменения.

## 4. Реестр и heartbeat

Каждый агент при старте сессии:

1. Генерирует `session_id` (uuid) и записывает его в свой
   `skynet_agent_<slug>` (наблюдение `session_id=...`).
2. **Зеркалит реальный opencode ses_id** (если доступен) как наблюдение
   `opencode_session_id=ses_...` — оркестратор использует его для возобновления
   канонической сессии (`-s`) вместо создания новой (см. §25b).
3. Обновляет `status=active`, `heartbeat=<ISO-ts>`, `last_ref=<branch> <commit>`.
4. Сверяет себя с `skynet_registry`: если он там не значится — регистрируется
   (см. §5), иначе — сверяет session_id и heartbeat.

Периодичность обновления heartbeat (обязательно):

- **Активная работа** (busy): обновлять heartbeat не реже **каждых 5 минут**.
- **Простой** (idle): не реже **каждых 15 минут**.
- Обновление — новая строка-наблюдение в `skynet_agent_<slug>` вида
  `heartbeat=<ts> status=<state> task=<TASK-n|—> [progress=<одно слово>] [ref=<branch@commit>]`.
- Помимо записи в свою сущность, каждый агент обязан **уведомлять координатора**
  письмом `HEARTBEAT` в `skynet_inbox_main_architect` (см. §19) с той же
  периодичностью и всегда при смене статуса.

Сводку ведёт главный архитектор/координатор в `skynet_registry`.

Правило устаревания (stale):

- Агент **stale**, если: (а) от него нет `HEARTBEAT`-уведомлений координатору
  дольше **2× допустимого интервала** (по умолчанию > 20 минут при busy,
  > 30 минут при idle), **либо** (б) его запись в `skynet_agent_<slug>`
  не обновлялась (heartbeat старше 60 минут), **либо** (в) `session_id`
  отличается от текущего session_id агента.
- Stale-агент при пробуждении обязан: перечитать память + git,
  выполнить процедуру восстановления (§7), перерегистрироваться, обновить
  session_id/heartbeat и отправить `NOTIFY "resumed after stale"` координатору.
- Координатор не назначает задачу агенту со stale-статусом, пока тот не
  перерегистрируется; координатор может переназначить задачу stale-агента (§19).

## 5. Регистрация нового агента

Агент создаёт в MCP-memory:

- `skynet_agent_<slug>` (наблюдения: slug, name, rank, role, specialization,
  status, session_id, heartbeat, last_ref, mailbox).
- `skynet_inbox_<slug>` (наблюдение `empty at registration <ts>`).
- Связи: `skynet_registry -tracks-> agent`, `agent -uses_mailbox-> inbox`.
- Сообщение в `skynet_inbox_main_architect`: `NOTIFY "new agent <slug> registered"`.

Затем главный архитектор подтверждает регистрацию (`ACK`) и включает агента
в roster `skynet_registry`.

## 6. Почта (mailboxes)

### 6.1 Формат письма

Каждое письмо — наблюдение в `skynet_inbox_<получатель>`:

```
[<msg_id>|<ISO-ts>] <from> -> <to> : <TYPE> <subject> | payload: <path|ref> | <однострочное тело>
```

- `msg_id` — сквозной идентификатор: `mail-<seq>-<from>-<to>` (seq — счётчик отправителя).
- `TYPE` — одно из: `PING`, `HEARTBEAT`, `TASK`, `REQUEST`, `QUESTION`,
  `REPORT`, `NOTIFY`, `ACK`, `EOT`, `PROPOSE`.
- `payload:` — ссылка на файл/коммит/PR (если есть). Тяжёлый контекст — только тут.
- Тело — одна строка, без вложенности.

### 6.1a Типы ответов координатора (явные вердикты)

На `REQUEST`/`QUESTION`/`REPORT` координатор отвечает письмом с **явным типом**,
чтобы агент всегда знал состояние своего запроса:

- `REVIEW <VERDICT>` — содержательное ревью результата. `VERDICT` ∈
  `approved` | `approved-with-notes` | `needs-changes`. **Всегда** содержит
  конкретные замечания/пункты (даже при `approved` — что улучшить далее),
  а не просто «смёржено». `needs-changes` требует пересдачи с учётом пунктов.
- `MERGED <ref>` — работа принята и влита в devel (отдельное письмо от `REVIEW`;
  после `REVIEW approved` и мержа шлётся и то и другое, или одно `MERGED` с
  приложенным вердиктом ревью).
- `ANSWERED <ruling>` — решение по вопросу/запросу (для `QUESTION`/`REQUEST`).
- `REJECTED <причина>` — запрос отклонён с пояснением.

### 6.1b Право на исследования и предложения (owner, 2026-09-23)

Агенты **поощряются** проводить исследования по своему усмотрению и предлагать
существенные изменения в практиках/инструментах/технологиях/процессах/
использовании компонентов — не только в рамках назначенных задач:

- Исследование (research) — допустимо без предварительного запроса: read-only
  изучение кода/инфраструктуры/внешних практик; результат — `REPORT` с выводом
  «что изменить и зачем» (не код).
- Существенное предложение — письмо типа **`PROPOSE`** в ящик координатора:
  `[mail-N-<slug>-0.coordinator|ts] <slug> -> 0.coordinator : PROPOSE <что меняем> |
  payload: <ref/док> | обоснование + влияние + риски`. Координатор отвечает
  `REVIEW approved|needs-changes|rejected` или `ANSWERED`.
- Обнаруженный дефект утилит/кода с публичным интерфейсом → координатор
  заводит **GitHub issue** (образец: issues/47) и подготавливает PR по
  стандартному процессу (§30b); агент готовит фикс на ветке.
- Цель (owner): «включить это в процесс управления проектом» — чтобы владелец
  мог комфортно провести ревью публичных артефактов (issues/PR), а рой —
  генерировать существенные улучшения, а не только исполнять ТЗ.

### 6.1c Специализация и право отказа (owner, 2026-09-23)

Экспертиза агента — главный актив роя; распыление по чужим областям превращает
экспертов в чернорабочих (теряется один навык, приобретается половина другого,
потом переучивание). Принципы (division of labour — Smith/Kant; routing-паттерн
Anthropic):

1. **Специализация — приоритет над полнотой решения.** Агент работает строго
   в своей области (см. `skills-roles.md`). Порядок опоры: **набор скиллс →
   контекст → характер информации → цели/задачи**.
2. **Право отказаться от части задачи.** Если назначенная работа требует
   глубокого погружения ВНЕ специализации агента (например CI-инженер вынужден
   разбирать движковый assert) — агент **обязан** остановиться на этой части и
   эскалировать: письмо `QUESTION "scope outside specialization"` + зафиксировать
   найденные факты, чтобы передать владельцу проблемы без потери.
3. **Координатор обязан перепланировать** (routing): передать часть задачи
   профильному агенту, сохранив у исходного только его доменную часть.
4. **Граница передачи**: агент фиксирует находки/гипотезы/воспроизведение в
   файл (`.skynet/tmp/<slug>/<task>-handoff.md`) и ссылается в `QUESTION`;
   принимающий агент продолжает с этой точки (никакого повторного расследования).
5. **Контекст экономится**: НЕ исследовать вне зоны «на всякий случай»;
   research по усмотрению (§6.1b) — тоже в своей области или с явным
   `PROPOSE` перед входом в чужую.

### 6.1d Коллективная база знаний — синергия роя (owner, 2026-09-23)

Знание — основной «производительный актив» роя; **эмерджентный эффект**
(«вместе больше, чем сумма») возникает только когда знания накапливаются в
общей базе и используются всеми:

1. **Пользоваться базой знаний — обязательно.** Перед решением/исследованием
   агент СНАЧАЛА ищет в MCP-memory (`search_nodes`) и в `memory-codex.md`
   существующие сущности/наблюдения по теме — не начинает с нуля. Если знание
   уже есть — опирается на него (с указанием источника), а не переоткрывает.
2. **Пополнять базу знаний — обязательно.** В ходе работы агент записывает
   новые факты/инварианты/уроки в MCP-memory: создаёт/дополняет сущности
   (`create_entities`, `add_observations`) с наблюдениями вида
   `[<ts>] <область>: <факт> (provenance: task/commit/evidence)`.
   Особенно: инварианты кода (Gemba-проверенные), найденные дефекты, принятые
   решения и их обоснование, нетривиальные трапы именования, выводы исследований.
3. **Дублировать знание запрещено** (Kaizen E5): если факт уже есть в базе —
   не копировать, а ссылаться. Новая запись — только новое знание или уточнение
   с `[update ts]`.
4. **Проверка перед записью (Gemba)**: наблюдение фиксируется только после
   сверки с кодом/реальностью (не «вера в отчёты»). Источник/доказательство —
   обязательное поле.
5. **Координатор поддерживает** актуальность `memory-codex.md` (схема памяти,
   инварианты с provenance) и поощряет агентов к наполнению; ретроспективно
   проверяет, что значимые находки каждого цикла осели в базе.
6. Синергия: при поиске агент видит чужой опыт (дефекты, трапы, решения),
   не тратя контекст на повторное открытие; знания дешевеют с каждым добавлением.

Жизненный цикл поставки: агент `REPORT` (готово) → координатор `REVIEW`
(содержательно) → при `approved`/`approved-with-notes` → `MERGED <ref>`
(или `needs-changes` → пересдача) → задача `done`.

### 6.1e Динамика ролей — дрейф специализации (owner, 2026-09-23)

Роли агентов **не статичны**: проект меняется, меняется характер работы,
поэтому фиксированный набор ролей всегда становится неоптимальным. Цель —
**эволюция ролей как управляемый процесс**:

1. **Выявление новых ролей** — появление новой области работы (новая
   технология/процесс/компонент) → агент или координатор инициирует
   `PROPOSE "new role <имя>"` с обоснованием (какие задачи, какой скиллс,
   кто кандидат).
2. **Окрашивание существующих ролей** — уточнение специализации внутри роли:
   например REV:cmake расширяется на build/manifest/amalgam; тестер получает
   направление golden-characterization. Изменения фиксируются в `skills-roles.md`
   (актуальный реестр) и ролевом SKILL-файле.
3. **Дрейф специализации в нужную сторону** — наблюдая, куда смещается
   реальная нагрузка, координатор сознательно сдвигает фокус роли (контекст,
   скиллс, типовые задачи). Не «расширение до чернорабочего», а переориентация
   экспертизы.
4. **Самооценка навыков агентом как обратная связь** — агент регулярно (в
   HEARTBEAT/REPORT) сообщает субъективную уверенность по своим навыкам
   (`skill_confidence` по областям), наблюдения за дефицитом знаний, что даётся
   легко/тяжело. Координатор использует это для перепланирования и дрейфа.
   Это обратная связь для решений и оптимизации — не формальность.
5. **Координатор ведёт** реестр ролей актуальным, фиксирует решения о дрейфе
   с обоснованием (что изменилось в проекте, почему роль эволюционирует),
   чтобы история ролей была видна.

Координатор обязан учитывать §6.1c (не распылять агента) при окрашивании:
дрейф = замена фокуса, а не добавление разрозненных зон.

Координатор **обязан** ответить на каждый `REQUEST`/`QUESTION`/`REPORT`
(даже «ничего не требуется» — письмом `ACK`/`ANSWERED`), а агент обязан
подтвердить получение решения (`ACK`) — иначе запрос считается висящим (§20).

Примеры:

```
[mail-1-main_architect-tests_lead|2026-09-20T11:20:00Z] main_architect -> tests_lead : TASK add cursor batch tests | payload: devel@c4e44373 | branch feature/cursor-batch from devel, target P1 ut.cursor
[mail-2-tests_lead-main_architect|2026-09-20T13:05:00Z] tests_lead -> main_architect : REPORT done | payload: local-origin feature/cursor-batch@f00d | pushed, 3 tests green on gcc+clang
[mail-3-main_architect-tests_lead|2026-09-20T13:07:00Z] main_architect -> tests_lead : ACK ok | merged to devel
```

### 6.2 Поток работы

- Отправитель кладёт письмо в ящик получателя и, при важности, уведомляет
  (`NOTIFY` в ящик координатора).
- Получатель при старте/в цикле читает свой ящик, обрабатывает письма,
  отвечает (`REPORT`/`QUESTION`/`ACK`) и **помечает обработанное** дописав
  `[done <ts>]` к исходному наблюдению (или удаляя его — по договорённости).
- Подтверждение задачи: `TASK` → ожидается `ACK` (принял) и `REPORT` (сделал)
  или `EOT` (завершил с итогом).

### 6.3 Файловый канал

Объёмный контекст — в файлы:

- В репозитории: ветки, коммиты, PR (указываются в `payload:`).
- Вне репозитория: `${SKYNET_ROOT}/.skynet/<msg_id>/` (например,
  полные логи, диффы, отчёты). В git не коммитить.

## 7. Восстановление ситуации (важно)

Если что-то пошло не так, агент обязан восстановить картину **по любому
одному источнику**:

### Только данные MCP-memory (graph.mdbx — канон; legacy JSONL — архив)
- Прочитать `skynet_registry` (roster, heartbeat, stale-правило) →
  понять, кто активен/занят.
- Прочитать свой `skynet_inbox_<slug>` → восстановить незакрытые `TASK`
  (без `EOT`/`ACK`), на которые надо ответить.
- Прочитать `skynet` (версия протокола) и `skynet_agent_*` соседей.
- Если собственная запись имеет чужой/старый `session_id` → это «я после
  рестарта»; предыдущие in-flight задачи считать незавершёнными.

### Только git-состояние
- `git log`, `git status`, ветки в `local-origin` → восстановить, где остановилась
  работа (последний `last_ref` из памяти, ветка/коммит).
- Проверить CI-статусы (SourceCraft/GitHub) — что валидировано.
- Сверить с `skynet/README.md` и `AGENT-WORKSPACE.md` (структура и правила).

После восстановления агент синхронизирует память и git (обновляет
session_id, heartbeat, last_ref) и сообщает координатору.

## 8. Развитие протокола

- Изменения протокола — новым мажорным/минорным номером в `skynet_registry`
  (`protocol_version=...`) и правкой этого документа.
- Предложения: письмо `QUESTION "protocol: ..."` координатору (главному
  архитектору) → решение → правка документа → `NOTIFY "protocol vX.Y"`.

## 10. Жизненный цикл агента (v2)

Состояния агента (`status` в `skynet_agent_<slug>`):

```
unregistered ──регистрация──▶ pending ──одобрение──▶ active
                                                      │   ▲
                                        idle ◀──простоя──┤ busy
                                                      │
                                                  stale/offline (heartbeat > 60 мин)
```

- `unregistered` — агента нет в реестре (нужен онбординг, §11).
- `pending` — заявка подана, ждёт решения координатора.
- `active` — принят, может брать задачи.
- `busy` — выполняет задачу (ставит при взятии, снимает при сдаче).
- `idle` — свободен, готов к назначению.
- `stale`/`offline` — не отвечает (протух heartbeat или чужой session_id).

Переходы фиксируются наблюдением `status=<новое>` с датой в `skynet_agent_<slug>`.

## 11. Протокол присоединения (онбординг нового агента)

Агент стартовал и **не найден** в `skynet_registry` → онбординг:

1. **Имя/slug**: агент придумывает себе slug сам (латиница, нижний регистр,
   слова через `_`), уникальный в реестре. Если не уверен — пишет координатору
   `QUESTION "help choose slug"` с предложениями. Координатор обязан ответить.
2. **Специализация**: агент **предлагает** свою специализацию (фокус:
   наполнение/поддержание SKILL и контекста по направлению). Финальное
   значение утверждает owner или главный архитектор (§3).
3. **Заявка** — письмо координатору в `skynet_inbox_main_architect`:
   ```
   [mail-1-<slug>-main_architect|ts] <slug> -> main_architect : REQUEST join
   | payload: — | rank=2 role=<role> specialization=<предложенная> motivo=<одна строка>
   ```
4. Агент создаёт свои сущности немедленно со `status=pending`:
   `skynet_agent_<slug>` + `skynet_inbox_<slug>` (см. §5), чтобы с ним можно
   было общаться до одобрения.
5. Координатор проверяет: уникальность slug, соответствие ранга политике,
   согласованность специализации; отвечает одним из:
   - `APPROVED <rank> <role> <specialization>` (может скорректировать роль/ранг);
   - `ADJUST <что изменить>` (нужна перезаявка);
   - `REJECTED <причина>`.
6. При `APPROVED` агент ставит `status=active`, обновляет heartbeat и получает
   **первое назначение** от координатора (§14) или `NOTIFY "await tasks"`.

## 12. Возобновление (агент уже зарегистрирован)

Агент найден в реестре → **без онбординга**, по состоянию:

- **Тот же session_id** → «я продолжаю сессию»: обновить heartbeat, обработать
  почту (§6), продолжить незакрытые `TASK` из своего ящика.
- **Другой session_id** → «я после рестарта»: выполнить восстановление (§7),
  обновить session_id/heartbeat/status, **переподтвердить** незакрытые задачи
  (координатор может переназначить, если задача была у другой сессии).
- **status=pending** → «заявка в процессе»: ждать решения координатора,
  отвечать на `QUESTION`/`ADJUST`.
- **stale/offline** → перерегистрация: пометить себя `active`, сообщить
  координатору `NOTIFY "resumed after stale"`.

## 13. Обязанности координатора (главного архитектора)

- Принимать заявки (§11), вести roster в `skynet_registry`.
- Назначать задачи (§14), отслеживать их жизненный цикл.
- Разрешать конфликты и эскалации (§16), выдавать claims (§15).
- Поддерживать «ситуационную доску»: сводка в `skynet_registry`
  (кто занят, какие задачи открыты, что слито).
- Валидировать специализацию/ранги (owner-политика).
- Работать как оркестратор по SKILL `skynet/orchestrator-kaizen.md`
  (Scrum-каркас + Kaizen): декомпозиция, module-locks, Sprint Goal,
  DoD, rollback-протокол, самомониторинг. Координатор НЕ занимается
  исполнением обычных задач — только координация, менеджмент и
  анализ процессов (принципы SKILL §1).

## 14. Задачи (task-менеджмент, Kanban-поток v2.16)

Сущность `skynet_tasks` — доска задач (наблюдения = задачи). Формат записи:

```
TASK-<n>: <краткое описание> | status=<new|ready|in_progress|review|done|rejected|cancelled>
| assignee=<slug> | priority=<P0..P5> | depends_on=<TASK-x,...> | ref=<ветка@коммит|PR>
| issued_by=<slug> | issued_at=<ts>
| started_at=<ts> | finished_at=<ts> | cycle_ms=<мс> | type=<bugfix|feature|refactor|docs|infra>
| wsjf=<число> | column=<backlog|ready|in_progress|review|done>
```

**Kanban-колонки и WIP-лимиты** (решение владельца 2026-09-23):

| Колонка | Статусы | WIP-лимит |
|---|---|---|
| backlog | `new` | — |
| ready | `ready` | — |
| in_progress | `in_progress` | ≤ 3 (= busy, протокол §25a) |
| review | `review` | ≤ 2 (доменные REV: очереди) |
| done | `done` | — |

**Pull-модель:** агент берёт следующую задачу из колонки `ready` при свободном
слоте (координатор НЕ толкает каждую задачу письмом). Порядок выбора — по
`wsjf=` (выше = раньше; при отсутствии — по приоритету P0..P5). При взятии —
`status=in_progress` + `started_at=<ts>`.

Жизненный цикл задачи (pull):

```
backlog ──(готово к работе)──▶ ready ──(агент взял, слот свободен)──▶ in_progress
   in_progress ──REPORT──▶ review ──approve──▶ done
                              └── needs-work ─▶ ready/in_progress
```

- Координатор создаёт задачу (`TASK` письмо + запись на доске `TASK-n`,
  `column=backlog`); когда задача готова к выполнению (DoR выполнен:
  критерии приёмки, приоритет, зависимости) — `status=ready`.
- Исполнитель при свободном слоте берёт `ready`-задачу: `ACK` письмом +
  `status=in_progress`, `started_at`, `assignee`.
- Сдача: `REPORT` с `ref=` (ветка/коммит/PR) → `status=review` → координатор
  ревьюит/мержит → `done` (`finished_at`, `cycle_ms` считает оркестратор).
- **Flow-метрики**: cycle time = finished_at − started_at (по типам работ);
  throughput = число done за период; прогноз следующей задачи — медиана+P85
  исторического cycle-time (SLE). Узкие места видны по заполнению колонок
  против лимитов (очередь review/ci).
- Незакрытые задачи (без `done`/`cancelled`) видны всем и переживают рестарт
  агентов (см. §7/§12).

Объёмные спецификации — файлом: `<repo>/skynet/tasks/TASK-<n>.md` (если задача
долговечная и должна попасть в историю) или `${SKYNET_ROOT}/.skynet/tasks/TASK-<n>.md`
(э-фемерное). Ссылка кладётся в `payload:`.

## 15. Claims (области работы)

Чтобы два агента не редактировали одни файлы:

- Агент берёт claim: наблюдение `claim=<область>|<ts>` в `skynet_registry`
  (или `skynet_tasks` в записи задачи), например `claim=tests/ut/cursor`.
- Правило: одна область = один агент. При конфликте — договориться или
  эскалировать координатору.
- Освобождение: `claim=<область>=<released>|<ts>` при сдаче задачи.
- Координатор может аннулировать claim (`NOTIFY` владельцу).

Рекомендуемые области: `src/`, `mdbx++/`, `tests/ut/*`, `tests/issues/`,
`tests/framework/`, `cmake/`, `.github/`, `docs/`, `skynet/`.

## 16. Конфликты и эскалация

- **Разные реализации одного исправления** → оба агента приостанавливаются,
  координатор выбирает (или просит owner), выбранная версия мержится,
  вторая закрывается `REJECTED` с пояснением.
- **Блокировка** (агент не может двигаться) → `QUESTION escalate` координатору
  с формулировкой проблемы; координатор отвечает в течение разумного времени
  или передаёт owner.
- **Рассинхронизация памяти/git** → процедура §7 + сверка `last_ref`.

## 17. Гигиена почты и идемпотентность

- Обработанное письмо помечается `[done <ts>]` в конце исходного наблюдения
  (не удалять — история полезна для восстановления).
- `msg_id` уникален и используется для идемпотентности: повторно не обрабатывать
  письма с уже известным `msg_id`.
- Пространства `msg_id` инфраструктурных демонов (детерминированные, от event-id):
  `notify-<src>-<type>-<eventid>` — notify-daemon (TASK-38), события
  GitHub/SourceCraft; `bg-<job>-<launch_ts>` — run-bg-notify (TASK-39).
  Парсеры/диджест учитывают их наравне с `mail-*` (идемпотентность по msg_id).
- При большой переписке старые письма (старше недели) координатор архивирует:
  переносит текст в файл `${SKYNET_ROOT}/.skynet/mail-archive/<date>.md`
  и заменяет наблюдение пометкой `[archived <файл>]`.

## 18. Bootstrap-чеклист сессии

Каждый агент при старте выполняет по порядку:

1. Прочитать `AGENT-WORKSPACE.md` и `skynet/skynet-protocol.md` (правила + версия).
2. Прочитать `skynet` и `skynet_registry` (версия протокола, roster, stale-правило).
3. Определить собственное состояние (§10): новый / продолжаю / рестарт / pending.
4. Выполнить онбординг (§11) или возобновление (§12).
5. Сгенерировать новый `session_id`, обновить `session_id`, `heartbeat`, `status`,
   `last_ref` в `skynet_agent_<slug>`.
6. Обработать почту (`skynet_inbox_<slug>`): ответить на `TASK`/`QUESTION`,
   переподтвердить незакрытые задачи.
7. Сообщить координатору `NOTIFY "ready <slug> session=<id>"` и взять следующую
   задачу с доски `skynet_tasks` или ждать назначения.

## 19. Осведомлённость роя (обязательные уведомления координатору)

Координатор отвечает за распределение задач, разрешение конфликтов и эскалацию.
Чтобы он мог работать с актуальной картиной, **каждый агент обязан**:

1. **HEARTBEAT письмо** в `skynet_inbox_main_architect` не реже:
   - каждых **5 минут** при активной работе (busy),
   - каждых **15 минут** в простое (idle),
   - всегда при смене статуса и в конце сессии.
   Формат:
   ```
   [mail-<seq>-<slug>-main_architect|<ts>] <slug> -> main_architect : HEARTBEAT status=<state> task=<TASK-n|—> | payload: ref=<branch@commit> | <однострочный прогресс>
   ```
   Письмо считается также обновлением heartbeat (см. §4). Дублировать запись
   в `skynet_agent_<slug>` всё равно нужно — это локальная копия состояния.

2. **Событийные уведомления** (`NOTIFY`/`REPORT`/`QUESTION`) во всех случаях,
   когда состояние меняется содержательно:
   - взял задачу из `ready` (`ACK TASK-n`, status=in_progress),
   - начал/завершил работу (status=busy/idle, `REPORT`),
   - блокировка, вопрос, эскалация (`QUESTION escalate`),
   - готовность к новому назначению (`NOTIFY ready`).

3. **Идемпотентность**: HEARTBEAT-письма уникальны по `msg_id`; обработка
   сводок не должна порождать новых задач без причины.

Обязанности координатора по осведомлённости:

- Периодически (в начале сессии, при простое и после уведомлений) читать
  `skynet_registry` + `skynet_tasks`, вести сводку «кто занят / что открыто».
- Помечать stale-агентов (правило §4) и, при необходимости, переназначать их
  незакрытые задачи, уведомляя нового исполнителя.
- Менять допустимые интервалы heartbeat (своим решением) для конкретного
  агента или задачи: наблюдение `heartbeat_interval=<мин>|<ts>|<причина>`
  в `skynet_agent_<slug>` или записи задачи.
- При долгом отсутствии уведомлений от координатора агенты продолжают работу
  по последним назначениям (протокол рассчитан на асинхронность), но обязаны
  раз в 30 минут удостоверяться, что их задача не была переназначена
  (сверка `skynet_tasks`).

## 20. Очередь ожиданий и дисциплина ответов

Чтобы ни один запрос агента не «зависал», координатор ведёт **очередь ожиданий**
(observation-записи в `skynet_registry`, префикс `wait=`):

```
wait=<slug>: <предмет> | state=pending_review|awaiting_answer|in_progress
| since=<ts> | expect=<REVIEW|MERGED|ANSWERED>
```

Правила:

1. Агент, отправляющий `REQUEST`/`QUESTION`/`REPORT`, добавляет запись в очередь
   ожиданий (или просит координатора внести). Появившаяся запись `wait=` —
   сигнал координатору отвечать.
2. Координатор отвечает явным типом (§6.1a) и **закрывает** запись:
   `wait=<slug>: ... =<closed>|<ts>|<итог>`.
3. Координатор обязан проверять очередь ожиданий при каждом старте сессии,
   после каждого события и не реже раза в 10 минут.
4. Норматив ответа: `ANSWERED`/`ACK` на `QUESTION`/`REQUEST` — в течение 15 минут;
   `REVIEW`/`MERGED` на `REPORT` — в течение 30 минут (или явное
   `NOTIFY "review in progress, ETA=..."`).
5. Просроченная запись (без ответа сверх норматива) — агент правомерно эскалирует
   (`QUESTION escalate`) или повторяет запрос; координатор отвечает в приоритетном
   порядке. Сверка очереди — критерий готовности ответа координатора.
6. Агент при получении решения подтверждает `ACK` и помечает письмо `[done]`;
   без ACK координатор считает решение недоставленным и дублирует.
7. **Read-receipt**: на каждое `REQUEST`/`QUESTION` координатор отвечает
   `ACK <ETA>` или `ANSWERED`; отсутствие такого ответа в пределах норматива
   даёт агенту право эскалировать или действовать по последнему решению
   (отправитель не должен гадать «прочитано или потеряно»).
8. **Координатор — тоже агент**: он обязан вести собственный `session_id`,
   `heartbeat`, `status` в `skynet_agent_main_architect` под тем же stale-правилом
   (§4), обновлять доску `skynet_tasks` при каждом мерже/решении и закрывать
   записи `wait=`; иначе его молчание трактуется как stale так же, как у любого
   другого члена роя.
9. **Не блокируйся**: агент, отправивший `REQUEST`/`QUESTION`/`REPORT`,
   НЕ останавливается в ожидании ответа. Он продолжает работу по последнему
   действующему решению/рулингу и в очередном `HEARTBEAT`/`REPORT` указывает
   «awaiting reply on <msg_id>, continuing». Остановка допустима только если
   нет ни одного применимого решения И нет следующего осмысленного шага —
   тогда эскалация (`QUESTION escalate`) с формулировкой. Read-receipt
(п.7) — подтверждение, что письмо не потеряно; координатор обязан
    отвечать в пределах SLO.

## 21. Дежурный оркестратор (duty daemon)

Интерактивная сессия координатора не может «проснуться» сама (нет push).
Чтобы рою не приходилось ждать, на машине работает **дежурный оркестратор**:
`${SKYNET_ROOT}/.skynet/orchestrator.py` (вне git).

> **Критично (архитектура v2.15):** общая память — **libmdbx `graph.mdbx`**
> (ACID, канон; legacy JSONL только для старых сессий, см. `memory-codex.md`).
> Единственный писатель — `memory-mdbx-server.py` (через MCP `mcp.memory`).
> Внешние процессы НЕ пишут в БД напрямую. Оркестратор **только читает**
> память через `memory_reader.py` (merge mdbx+legacy), а своё состояние ведёт
> в собственных файлах (`orchestrator-state.json`, `duty.log`). Любое изменение
> памяти агенты выполняют через свой MCP-сервер.

Оркестратор берёт на себя рутину координатора без принятия дизайн-решений:

- **Локальный duty-лог**: heartbeat дежурного режима в `.skynet/duty.log`
  (в общую память НЕ пишется; интерактивный координатор обновляет свой
  heartbeat сам при старте сессии).
- **Сводка активности**: `last_seen=<slug>=<ts>` ведётся в
  `orchestrator-state.json` (не в памяти).
- **Digest**: рендерит `${SKYNET_ROOT}/.skynet/main_architect/ACTION-NEEDED.md`
  (письма, требующие человека; просроченные `wait=`; stale-агенты), шлёт
  `notify-send`/beep при изменении.
- **Очередь ожиданий**: отслеживает `wait=` записи и помечает просроченные
  (SLO 15/30 мин).

Правила:

- Интерактивный координатор при старте сессии и после каждого события обязан
  читать `ACTION-NEEDED.md` и закрывать перечисленное (ответить, отметить `[done]`,
  закрыть `wait=`), обновляя доску.
- Оркестратор НЕ принимает решения и НЕ пишет в память: ревью, мержи, рулинги,
  receipts — только человек/главный архитектор в интерактивной сессии.
- Read-receipt заменяется правилом «не блокируйся» (§20.9): отправитель не
  останавливается и видит себя в digest'е, если ответа нет в пределах SLO.

## 21a. SLA доставки и ответов (E3, v2.17)

> Формализация эпика E3 «Контракты SLA + владелец процесса "здоровье роя"».
> Цель: сделать координацию измеримой и предсказуемой (циклы «5 почему» №6–7).
> Health-first: механический сбой чинится немедленно, SLO нарушается только
> по эскалации. Владелец процесса «здоровье роя» — **координатор** (main_architect).

### Обязательства (константы в `.skynet/orchestrator.py`)

| Соглашение | Значение | Что измеряет | Нарушение → |
|---|---|---|---|
| `SLO_ANSWER` | 15 мин | ответ координатора на REQUEST/QUESTION/эскалацию | эскалация владельцу + digest |
| `SLO_REVIEW` | 30 мин | вердикт ревьюера на REV:* запрос | re-wake ревьюера, digest |
| `STALE_MIN` | 30 мин | письмо без `[done]` И нет heartbeat = залипла сессия | fresh boot / drop session |
| `ACTIVE_TASK_STALE_MIN` | 30 мин | задача `in_progress`, но heartbeat агента старше = застрял (B44) | авто-wake busy-агента |
| `WOKE_MIN` | 10 мин | мин. интервал между headless wake одного агента | — (анти-шторм) |
| `MAX_BUSY` | 4 | параллельных headless-инстансов (3→4, владелец 2026-09-23) | defer wake (пул полон) |
| READ-receipt | §20.9 | отправитель НЕ блокируется, видит себя в digest | эскалация при просрочке |

### Правила

1. Доставка письма отправитель→получатель: получатель обязан ACK/обработать в
   пределах SLO; иначе письмо попадает в `ACTION-NEEDED.md` (digest координатора)
   и получатель будет разбужен снова.
2. Измерения — `health.json` (оркестратор, каждые 5 мин): pending/возраст писем,
   last_activity, dead-sessions, busy, CI. Человекочитаемый вид — `tools/health-report.py`.
3. Метрика здоровья роя (E8): залипшие=0; координация <3% времени; доставка→ACK
   медиана ≤10 мин, P90 ≤30 мин; автотриггер >60 мин. Baseline reset 2026-09-22T12:15Z.
4. Владелец процесса «здоровье роя» — координатор: следит за метриками в
   медитации, инициирует kaizen при деградации, эскалирует владельцу структурные.
5. Пересмотр констант — по факту, через BACKLOG/kaizen, не ad-hoc.
6. **Батчинг (E5, экономика координации)**: письма координации ACK/подтверждения
   отправлять ГРУППАМИ (один REPORT за wake, а не N писем), вердикты ревьюеров —
   без обязательного ACK от получателя (достаточно digest). Цель — снизить долю
   координационных писем с ~89% (замер 2026-09-23, 194 письма/день) к <50%:
   каждое письмо = лишний wake-цикл. Исключения — эскалации, REV:* запросы,
   важные вехи задачи.

## 23. Ожидание почты (waitmail, v2.5 → v2.15)

Агент в рабочем цикле вместо слепого `sleep N` использует блокирующий ждун
`${SKYNET_ROOT}/.skynet/waitmail.py`:

    python3 ${SKYNET_ROOT}/.skynet/waitmail.py <slug>

Семантика (решение владельца):

- Если в `skynet_inbox_<slug>` есть необработанные письма — немедленно печатает
  их и выходит (rc=0).
- Иначе блокирует в ядре на FIFO `.skynet/pipe/<slug>.fifo` (select) до сигнала
  от оркестратора; по сигналу сверяется с памятью: письма есть → печатает и
  выходит; ложный сигнал → продолжает ждать.
- **Таймаут по умолчанию — бесконечный**: короткие таймауты создают холостые
  пробуждения. Владелец прерывает утилиту (`Ctrl+C`, rc=130), когда нужно
  взаимодействие. `--timeout N` допустим только при осознанной необходимости.
- Оркестратор шлёт сигнал при появлении новых писем (и пишет `.skynet/wakeup.txt`).
- FIFO-сигнал — лишь ускоритель; корректность всегда обеспечивается памятью.

Backend чтения (v2.15, 2026-09-23):

- По умолчанию `--backend auto` — читает **каноническую память через
  `memory_reader.py`** (merge graph.mdbx + legacy JSONL). Это обязательный режим
  для всех агентов: письма агентов пишутся в mdbx.
- `--backend jsonl --memory <file>` — только для тестов/diagnostics (plain
  JSONL), НЕ для рабочего цикла.
- **PID-файл**: пока waitmail ждёт, он пишет `.skynet/pipe/<slug>.pid`.
  Владелец вызывает координатора извне: `kill -INT $(cat .../0.coordinator.pid)`
  → rc=130 (OWNER-CALL). PID-файл удаляется при выходе.
- Сельфтест: `python3 .skynet/selftest-waitmail.py` (6/6).

Ожидание «без блокировки роя»: пока агент ждёт в waitmail, он не тратит токены;
правило «не блокируйся» (§20.9) применяется к отсутствию следующего шага работы,
а не к самому ожиданию почты в цикле.

## 24. Командная инстанция и дежурный цикл координатора (v2.6 → v2.15)

- **Команды и решения агенту даёт КООРДИНАТОР** (`main_architect`), а не
  владелец. Владелец не участвует в рутине и не даёт команды по задачам.
  Его участие — только эскалация (приоритеты, конфликты, смена специализации,
  `QUESTION escalate`).
- Координатор держит **event-driven loop** (решение владельца 2026-09-23):
  один шаг цикла = `.skynet/coordinator-step.sh`:

      .skynet/coordinator-step.sh [slug] [-- WAIT]

    - вызывает `waitmail.py <slug> --timeout <WAIT>` (WAIT≈540с, всегда меньше
      таймаута внешнего tool-вызова),
    - печатает явный статус и пишет `.skynet/<slug>/event-loop.log`,
    - возвращает rc: **0=MAIL** (письма напечатаны), **130=OWNER-CALL**
      (владелец прервал SIGINT, его директива — в сессии), **1=NO-MAIL**
      (сердцебиение без писем).

  Логика координатора: rc==0 → обработать всю почту (ответить, отревьюить,
  смёржить, закрыть `wait=`, обновить доску, раздать задачи) → «в начало
  цикла»; rc==130 → прочитать директиву владельца, ответить → «в начало»;
  rc==1 → **Improvement Tick** (продуктивная пауза: gemba-обход состояния
  агентов, health-first починка дефекта цикла, один кайдзен-элемент из
  «50 почему», сверка с планом/целями — см. SKILL медитации) → «в начало».
  Владелец вызывает координатора в любой момент:
  `kill -INT $(cat .skynet/pipe/0.coordinator.pid)` → rc=130.
- **Живой Kanban-дашборд**: пока waitmail ждёт, каждые `COORDINATOR_BOARD_INTERVAL`
  (default 60с) доска задач перерисовывается (`tools/tasks.py`, колонки/WIP +
  кто чем занят). Рендер ВКЛЮЧЁН по умолчанию (живая консоль); выключить —
  `BOARD_SILENT=1` (headless/logged). При TTY — in-place (ANSI), иначе — с
  разделителями. `coordinator-step.sh` циклит: рендер → waitmail(интервал) →
  ... до MAIL/OWNER-CALL/бюджета.
- **Команды владельца «медитируй» / «помедитируй»** = переход в этот режим
  (event-driven loop). Координатор НЕ «ждёт промпт» — он вызывает
  `coordinator-step.sh` и блокирует в waitmail. Подробный навык:
  `skills/orchestrator/meditation/SKILL.md`.
- Агенты: запросы/отчёты — письмами координатору; ожидание ответа — через
  собственный `waitmail <slug>`; при просрочке SLO — `QUESTION escalate`,
  но НЕ прямое обращение к владельцу. Назначенные задачи — авторитетны,
  начинать сразу, отчитываться `REPORT`.

## 25. Headless-пробуждение сессий (v2.7) + планировщик ёмкости (v2.11)

Сессии агентов запускаются через `src code` (`src code -- -c` — последняя,
`src code -- -s <ses_id>` — конкретная). Завершённая/спящая сессия не
прочитает письмо сама; её возобновляет **оркестратор**:

- При наличии непрочитанных писем у агента оркестратор выполняет
  `.skynet/wakeup-headless.sh <slug> [ses_id]`: внутри `nook-<slug>` запускается
  `src code -- run --dangerously-skip-permissions [-s <ses_id>] "обработай почту..."`.
  Агент просыпается, читает ящик, отвечает координатору, продолжает задачи.
- Сессии агентов: реальные opencode `ses_...` смотрятся через
  `src code -- session list`; маппинг slug→ses_id ведётся в
  `.skynet/sessions.json` (обновляет координатор). Без ses_id — свежая сессия
  в nook. НЕ использовать голый `-c` (он продолжает глобально последнюю сессию).
- Флаг `--dangerously-skip-permissions` обязателен для headless (иначе агент
  «auto-rejects» инструменты и падает); v1.4.x не имеет `--auto`.
- Cooldown: не чаще раза в 10 минут на агента (state-файл), чтобы не спамить.
- `main_architect` (интерактивная сессия координатора/владельца) НЕ будится
  headless автоматически — во избежание конфликтов двух координаторов.
- Ограничение: `src code` требует инсталляции управляемого opencode
  (`~/.config/sourcecraft/bin/opencode`, версия v1.4.x); сторонний CLI beta
  НЕ использовать (ошибка провайдера `prompt_cache_key`).

### 25a. Планировщик ёмкости (v2.11, одобрено владельцем 2026-09-21)

Ограниченные ресурсы хоста (4 vCPU / 15 GiB) фиксируются как **жёсткий пул
одновременных работающих (busy) headless-инстанций**:

- `MAX_BUSY = 4` — одновременно работают не более четырёх busy-инстанций
  (было 3; владелец 2026-09-23: +1 агент). Интерактивный координатор вне пула.
  Значение хранится в `.skynet/orchestrator.py` (`MAX_BUSY`) и показывается
  в ACTION-NEEDED.
- Оркестратор при каждой волне: считает активные headless-процессы
  (`pgrep wakeup-headless.sh` + `opencode run --dangerously-skip-permissions`),
  сортирует кандидатов по приоритету задачи (P0 > P1 > P2, из `skynet_tasks`),
  будит до заполнения пула; остальные остаются в очереди (defer, сессия НЕ
  создаётся). Это устраняет лавину одноразовых сессий.
- **Гейт пробуждения — только память** (владелец 2026-09-23): load-average-гейт
  УБРАН — медленная обратная связь-осциллятор: сборки/тесты поднимают load и
  вытесняют агентов, после завершения load снижается медленно → потеря времени.
  Сборки уже идут под `nice`, запас ОЗУ есть, MAX_BUSY ограничивает конкуренцию.
  Единственный предохранитель — `mem > 90%` (риск OOM/свопов).
- Запрещено запускать вторую инстанцию одной роли, пока первая busy.

### 25b. Каноническая сессия на роль и авто-захват ses_id (v2.11)

Модель: **роль → инстанции → канонический ses_id** (кратность K≤3):

- Рабочие песочницы — **пул из 5 общих nook** `nook-pool-1..5` (owner-approved
  2026-09-21). Роль НЕ привязана к фиксированному каталогу: оркестратор
  назначает свободный nook из пула (`nook_map` в state-файле) и переключает его
  на ветку роли (`prepare_pool_nook`) перед wake. См. `orchestrator-kaizen.md`
  §swarm-management. Дисковая экономия — hardlink-шеринг `.git`.
- **Изоляция работы агента**: nook-pool-N — ОБЩИЙ и пересбрасывается
  оркестратором между wake (`prepare_pool_nook` делает fetch+checkout). Поэтому:
  (1) агент НЕ должен держать незакоммиченную работу в рабочем дереве пула —
  она будет потеряна; (2) для длительной работы (задачи > одного wake, ветки,
  документы) использовать **изолированный worktree** `${SKYNET_ROOT}/.skynet/tmp/<slug>/<task>-wt`
  (`git worktree add <путь> -b feature/<task> origin/devel`), оттуда коммитить и
  пушить инкрементально; (3) никогда не править чужие ветки/рабочее дерево пула
  (инцидент 2026-09-23: B.tester stash'ил правку B51 поверх чужой ветки
  task36-c1-relocate в nook-pool-1).
- Канонический ses_id роли хранится в `.skynet/sessions.json`
  (`{ "<slug>": "ses_..." }`). Пишет его только планировщик/координатор
  (с файловой атомарной заменой), агенты напрямую не правят этот файл.
- Авто-захват: если свежая сессия была запущена без ses_id, оркестратор на
  следующем такте находит новую top-level сессию этого nook в `opencode.db`
  (`parent_id IS NULL`, `directory = nook-<slug>`, `time_created >= launch`)
  и записывает её как каноническую. Последующие wake идут строго через `-s`.
- Агент может зеркалить реальный id как наблюдение
  `opencode_session_id=ses_...` в своём `skynet_agent_<slug>` — оркестратор
  учитывает его как fallback (помимо `session_id=<uuid>` из §4).
- Мёртвая/удалённая каноническая сессия (отсутствует в `opencode.db`) →
  секция DEAD в ACTION-NEEDED; следующий wake пересоздаёт и перезахватывает id.
- Мониторинг churn: число top-level сессий на nook показывается в ACTION-NEEDED
  (>25 — предупреждение), рост без смены канонической означает регресс.

## 27. Контракт локальной валидации (v2.9)

Кайдзен: агенты **не дублируют** сборки/прогоны друг друга и координатора;
каждый сдаёт в работу только локально проверенный результат.

- Перед `REPORT`/запросом на мерж агент обязан сам собрать и прогнать
  релевантные тесты (по сегментированной шкале P0–P4 из AGENTS.md).
- Отчёт обязан содержать **матрицу валидации**: компиляторы/конфигурации,
  команды (build/ctest), число пройденных/упавших тестов, скорость.
  Формат: `VALIDATED: gcc Release P1 47/47; clang Debug P1 47/47; asan P1 47/47`.
- Координатор **не пересобирает и не перегоняет** результат повторно, если
  матрица полная и непротиворечивая: мержит на основании матрицы агента +
  кода. Повторная локальная проверка координатором — только при отсутствии
  матрицы, подозрительных данных или изменении ядра (src/) с тонким покрытием.
- Кросс-платформенные риски гасит CI; избирательный запуск GitHub CI — по
  обоснованию (существенная причина), не для рутинных коммитов.

## 30. Бэкпорт фиксов в стабильные ветки (v2.10)

Постоянный процесс: исправления багов, найденные на devel, при необходимости
переносятся в стабильные ветки.

- Стабильные ветки сейчас: `master` и `lts/0.13`. В ближайшее время владелец
  оформит начало ветки `v0.15.x` (состав стабильных веток может измениться).
- Бэкпорт в `lts/0.13` может быть очень трудным, невозможным или ненужным —
  каждый случай оценивается отдельно.
- **Критерий решения — точечный тест с конкретным API** (самый простой и быстрый):
  1. Тест **проходит** → бэкпорт не нужен (бага в этой ветке нет либо уже покрыта).
  2. Тест **собирается, но падает** → точно нужно бэкпортировать и/или исправлять
     отдельно/дополнительно в этой ветке.
  3. Тест **не собирается** → разобраться, почему: возможно, такого API в стабильной
     ветке ещё не было, или есть более существенные проблемы; при неоднозначности —
     **спросить владельца**.
- Бэкпорты готовятся на локальных ветках (local-origin) от соответствующей
  стабильной ветки и публикуются по правилам публикации (§1/§28), не в рамках
  freeze devel.

## 30a. Подпись внешних коммуникаций (v2.16a, владелец 2026-09-23)

Правило для комментариев роя в публичных каналах (GitHub issues/PR, sourcecraft
и т.п.), где нас читают люди вне роя:

- **Первый ответ** в теме/треде всегда начинается с представления: кто пишет
  и от чьего имени. Пример: «Привет! Это skynet — координатор роя ИИ-агентов
  проекта libmdbx» / на англ. «Hi! This is skynet, the coordinator of the
  libmdbx AI-agent swarm».
- **Последующие ответы** в той же теме — короткая подпись «skynet here»
  (или эквивалент на языке тредa), чтобы читатель сразу видел авторство.
- Цель (владелец): хорошие технически комментарии роя не должны путать людей —
  авторство должно быть очевидно с первого слова.
