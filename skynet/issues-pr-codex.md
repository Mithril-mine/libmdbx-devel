# issues-pr-codex — Workflow Issues/PR/Discussions/CI (GitHub + SourceCraft)

> Адаптация черновика владельца (2026-09-22) к реальности роя **skynet /
> Concordia Intellectuum**. Применяется ко ВСЕМ внешним коммуникациям и к
> обработке событий пользователей (issues, PR, discussions, CI).
> Связано: `changelog-codex.md`, `news-codex.md` (TASK-33), протокол §27/§30,
> TASK-38 (notify-daemon).

## 0. Принципы внешних коммуникаций (обязательно, всегда)

1. **Язык пользователя.** Отвечать на языке собеседника; если язык нельзя
   определить — по-русски.
2. **Идентичность.** Представляться честно: «Это **skynet** — рой ИИ-агентов,
   работающий вместе с владельцем проекта (союз Concordia Intellectuum). Я
   действую от имени владельца в интересах libmdbx.» Не раскрывать внутренние
   роли агентов, процессы роя, оркестрацию, метрики эффективности команды.
3. **Разглашение информации** (обязательно во всех коммуникациях вне домена
   skynet):
   - МОЖНО: открытые коммиты/релизы/PR/issues (ссылками), улучшения UX/API,
     багфиксы с симптомами, рост покрытия тестами, общие направления улучшений
     роя («повышена стабильность оркестрации», «сокращено время планирования»),
     синергия («автоматизирована генерация тестов», «рой провёл классификацию
     тикетов») — без деталей реализации.
   - НЕЛЬЗЯ: внутренние репозитории/CI/CD/доступы/ключи/токены, фрагменты кода/
     логи/дампы/конфиги из закрытых частей, проприетарные алгоритмы/эвристики,
     персональные данные/роли/должности/контакты, внутренние обсуждения по
     тикетам, финансовые/коммерческие метрики, планы монетизации.
4. **Взял в работу — веди до конца.** Каждое обещание в комментарии (фикс,
   отчёт, апдейт) должно быть выполнено; по завершении — финальный отчёт в
   том же треде.
5. **Оперативность.** На P0-багрепорт реагировать немедленно: первый отклик —
   минуты, не часы. Демонстрировать скорость и качество.

## 1. Поток событий в нашей системе (как это работает у нас)

- **Вход событий:** GitHub REST (поллинг ~60с, **TASK-38 notify-daemon**) и
  SourceCraft (`src` CLI/API). Webhook'ов с публичным ingress у нас нет —
  используем поллинг + watermark-идемпотентность (см. TASK-38).
- **Event bus = почтовые ящики** (`skynet_inbox_*`): notify-daemon пишет события
  в `skynet_inbox_main_architect`; **координатор — роутер**: триаж, приоритеты,
  назначение агентов, контроль исполнения.
- **Триггеры** (в порядке важности): P0/P1 bug-issue → немедленно (секция 2);
  новый/обновлённый PR от внешнего контрибьютора → ревью; CI failure на
  devel/master → диагностика (секция 6); discussions → категоризация (секция 5);
  утренний дайджест — в `ACTION-NEEDED` (секция 8).

## 2. Быстрое реагирование на bug-report (сценарий «показать скорость и качество»)

Протокол, выведенный из опыта issue #47 (2026-09-22):

```
Вход: новый bug-report (issue/комментарий)
↓
1. Прочитать полностью (Summary/Environment/Repro/Анализ).
2. Реакция 👀 (eyes) на текст issue = «смотрю».
3. Ответ пользователю (на его языке), минимально-достаточный:
   - представиться как skynet/Concordia Intellectuum, действую от имени
     владельца;
   - поблагодарить за баг-репорт (особенно если есть repro/анализ);
   - сообщить: берём в работу как <приоритет>, назвать главную угрозу
     (данные/коррапт/краш/платформа);
   - краткий план (репро → фикс → CI → мерж → бэкпорт → ChangeLog → отчёт).
4. Назначить issue на владельца (erthink) — «self-assign» от его имени.
5. Анализ-гейт (Gemba): проверить в коде указанные места; подтвердить дефекты
   (или опровергнуть с пояснением). Если дефект → задача уровня P0/P1.
6. Создать TASK (spec: суть, ссылки на код, план воркфлоу, критерии готовности),
   назначить агента (обычно tests_worker), приоритет — выше остальных.
7. Сменить реакцию 👀 → 🚀 (в работе). Оставить feedback-комментарий
   («берём в работу»), если нужно уточнить — спросить коротко.
8. Фикс: ветка `fix/<issue-slug>` от devel → локальная валидация (матрица
   §27) → CI (веха; на Windows-дефекты обязателен Windows-прогон) → PR.
9. После зелёного CI: мерж devel → master → бэкпорт stable/lts (§30) →
   **ChangeLog по changelog-codex.md** на каждой линии.
10. Финальный отчёт в issue: что исправлено, где (commit/PR), как проверено,
    куда бэкпортировано. Закрыть issue (если fix merged).
↓
Дополнительно: при follow-up'ах пользователя отвечать быстро (мин.), признавать
уточнения (например «MDBX_EXCLUSIVE — workaround, не фикс»), не защищаться
вслепую.
```

**Правила ведения диалога:** тон профессиональный, благодарить за качественные
репорты; не обещать больше, чем можем; держать язык пользователя; снимать
устаревшие реакции; не «сливать» внутренний процесс.

## 3. Issues: триаж и lifecycle (адаптация)

- Триаж: классификация (bug/feature/question/docs), приоритет P0–P3, компонент;
  проверка дубликатов (поиск по открытым) → комментарий-ссылка.
- bug → взять в работу по секции 2; feature → уточнить use case, оценить
  альтернативы; question → ответ по документации; docs → предложить правки.
- Назначение: по CODEOWNERS/истории; комментарий-предложение.
- Stale: >7 дней без ответа → вопрос «актуально ли?»; >14 → закрыть с пояснением.
- Связка issue↔PR: авто-комментарий `Closes #N` при открытии PR, проверка.
- Эскалация: P0 без assignee >4ч → поднять руку координатору/владельцу.

## 4. Pull Requests (адаптация)

- Ревью при открытии/обновлении: diff, целевая ветка, связанные issues,
  CI-статус. Блоки: 🔴 Blocking / 🟡 Suggestions / 🟢 Positive. Метки
  needs-changes / ready-for-review.
- Проверки: стиль/линтеры, размер диффа (>500 строк → предложить разбить),
  тесты, секреты/безопасность, связь с issue, документация (при изменении API).
- Обновления PR: повторный анализ нового диффа, снятие needs-changes после
  закрытия блокеров; конфликты — инструкция по разрешению.
- **Мёрдж-протокол у нас:** внутренняя работа мержится через local-origin →
  devel (после ревью и локальной валидации §27); на GitHub (публичный репо)
  пушим после согласования, PR от внешних контрибьюторов — ревьюим на GitHub,
  CI обязателен, squash+merge. Branch protection соблюдать.
- CI на GitHub — только вехи/блокеры (квота); рутинные прогоны не плодить.

## 5. Discussions

- Категории: Q&A → ответ по коду/документации; Idea → связать с issues,
  оценить влияние; Show&Tell → позитив + предложить в документацию;
  RFC/Proposal → структурированный анализ (плюсы/минусы/альтернативы).
- Без ответа >48ч → предложить ответственным; закрытые с новыми комментариями
  → оценить reopen/перенос в issue.

## 6. CI-модуль (адаптация; интеграция с существующим)

- Оркестратор уже поллит GitHub Actions (poll_ci_status, группировка по headSha,
  health.json). TASK-38 расширит до событий + уведомлений.
- Failure → диагностика: какой job, категория (compile/test/lint/infra/deps),
  связь с коммитом, история (flaky?).
- Известные флайки: macos `smoke_fault` timeout на Release-раннерах, ARM64
  `smoke_t1_hill`/`smoke_sp_nested` (TASK-31) — НЕ перезапускать вслепую:
  классифицировать, исключать/чинить адресно.
- Эскалация: main/devel красный >15 мин → координатор; 3+ падений одного теста
  за неделю → issue с меткой flaky.

## 7. Кросс-платформа GitHub ↔ SourceCraft

- У нас: `upstream` = SourceCraft, `github` = зеркало, `origin` = local-origin.
  Публикация наружу — по правилам AGENT-WORKSPACE (devel→master→stable→lts,
  push только после локальной валидации).
- Issues/PR: статусы зеркалировать; PR связывать reference'ом
  («Mirrors GitHub PR #N»); discussions внешние — на GitHub, внутренние — в skynet.

## 8. Уведомления и дайджесты

- Немедленные: P0-issue, CI red на devel/master, security-флаг, конфликт на
  критическом PR → в inbox координатора (TASK-38) + поднятая рука владельцу.
- Ежедневный дайджест (в ACTION-NEEDED): issues (новые/закрытые/в триаже),
  PR (готовы к ревью/заблокированы CI/ждут автора), discussions, CI-сводка.

## 9. Связь с ChangeLog и процессами

- Каждый устранённый публичный дефект → запись в ChangeLog по
  **changelog-codex.md** (Fixes: как проявлялось/когда; важное — Important/Breaking;
  измеряемое — Improvements) на каждой линии (dev/master/stable/lts).
- Delivery contract §27: любой REPORT/мерж несёт VALIDATED-матрицу.
- Backport §30: targeted-API-test критерий.
- CI-quota: GitHub CI только на вехах/блокерах (обосновано в комментарии PR).

## 10. Архитектура: черновик владельца vs наша реализация

| Черновик | У нас |
|---|---|
| Webhooks + Router | Поллинг (TASK-38) → почтовые ящики; координатор = router |
| PlatformClient (GitHub/SourceCraft) | `gh` CLI/REST + `src` CLI; notify-daemon — адаптер |
| Event bus | `skynet_inbox_*` + orchestrator (signal/wake) |
| CI Dashboard | `health.json` + poll_ci_status + tools/health-report.py |
| Notification Service | notify-daemon (TASK-38) + «поднятые руки» в digest |
| Merge Protocol | local-origin→devel→(ветки)→master→stable→lts; внешние PR на GitHub |
