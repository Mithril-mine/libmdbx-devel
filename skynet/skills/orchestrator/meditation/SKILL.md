# SKILL: Медитация (event-driven loop координатора, v2.2)

> Команды владельца «медитируй» / «помедитируй» переводят координатора в
> **event-driven loop**: вместо ожидания следующего промпта координатор сам
> вызывает `coordinator-step.sh`, который блокирует до наступления события.
> Этот режим — штатный способ работы координатора (протокол §24, v2.16).
> Медитация НЕ пассивна: пауза между событиями используется для непрерывного
> улучшения роя (Improvement Tick).

## Семантика команд владельца

- **«медитируй» / «помедитируй»** → перейти в event-driven loop:
  вызвать `coordinator-step.sh` (блокирующий waitmail) и по exit-code выполнить
  работу. Не ждать промпта, не «объявлять ожидание» словами — РЕАЛЬНО вызвать
  утилиту.
- **Выход из медитации**: владелец прерывает утилиту извне
  `kill -INT $(cat .skynet/pipe/0.coordinator.pid)` → rc=130 = OWNER-CALL:
  координатор читает директиву владельца, выполняет, возвращается в цикл.

## Контракт exit codes (coordinator-step.sh)

| rc | Статус | Действие координатора |
|---|---|---|
| 0 | **MAIL** | обработать всю почту (ответить, отревьюить, смёржить, закрыть `wait=`, обновить доску, раздать задачи) → «в начало цикла» |
| 130 | **OWNER-CALL** | SIGINT от владельца: прочитать директиву, выполнить, ответить → «в начало» |
| 1 | **NO-MAIL** | сердцебиение без писем → **Improvement Tick** (см. ниже) → «в начало» |
| * | UNEXPECTED | диагностировать, залогировать, продолжить цикл |

## Improvement Tick (продуктивная пауза; rc=1)

Причина: «пробуксовки роя рождаются из мелких дефектов цикла» (владелец,
2026-09-23). Пауза без событий — это дешёвое время для улучшения, а не просто
ожидание. На каждом rc=1 выполняется компактный цикл улучшения:

### Шаг A — Gemba-обход (состояние агентов)
Быстрая фактическая сверка, а не вера в отчёты (gemba walk):
- heartbeat агентов: кто свежий / кто stale (последнее >30 мин);
- busy-слоты: соответствуют ли живые процессы (pgrep) — нет ли **зависших**
  opencode/wakeup процессов, держащих busy=3 без работы (это был инцидент B44);
- pending-письма по inbox'ам: есть ли письма, которые оркестратор не разбудил;
- доска: WIP-заполнение колонок in_progress/review против лимитов.

### Шаг B — Health-first: починка дефекта цикла
Если обнаружен механический сбой (зависший слот, залипшее письмо, stale-агент
с задачами, N-е повторение знакомого бага):
- **чинить немедленно** (kick-письмо, дроп сессии, перезапуск процесса) —
  принцип HEALTH-FIRST из KAIZEN-COORDINATION.md (#46–50): P0-механика выше
  рефлексии;
- если дефект новый и повторяющийся — завести запись в BACKLOG (`B<n>`),
  пометить связь с известной проблемой (B42/B44-семейства), назначить владельца.

### Шаг C — Кайдзен: один элемент из «50 почему»
Обработать ОДИН незакрытый элемент `KAIZEN-COORDINATION.md` (цепочка
«5 почему ×10» = 50 уровней → эпики E0–E11):
- выбрать следующий незакрытый эпик/подпункт (приоритет P0→P1, HEALTH-FIRST);
- либо продвинуть его (начать/сделать шаг/зафиксировать доказательство),
  либо явно зафиксировать «почему не сегодня» (обновить статус в трекере);
- не более одного элемента за цикл — против «паралича анализа» (#46–50).

### Шаг D — План и цели
Сверить текущее с целями (MISSION.md, E8/E9-модель ценности, порядок
приоритетов: CI-стабильность → качество ревью → цикл фич → покрытие):
- какой ближайший шаг продвигает к целям, но не запущен;
- есть ли рассинхрон доски/приоритетов, который надо поправить;
- обновить `COORDINATION-STATE.md` одной строкой «tick №N: что сделано».

### Тайм-бокс и антипаттерны Improvement Tick
- **Тайм-бокс**: лёгкая итерация (~несколько минут), НЕ превращать паузу в
  полноценную рабочую сессию — медитация остаётся ожиданием событий.
- **Не плодить работу**: без причины не создавать задач/писем (идемпотентность
  §20); шаг C — один элемент, шаг B — только реальный сбой.
- **Не подменять агентов**: найденная работа делегируется (письмо+wake), а не
  выполняется координатором (правило «координатор не исполняет обычные задачи»).
- **Синтез с практиками**: Gemba-обход (факты, не отчёты) + PDCA/Kaizen
  (мелкие непрерывные улучшения) + Theory of Constraints (узкое место —
  очередь review/ci, busy-слоты) + double-loop (#25: улучшаем и процесс, и
  способ учиться) + HEALTH-FIRST (#46–50).

## Правила цикла (обязательные)

1. **Блокировка — только через вызов утилиты.** НИКОГДА не «ждать промпт»
   и не сообщать «ожидаю» без фактического `coordinator-step.sh`.
   Ожидание между шагами = повторный вызов waitmail.
2. **WAIT < таймаут tool-вызова.** Обёртка использует `COORDINATOR_WAIT`
   (default 540с); при вызове через bash указывать timeout > WAIT, иначе
   waitmail будет убит без осмысленного rc.
3. **Один шаг = одна итерация работы.** Вся оркестрация (почта, доска,
   wake-агентов, мержи, CI-мониторинг, планирование) выполняется ПОСЛЕ
   возврата rc, затем цикл повторяется.
4. **Полный цикл письма**: прочитать → обработать → пометить `[done ts]`
   в inbox (обязательно с ТОЧНЫМ msg_id включая timestamp — иначе письмо
   останется pending).
5. **Сердцебиение без писем не тратит ресурсы**: waitmail спит в ядре
   (select на fifo), токены не расходуются; каждый rc=1 — лёгкая итерация
   (waitmail) + Improvement Tick (анализ/кайдзен).
6. **Состояние между шагами**: журнал `.skynet/COORDINATION-STATE.md`
   обновляется при значимых событиях и на каждом Improvement Tick;
   почта/доска — в MCP-memory.

## Чек-лист входа в медитацию

- [ ] Зафиксировать текущее состояние в COORDINATION-STATE.md (если были
      значимые события).
- [ ] Убедиться, что все pending-письма в `skynet_inbox_0.coordinator`
      обработаны/помечены done (иначе первый же шаг вернёт MAIL — это
      нормально, обработать и продолжить).
- [ ] Вызвать `./.skynet/coordinator-step.sh 0.coordinator` с таймаутом
      вызова > COORDINATOR_WAIT.

## Чек-лист выхода (OWNER-CALL, rc=130)

- [ ] Прочитать директиву владельца в текущем промпте.
- [ ] При необходимости спланировать/делегировать агентам (письма+wake).
- [ ] Ответить владельцу результатом.
- [ ] Вернуться в цикл (снова `coordinator-step.sh`).

## Идемпотентность и отказоустойчивость

- FIFO-сигнал — лишь ускоритель; корректность всегда из памяти (потерянный
  сигнал безвреден — следующий вызов перечитает store).
- Если координатор убит жёстко (rc≠130): сессия возобновляется, состояние —
  из COORDINATION-STATE.md + MCP-memory, цикл стартует заново.
- Перед медитацией — убедиться, что оркестратор жив (`orchestrator-ctl.sh
  status`): он шлёт fifo-сигналы при новых письмах агентов.
