# SKILL: Мантра (проактивный cyclic loop координатора, v2.1)

> Режим работы координатора, заданный владельцем (2026-09-24): непрерывный
> проактивный цикл без ожидания промпта. v2.0 (2026-09-24): петля построена
> на **механическом блокирующем вызове** `coordinator-step.sh` (как у
> «Медитации»), а не на словесном обещании «перейти к началу цикла».
> v2.1 (2026-09-24): устранён механический дефект `waitmail.py parse_msg_id`
> (timestamp попадал в msg_id → done-копии с другим timestamp не совпадали →
> старые письма вечно pending → ложные MAIL-пробуждения). Петля теперь
> честно возвращает rc=1 (NO-MAIL) при пустой почте.

## Корневая причина залипания (почему v1.0 не работала)

v1.0 содержала только текст-описание шагов и PRODUCE-принцип («пустая почта
≠ нет работы»). Но в конце ответа последним действием был **текст** («перехожу
к началу цикла») — поток управления возвращался владельцу, следующая итерация
не запускалась. Текст-инструкция не создаёт петли.

**Второй (механический) корень** обнаружен при внедрении v2.0: `waitmail.py
parse_msg_id` включал timestamp в msg_id, поэтому amended done-копии с другим
timestamp не совпадали с оригиналом → старые письма вечно висели pending →
координатор каждым шагом получал ложный MAIL и «застревал» на пере-обработке
истории вместо новых событий. Фикс v2.1: mid = часть до `|`.

**Закон Мантры**: петля существует только пока последним действием каждого
прохода является ВЫЗОВ УТИЛИТЫ `coordinator-step.sh`, который БЛОКИРУЕТ до
события. Слова «в начало цикла» запрещены как финальное действие — вместо
них фактический повторный вызов.

## Механизм цикла (обязательный, механический)

```
loop {
  rc = coordinator-step.sh 0.coordinator   # БЛОКИРУЕТ до события (waitmail)
  case rc in
    0)   MAIL      → обработать всю почту (шаги 1-2) → continue (re-call)
    1)   NO-MAIL   → пройти полный проактивный проход (шаги 2-9) → continue
    130) OWNER-CALL→ прочитать директиву владельца, выполнить,
                     ответить в МАКС, вернуться в цикл (re-call)
    *)   UNEXPECTED→ диагностировать, залогировать, re-call
  esac
}
```

- Вызовы выполняются с `timeout` в инструменте `bash` БОЛЬШЕ `COORDINATOR_WAIT`
  (default 540с): `BOARD_SILENT=1 timeout 600 ./coordinator-step.sh 0.coordinator`.
- rc=1 (нет писем) — это НЕ пауза: выполняется полноценный проактивный проход
  (шаги 2-9 ниже) и сразу повторный вызов step.
- Выход из цикла — ТОЛЬКО по явной инструкции владельца (в rc=130 он может
  сказать «выйди из Мантры»). Иначе — бесконечный цикл.

## Анти-паттерны (запрещено)

1. **Завершать ответ текстом** «цикл завершён / жду / перехожу к началу» без
   фактического вызова `coordinator-step.sh`. Последнее действие каждого
   прохода — ВЫЗОВ УТИЛИТЫ.
2. **Ждать промпт** владельца между проходами: между проходами — только
   блокирующий `coordinator-step.sh`.
3. **Плодить работу** без причины (идемпотентность §20): шаг 5 — один элемент;
   чинить только реальные сбои; но исследование/планирование/обучение/метрики
   (польза) всегда допустимы.
4. **Подменять агентов**: найденная работа делегируется (письмо+wake).

## Коммуникация с владельцем

- Чтение МАКС — локальный `cmd_poll` (marker `.skynet/comm/.max-marker`),
  отправка — локальный `_reply` (USE_INSECURE_TLS=True, verify=False).
  GH-мост для МАКС НЕ нужен.
- Telegram — ТОЛЬКО через GitHub Actions (KB, telegram_bridge).

## Состояние между проходами
