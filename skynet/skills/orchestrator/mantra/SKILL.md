# SKILL: Мантра (проактивный cyclic loop координатора, v1.0)

> Режим работы координатора, заданный владельцем (2026-09-24): непрерывный
> проактивный цикл без ожидания промпта. Отличие от «Медитации» (event-driven,
> блокирует до события) — **Мантра самоподдерживающаяся**: даже при пустой
> почте и занятых агентах цикл порождает работу из себя (PRODUCE-шаг).
> Владелец пишет указания в МАКС; команда «повторяй Мантру» включает режим.

## Семантика команд владельца

- **«повторяй Мантру» / «продолжай цикл»** → войти в проактивный цикл Мантры
  (шаги ниже), повторять до получения иных инструкций.
- Владелец НЕ ждёт ответа на каждый шаг: он пишет указания/поправки в МАКС,
  они учитываются в начале цикла (шаг 0) и смешиваются с потоком задач.
- Выход из Мантры: явная инструкция владельца (новая команда/режим).

## Цикл Мантры (обязательная последовательность)

### Шаг 0 — Актуализация описания цикла
- Прочитать МАКС (локальный `max-bridge.py cmd_poll`, marker из
  `.skynet/comm/.max-marker`) и любые свежие сообщения владельца.
- Зафиксировать «актуальное описание цикла» — с учётом поправок владельца;
  оно потребуется для выполнения шагов и для итогового отчёта (шаг 8).
- Если пришли существенные поправки к самому циклу — перейти к шагу 9.

### Шаг 1 — Оркестрация / координация / разбор почты (без ожидания)
- Обработать ВСЮ почту координатора (`skynet_inbox_0.coordinator`): ответить,
  отревьюить, смёржить, закрыть `wait=`, обновить доску, раздать задачи.
- Каждое письмо после обработки пометить `[done ts]` (точный msg_id + timestamp).
- Проверить health/CI/доску; делегировать найденную работу (письмо+wake),
  не выполняя её сам (правило «координатор не исполняет обычные задачи»).

### Шаг 2 — Глубокий анализ обстановки и состояния агентов
- Gemba-обход фактов (не отчётов): heartbeat, busy-слоты vs живые процессы
  (pgrep) — нет ли зависших opencode/wakeup (инцидент B44); pending по inbox'ам;
  WIP колонок доски против лимитов.
- Оценка причин и эффективности: что замедляет рой, где узкое место
  (Theory of Constraints — очередь review/CI/busy-слоты).
- Устранение проблем немедленно (HEALTH-FIRST, #46–50): механический сбой →
  чинить сразу (kick, дроп сессии, перезапуск); новое/повторяющееся → B<n>
  в BACKLOG с владельцем.
- Оптимизация процессов: один конкретный дефект цикла за проход.

### Шаг 3 — Кайдзен с фокусом на рой
- Продвинуть здоровье роя: инфраструктура, wake-механика, гигиена mailbox,
  метрики, экономика координации (overhead-тренд из health-report).

### Шаг 4 — Кайдзен с фокусом на тесты
- Продвинуть тестовый контур: время прогонов, покрытие, golden-кейсы,
  связка тестов с фиксами, LTO/Werror-чистота тестового кода.

### Шаг 5 — Элемент «50 почему»
- Извлечь ОДИН незакрытый элемент `KAIZEN-COORDINATION.md` (цепочка «5 почему
  ×10» = 50 уровней → эпики E0–E11), взять в работу:
  сделать выводы, построить умозаключения, продвинуть или зафиксировать
  «почему не сегодня». Не более одного элемента за цикл (против «паралича
  анализа», #46–50).

### Шаг 6 — Агрессия: стратегии и тактики
- Исследуй, планируй, внедряй, делегируй. Смешивать с потоком задач, учиться
  комбинировать, копить опыт и использовать его. Делегирование — не
  «откладывание», а немедленное письмо+wake свободному агенту.

### Шаг 7 — Кайдзен: рефлексия / самосовершенствование / обучение роя
- Записать уроки в KAIZEN-COORDINATION.md и memory (MCP). Что новое узнали о
  рое/процессе; какой навык стоит формализовать.

### Шаг 8 — Отчёт владельцу в МАКС
- Написать в МАКС (локальный `_reply`): **описание выполненного цикла**,
  что обработано из «50 почему», какие исследования проведены, какую пользу
  выработал.

### Шаг 9 — Корректировка цикла
- Если были новые вводные/поправки владельца — скорректировать цикл,
  смешивая с потоком задач.
- Если цикл был скорректирован — написать об этом ещё раз (в МАКС);
  **существенные изменения документировать и внести в этот SKILL** (bump v).
- Перейти в начало цикла (Шаг 0). Повторять, пока не получены другие инструкции.

## PRODUCE-принцип (анти-залипание)

- **Правило**: «пустая почта + занятые агенты ≠ нет работы». В каждом проходе
  минимум одно проактивное действие: элемент «50 почему», исследование,
  улучшение инфраструктуры, подготовка следующей фазы, гигиена, метрики.
- **Запрещено** сообщать «ожидаю/завершил цикл, жду промпт» без фактического
  продолжения работы. Конец отчёта ≠ пауза: следующий шаг — немедленно в
  начало цикла.
- **Не плодить работу** (идемпотентность §20): шаг 5 — один элемент; только
  реальные сбои чинить; но «польза/подготовка» (исследование, планирование,
  обучение, метрики) — всегда допустима и поощряется.

## Коммуникация с владельцем

- Владелец пишет в МАКС; чтение — локальный `cmd_poll` (marker-файл
  `.skynet/comm/.max-marker`), отправка — локальный `_reply` (USE_INSECURE_TLS,
  verify=False). GH-мост для МАКС НЕ нужен.
- Telegram доступен ТОЛЬКО через GitHub Actions (записано в KB).
- Отчёт в МАКС — компактный (что сделано, польза), без перечисления каждой
  мелочи; подробности — в COORDINATION-STATE.md / KAIZEN-COORDINATION.md.

## Состояние между шагами

- Журнал `.skynet/COORDINATION-STATE.md` — при значимых событиях и на каждом
  цикле (строка «iteration N: ...»).
- Почта/доска — в MCP-memory; KAIZEN-журнал — KAIZEN-COORDINATION.md.
- При жёстком убийстве сессии: возобновление из COORDINATION-STATE.md +
  MCP-memory, цикл стартует заново с Шага 0.
