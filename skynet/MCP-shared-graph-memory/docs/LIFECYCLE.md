# Жизненный цикл AST-данных refactoring-map

> **Статус:** дизайн-документ (альтернативы/предложения/соображения зафиксированы,
> чтобы не потерять контекст). Реализовано на текущий момент — минимально:
> таблица `sym_aliases` + `refresh_stale` mark-not-delete при наличии алиаса.
> Полное обсуждение — с владельцем перед началом рефакторинга C→C++.

## Проблема

Карта исходников (`symbols`/`call_edges`/`groups`) **перегенерируется** после
каждого коммита (`map_load_batch(replace=True)`). Это самоизлечивает дрейф
координат, но во время тяжёлого рефакторинга C→C++ данные карты живут
**дольше одного поколения**:

- C-функция переименовывается/переносится в C++ (например `mdbx_env_open` →
  `mdbx::env::open`); канонический ключ меняется;
- символ удаляется (код перенесён в шаблон/заменён);
- блоки внутри функции меняют path-based id при переписывании тела;
- курируемые записи (баги, решения) связаны `related-to → fn:...` — при
  исчезновении символа знание теряется или становится висячим.

## Инварианты (цель)

1. **Ссылки переживают регенерацию**: курируемая запись, связанная с символом,
   не должна молча терять связь при переименовании символа.
2. **Переименование прослеживаемо**: `X был переименован в Y` — факт в памяти,
   с временем и причиной (provenance).
3. **Удаление не стирает историю**: символ, удалённый из карты, оставляет
   tombstone с последними координатами — для диффа до/после.
4. **Поколение карты известно**: каждому набору символов сопоставимо поколение
   (canary y) — чтобы отличать «ещё не просканировано» от «удалено».

## Текущее состояние (что уже есть)

| Механизм | Статус |
|---|---|
| `sym_ids`/`sym_id2key` — стабильные числовые id, не чистятся при replace | ✅ |

## Альтернативы по механизму переименования

### A. Таблица `sym_aliases` (old_key → new_key) + mark-not-delete — РЕКОМЕНДОВАНО
- Новый DBI `sym_aliases`: `old_key → new_key` (может быть цепочкой).
- `map_refresh_stale` при исчезновении символа: если есть алиас —
  **перенаправляет** ссылку на new_key (или помечает `stale:true`),
  а не удаляет; если алиаса нет — tombstone.
- Наполнение: курируемо (агент при рефакторинге явно вызывает
  `map_alias(old, new)`) + стартовая эвристика из `cpp_eq`/`mangled`.
- Плюсы: просто, аддитивно, ссылки переживают рефакторинг.
- Минусы: требует дисциплины (алиас надо заводить при переименовании).

### B. Автоматическое перенаправление по сигнатуре/телу
- При регенерации новый символ с похожей сигнатурой + тем же файлом/диапазоном
  автоматически считается «наследником» старого.
- Плюсы: не требует ручных действий.
- Минусы: ложные срабатывания (случайные совпадения), нестабильно, рискованно
  для accuracy карты. **Отклонено** как автоматика, допустимо как подсказка.

### C. Только tombstone + история (без перенаправления)
- Исчезнувший символ → tombstone в `archive`-подобной таблице; ссылки помечаются
  `stale`, агент вручную перенаправляет при разборе.
- Плюсы: максимально честно, ноль ложных связей.
- Минусы: ручной труд на каждом исчезновении; знание теряется до разбора.
- Компромисс: **tombstone всегда**, алиас — ускоритель, когда он известен.

## Соображения по остальным аспектам жизненного цикла

### Блоки и probes (`symbol#block-id`)
- Path-based id стабильны к вставке строк, но НЕ к переписыванию тела.
- Для сравнимости трасс до/после (behavioral parity) нужно сопоставление
  старых и новых блоков: кандидат — структурный fingerprint (последовательность
  kind'ов детей), не точный id.
- Влияние: probes/bookmarks (USDT) ссылаются на `symbol#block-id`; при
  переписывании их надо перенацеливать. Открытый вопрос — формат анкора.

### Поколение карты и diff
- Сейчас `generated_at`/`canary.y` — текущее поколение, но diff между
  поколениями нигде не хранится.
- Кандидаты: (a) таблица `map_generations` (gen → counts + snapshot deleted/
  added); (b) у каждого символа поле `since_gen`/`removed_gen`. (b) дешевле,
  но требует прохода при replace. Открыто.

### `sym_ids` — tombstone политика
- id не переиспользуются (sequence), ключ в `sym_id2key` остаётся — это
  уже tombstone-подобно. Оставить как есть; добавить пометку состояния
  (`alive`/`renamed`/`removed`) — кандидат на расширение значения.

### Покрытие после рефакторинга
- `coverage` (тест → символы) опирается на ключи; после переименования тесты
  покрывают новые ключи — старые связи `coverage` устаревают вместе с
  `refresh_stale`. При миграции coverage надо перепривязывать через алиасы
  (те же правила, что для curated-ссылок).

## Реализованный минимум (этот шаг)

1. `Store.TABLES["sym_aliases"]` — `DEFAULTS`, `old_key → new_key`.
2. `Store.map_alias(old, new)` — завести алиас (и обратный факт для истории?).
3. `map_refresh_stale` — при исчезнувшем символе: если есть алиас →
   помечаем связь stale (не удаляем безвозвратно; конкретная семантика —
   в реализации ниже), иначе — как раньше.
