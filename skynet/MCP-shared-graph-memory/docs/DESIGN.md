# DESIGN — постановка задачи и проектирование MCP-shared-graph-memory

## 1. Постановка задачи

Переписать персистентную память роя (ранее `memory-mdbx-server.py`, 4 subdb
`E/O/R/RV` на libmdbx) в новый модуль с гарантиями устойчивости для LLM-агентов.

**Проблемы legacy-сервера (факты):**
1. **Инцидент B48**: наблюдения в dupsort-таблице хранились как «ключ вложенного
   b-tree»; при странице 4K значение длиннее ~2022 B **молча не вставлялось**.
   Чанкование было паллиативом.
2. **Семантический тупик LLM**: повторяющаяся ошибка инструмента зацикливала
   агента на ретраях до исчерпания бюджета шагов (сессия fail rc=124). БД при этом
   всегда цела, libmdbx честно возвращает код ошибки.
3. Дыры аудита старого сервера: `_Txn.__exit__` не проверял rc commit/abort;
   `_put_observation` игнорировал rc; ABI-ошибка `c_int` вместо `c_size_t`.

**Требования владельца (подтверждены 2026-09-25):**
- Язык: Python + cffi.
- Чистый старт БД; старые данные — только в архиве (`mcp-memory-dump.yaml`,
  126 entities / 104 relations).
- Схему фаз 1 согласовать с внешним консультантом (Алиса, Yandex AI Studio).
- Дефолты: gc никогда не удаляет (только tiering + archive + явный purge);
  одна write-txn на операцию; автосвязывание убрано; unit-тесты прямыми вызовами
  без MCP; старый сервер остаётся до переключения.
- Много тестов, полное покрытие.
- Исходная инструкция владельца (`SKILL_mcp_memory_mdbx.md`) разделяется на
  SKILL по использованию и документацию по схеме.

## 2. Консультация с Алисой (итоги)

Раунд 1 — схема фаз 1:
- Рекомендован вариант **без TF-IDF векторов** для корпуса в сотни записей;
  векторы — после роста корпуса до тысяч.
- Mailbox/inbox — отдельный модуль/хранилище (не в этой БД); письма сохранены
  в архиве для анализа.
- SimHash-only (uint64) оправдан как дешёвый fuzzy-дедуп без косинуса.

Раунд 2 — уточнения:
- inverted лучше строить не как одну packed-строку, а через нативные
  возможности движка — это привело к выбору `MDBX_INTEGERDUP` (см. §3.2).
- LRU-поля — отдельная таблица `access` (не в теле записи): частые обновления
  не перезаписывают body, тиринг сканирует компактные записи.

## 3. Целочисленные индексы (INTEGERKEY / INTEGERDUP)

### 3.1 MDBX_INTEGERKEY

Ключи — бинарные целые **uint32/uint64**, native byte order, одного размера,
выровненные. Другие типы (signed, uint16, float) не поддерживаются.

| Преимущество | Механизм |
|---|---|
| Скорость сравнения | Числовое O(1), branchless-компараторы (`cmp_uint32/64`) |
| Компактность | 8 байт против ~40–60 байт у строкового ключа |
| Монотонные вставки | Автоинкрементные id ложатся на APPEND-путь (вставка в конец) |
| Range-поиск | Нативные `SET_RANGE` / `SET_LOWERBOUND` / `SET_UPPERBOUND` |
| Связка с мультизначениями | Пары «числовой ключ → множество целых» с `INTEGERDUP` |

Ограничения: строго uint32/uint64; **неприменим** к float (score) и строкам
(канонические ключи, термы); native byte order ⇒ перенос БД между архитектурами
с разным порядком байт потребовал бы миграции — **неактуально** (рой на одном
хосте, решение владельца).

### 3.2 Инвертированные списки на MDBX_INTEGERDUP

```
term (строка)  →  сортированное множество record_id (uint64)
таблица: DUPSORT | DUPFIXED | INTEGERDUP
```

Операции: добавление id — `cursor_put(..., MDBX_NODUPDATA)` (уникальность на
уровне движка); точечное удаление — `mdbx_del(txn, dbi, term, id)`;
пересечение термов — слияние сортированных постинг-списков O(|L1|+|L2|);
подсчёт — `cursor_count`; пакетное чтение — `GET_MULTIPLE`/`NEXT_MULTIPLE`.

**Ключевое преимущество над ранним решением «term → packed-список строк в
non-dupsort»:** каждое значение — отдельный элемент набора размером 8 байт, а не
одна растущая строка. Это полностью снимает лимит ~2022 B (корень B48), делает
обновление индекса точечным (CoW одного элемента) и открывает пакетное чтение.

### 3.3 Отклонённые варианты

| Вариант | Причина отклонения |
|---|---|
| `inverted` = dupsort, term → строковые ключи | лимит ~2022 B на значение, «салат» при переполнении |
| `inverted` = non-dupsort, term → packed-список | RMW всей строки, overflow-страницы, нет пакетного чтения |
| TF-IDF `float[64]` в фазе 1 | избыточно для сотен записей (решение Алисы) |
| `access` = dupsort-индекс `score → keys` | избыточно: gc-сортировка в памяти дешевле |
| `MDBX_DUPFIXED`/`INTEGERDUP` для строковых значений links | значения разной длины |
| `MDBX_REVERSEDUP` | направление сортировки не используется в логике |

## 4. Согласованная схема (итог)

11 DBI — см. [`SCHEMA.md`](SCHEMA.md). Ключевые свойства:

- **dupsort только в `inverted` и `links`** и только как `set<uint64 id>` —
  класс ошибок лимита исключён из основной схемы;
- канонические ключи остаются строками (`records`), чтобы работал prefix-recall
  `bug:crypto:*`;
- связь key↔id — таблицы `ids` и `id2key` (INTEGERKEY);
- `simhash` (INTEGERKEY) — скан-дедуп Hamming ≤ 3 для малого корпуса;
- `access` (INTEGERKEY) — score+last_access+access_count (24 B);
- `meta.next_id` — атомарный sequence внутри write-txn (в libmdbx нет sequences);
- контракт ошибок `error$CODE|CLASS|DESC|ACTION|RETRY` — см. `SKILL.md`;
- одна write-транзакция на операцию; конкурентные записи сериализуются движком
  (single-writer), `MDBX_BUSY` ретраится до 3 раз (класс `busy-io`).

## 4.1 Доработки по критическому ревью (окт 2026)

- **Поиск `search()`**: BM25-подобное ранжирование (IDF редких терминов) +
  включение структурного слоя (symbols/groups) при совпадении с
  идентификатором символа — единая точка входа «код + знания» для
  глубокого рефакторинга.
- **`safe_store(auto_vocab=True)`**: авто-регистрация новых модуля/темы в
  словарь (persist в vocab) вместо ошибки invalid; строгий режим — через
  `auto_vocab=False`. Новые темы в потоке рефакторинга не блокируют запись.
- **`links_in`**: денормализованный счётчик входящих рёбер (INTEGERKEY);
  обновляется при link/unlink/purge; fallback на скан для старых записей.
- **Слой тестов/CI**: таблицы `coverage` / `test_metrics` / `ci_jobs` и
  коллектор `tools/collect_test_metrics.py` (ctest XML/LastTest.log) —
  основа для реорганизации тестов (длительности, флаки, «тест → символы»).
- **Поколение карты**: `map_load_batch(replace=True)` инкрементирует
  canary.y (видимый diff поколений регенерации).
- **Фиксы**: `_merge` корректно выделяет новый id при отсутствии `_id`
  (иначе коллизия); traceback логируется в stderr на internal-ошибках MCP.

## 4.2 Полный E2E и Кайдзен-итерация (окт 2026)

После расширения до 76 MCP-инструментов модуль был **полностью опробован**
на живой БД: карта (`scan_symbols --config linux`), project-map, probes,
coverage/ci_jobs/test_metrics, traces, ADR, CBM-мост, `version_info`.
Каждое наблюдение → улучшение (по одному на итерацию):

- **map_symbols(prefix="fn:gc")** не находил символы по модулю: канонические
  ключи функций — `fn:{qname}`, module в теле. Добавлен аддитивный фильтр по
  `module`-полю тела (поиск по модулям работает). Документирована модель
  ключей (REFACTORING-MAP §symbols).
- **map_edges_of/map_callers_of** принимали только caller/callee — добавлен
  алиас `symbol` (дружелюбно для агентов).
- **scan_probes.py --db** падал (MODULE_DIR не в sys.path) — исправлено.
- **ci_jobs tests_hint** не резолвился: реестр cells — `list[dict]`
  (id + ctest), а не dict; `map_ci_jobs` теперь раскрывает cell → тесты.
- **CI-workflow**: после merge не запускался `scan_uncovered` — добавлен.
- **Версионный контроль**: добавлен `version_info` (модуль / libmdbx /
  схема / данные); `meta.schema_ver` пишется при создании БД;
  `schema_matches` — контроль совместимости.
- **Дисциплина ключей** для агентов зафиксирована в SKILL («не выдумывайте
  fq-ключи; получайте через map_symbols/map_symbol»).

## 4.3 Пилот «покрытие подсистемы GC» (окт 2026)

Проверка «реального покрытия тестами и белых пятен» на живой БД:

- **`tools/gcov_to_coverage.py`**: прогон `mdbx_test` (smoke_basic) с gcov →
  `.gcda` → `gcov -b` → {file: covered_lines} → карта → символы + **блоки**.
  Загрузка: `coverage:{test}` (символы) + `coverage_blocks:{test}:{sym}`
  (блочная детализация). Результат: 47 файлов, 508 символов, 812
  блочных записей.
- **Дашборд GC**: `coverage_gaps(module="gc")` → 44 непокрытых символа
  (`consume_remaining`, `defrag_aborted`, `dbg_*` и др. — белые пятна);
  `coverage_symbols`/'coverage_get' → 27 покрытых GC-символов smoke-сценария.
  Реальная ценность: «какие тесты покрывают КАЖДЫЙ блок» — блочная
  детализация (blocks) + обратный индекс.
- **Probes GC**: в реестре 10 зондов (rkl_check_*, watch). Расстановка
  недостающих пробников (спилл, alloc-пути) отложена на итеративное
  развитие покрытия.
- **Вывод**: пилот подтвердил ценность связки «карта → gcov → блочный
  coverage → gaps/probes». Для полного покрытия нужен сбор покрытия по
  ВСЕМ тестам (по celл у coverage), а не одному smoke.

## 5. Критерии приёмки

1. Валидация: unit-тесты ≥ 95% покрытия, прогон `nice -n 10`.
2. E2E: MCP-диалог через stdin (initialize → vocab_add → safe_store → recall).
3. Ошибки — только контрактные (`error$...`), как JSON-RPC protocol error (-32000).
4. Лимит ~2022 B больше не является источником сбоев записи.
5. Старый сервер не затронут до переключения сессий.
